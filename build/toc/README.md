# 목차 템플릿 빌더

사이드바 **목차 템플릿** 화면이 쓰는 장(L_TOC_*)과 업종별 내용을 만드는 스크립트.

표준 제안서 템플릿은 업종별 표준 제안서 44종(`bs_std_<업종>`, `app/scripts/vertical_standard/`)을 그대로 쓴다.
다른 템플릿도 표준 제안서와 이름이 같은 목차(Overview · AI 업종 · 공간별 제안 · 업종 솔루션 · 도입사례 · Why Samsung)는
그 업종 표준 제안서의 장(L_VS_*)을 그대로 옮기고, 장 번호 · 간지 쪽 · 덱 이름 · 쪽 번호만 바꾼다.
여기서 만드는 것은 표준에 없는 목차의 장과 내용뿐이다.

| 결과물 | 만드는 스크립트 | 입력 |
| --- | --- | --- |
| `app/web/src/domain/templates/toc_layouts.js` — 장 42개(TOC_META · TOC_HTML · TOC_SLOTS, 은퇴 2개 포함) | `python3 build/toc/gen_module.py` | `layouts.py`(장 디자인) · `base.py`(+ `build/v25/std.py`) |
| `app/web/src/domain/templates/toc_content.json` — 업종 44개 내용 | `python3 build/toc/build_content.py` | `app/data/vertical_space_product.json` · `vertical_space_solution.json` + 아래 문구 |
| 위 JSON의 `pp` — 업종별 제품 제안서(대표 제품 · 관련 솔루션 · Value Prop 3 · 유관사례 2 · Spec) | `build/toc/product.py` (`build_content.py`가 부름) | 업종 표준 제안서 시나리오 · 채움, 제품 상세(USP · 기능 · 사양) · 제품 DB, 공식 도입사례 · 사례 사진 |
| `app/web/public/assets/toc/icons/<기능 id>.on/off.png` · `ui-*.png` · `cp-*.png` | `cd build/toc/icons && npm i && node make_icons.mjs && node make_ui_icons.mjs && node make_cp_icons.mjs` | `feature_icons.json`(기능 id → Lucide 아이콘, ISC) · 경쟁사 비교 기준 아이콘 35개(`make_cp_icons.mjs`) |

## 추천 구성 — 전체 파트 목록의 파트만 (2026-11-16)

추천 구성(`toc_templates.js` `TOC_TEMPLATES`)은 관리자 「전체 파트 확인하기」 목록에 있는 파트만 쓴다 — Overview · 당사의 이해 · AI {업종}(3 Value Props) · 공간별 제안 ·
공간별 가치 제안 · {업종} 솔루션 · 도입사례 · Why Samsung · 유관사례 · Spec · 구독 솔루션.

| 구성 | 목차 |
| --- | --- |
| 표준 제안서 `std` · 확장형 `stdx` | (Overview \| 당사의 이해) → AI {업종} → 공간별 제안 → {업종} 솔루션 → 도입사례 → Why Samsung — 그대로 |
| 공간 가치형 `space` · 확장형 `spacex` | (Overview \| 당사의 이해) → 공간별 가치 제안 → {업종} 솔루션 → 도입사례 → Why Samsung |
| 과제 해결형 `pain` | 당사의 이해 → AI {업종} → 공간별 가치 제안 → 도입사례 → Why Samsung |
| 구축형 `build` | 공간별 제안 → {업종} 솔루션 → 도입사례 → Why Samsung → Spec |
| 제품 제안서 `prod` | AI {업종} → 유관사례 → Why Samsung → Spec |
| 구독 제안서 `subs` | Overview → 구독 솔루션 → 공간별 제안 → 도입사례 → Why Samsung |
| (자동 변형) 표준 + 구독 솔루션 `stdsub` | 표준 제안서의 도입사례 앞에 구독 솔루션 |

- **Spec 은 구성의 맨 마지막에만** 온다(`specLast` — 구독 솔루션을 더할 때도). 구성은 파트 4–10개(목차 장 `L_TOC_INDEX4–10`). 둘 다 모듈을 읽을 때 확인한다.
- **은퇴**(`RETIRED_TEMPLATES`): 투자 효과형 `roi` · 경쟁 비교형 `compete` · 요구사항 대응형 `rfp` · 투자 효과형 + 구독 `roisub` · 구독 전환 `subsl` — 목록에서 뺀 목차(제안 요약 · 기대 효과 ·
  비용 · 구매 · 파일럿 · 확산 · 실행 계획 · 요구사항 대응 · 제품 사양 · 구성 · 수량 · 핵심 기술 · Value Props · 구독 한 장 요약)가 뼈대라 지금 파트로 나타낼 수 없다. 추천 · 목록 · 관리자 화면에는 없고,
  이 구성으로 이미 만든 제안서를 위해 `TPL` 로 찾을 수만 있다(조립도 된다). 그 목차의 장 · 조립 코드는 그대로 남아 있다.
- 다시 짠 구성으로 예전에 만든 제안서는 목차 키로 견본 장을 찾는다(`services/layout-compose.js`) — 지금 구성에 없는 목차는 견본 없이 구성한다.
- 연결 샘플(`related`)은 다시 짠 구성에서 비웠다 — 옛 샘플은 파트 구성이 다르다(폴 바셋 덱은 옛 공간 가치형 확장형 기준, 구독 샘플 9종은 구독 목차 넷 기준).

## 당사의 이해 — 업종 묶음별 항목 · 새 장 (L_TOC_UA_<묶음>_<항목>)

당사의 이해는 파트는 하나지만 업종에 따라 짚어야 할 것이 크게 다르다(사용자 규칙 2026-11-16). 그래서 업종을 **크게** 묶고(세부 업종 44곳 → 12묶음 — 대형 · 중소 병원 · 의원 · 요양은 같은 「병의원」, 학교와 오피스는 다른 묶음),
묶음마다 이해 항목을 따로 정해 항목마다 장을 **새로** 그렸다. 기존 당사의 이해 장(`L_TOC_UAPROF` · `UAPAIN` · `TR*` · `CP*`)은 쓰지 않는다.

| 묶음 | 세부 업종 | 이해 항목 (장 4개) |
| --- | --- | --- |
| 외식 · 카페 `FB` | 프랜차이즈 · 카페 · 식당 | 매장망 → 주문 흐름 → 운영 구조(본사 · 지역 담당 · 점주) → 메뉴 · 행사 주기 |
| 리테일 · 서비스 매장 `RT` | 리테일 4 · 생활 서비스 4 · 통신 매장 | 점포 포맷 → 고객 동선 → 판촉 · 진열 교체 → 운영 시간 · 인력 |
| 호텔 · 숙박 `HT` | 대형 · 중소형 · 레지던스 | 객실 · 부대시설 → 투숙객 · 성수기 → 투숙 여정 → 브랜드 표준 · 시스템 |
| 문화 · 여가 · 집회 시설 `CU` | 테마파크 · 전시 · 경기장 · 공연장 · 피트니스 · 종교 | 규모 · 방문객 → 시즌 · 행사 일정 → 관람 동선 → 콘텐츠 · 수익 |

| 주거 `RS` | 아파트 · 오피스텔 · 시니어 · 인테리어 파트너 | 단지 · 평형 → 사업 일정 → 의사결정 구조 → 세대 · 커뮤니티 |

| 공공 · 교통 · 국방 `PB` | 공공기관 · 교통 인프라 · 군 | 기관 · 이용 규모 → 예산 · 조달 일정 → 인증 · 보안 요건 → 서비스 공간 |

| 제조 · 물류 `MF` | 공장 · 물류센터 | 사업장 · 교대 근무 → 공정 · 물류 흐름 → 현장 환경 → 안전 · 현장 시스템 |
| 금융 `FN` | 영업점 · 본점 | 영업망 · 점포 유형 → 내점 고객 여정 → 디지털 전환 → 보안 · 규제 |
| 미디어 · 광고 `MA` | 옥외 광고 · 방송 스튜디오 | 매체 현황 → 편성 · 구좌 → 광고주 · 판매 방식 → 규제 · 화질 기준 |

**경쟁 우위 3장** — 묶음마다 이해 항목 4장 뒤에 붙는다(사용자 규칙 2026-11-16: 경쟁사보다 나은 점을 보이는 것이 매우 중요하다. 근거는 통합 솔루션 · 제품의 핵심 스펙에 바탕을 둔 key message · 여러 사례).
세 장의 틀은 같고(`ua/compete.py`), 업종마다 달라지는 것은 묶음 파일의 `COMPETE` 가 정한다.

| 장 | 무엇을 보이나 | 업종마다 정하는 것 | 삼성 칸(실제 값) | 경쟁사 칸 |
| --- | --- | --- | --- | --- |
| 경쟁 구도 · 통합 솔루션 `…_RIVAL` | 업종의 영역 5곳마다 삼성이 놓는 제품(컷)과 하나로 묶는 솔루션 띠, 그 아래 경쟁 유형 둘이 맡는 영역 — 삼성 5 / 5 대 경쟁 n / 5 | 영역 축(병원: 로비 · 원무 → 진료실 → 병동 · 간호 → 병실 냉난방 → 병실 공기 / 학교: 교실 칠판 → 학생 기기 → …) · 영역마다 제품 · 묶는 솔루션 | 그 업종의 제품 분류 · 컷 · 솔루션 이름 | 경쟁 유형 이름(익명 — 앱의 업종별 경쟁 유형) + 영역마다 한마디 — **예시**, 조사한 내용으로 바꾼다 |
| 핵심 스펙 `…_EDGE` | 대표 제품 컷 + 스펙 값 셋과 그 값이 이 업종에서 뜻하는 것(key message) | 대표 제품(그 묶음 업종의 대표 제품) · 스펙 셋 · 메시지 | 제품 이름 · 모델 · 스펙 값 | 같은 항목의 경쟁 제품 값 `00` — 조사해 직접 입력 |
| 같은 업종 사례 `…_PROOF` | 공식 도입사례 셋(사진 · 어떤 곳 · 도입한 것 · 도입 포인트 · 원문 시기) + 같은 업종의 다른 사례 이름 | 사례 셋 | 그 묶음 업종의 표준 제안서에 실린 samsung.com 도입사례 | 경쟁사가 낸 같은 업종 사례 수 `00` — 조사해 직접 입력 |

- 삼성 칸은 지어 적지 않는다 — `ua/data.py` 가 앱 자료(`toc_content.json` 의 제품 · 솔루션 · 스펙 · 경쟁 유형, `standard_vertical_scenarios.json` 의 도입사례)에서 읽고, 묶음 파일에 적은 이름이 자료에 없으면 생성이 멈춘다.
  경쟁사의 숫자도 지어 적지 않는다(스펙 값 · 사례 수는 `00`, 경쟁 유형 칸에는 숫자를 쓰지 않는다). 제품 DB · 사례가 바뀌면 `gen_ua_catalog.py` 를 다시 돌린다(검사가 파일과 생성 결과가 다르다고 알려 준다).
- 간지는 줄이 여섯까지라 항목 7개 묶음은 `L_VS_DIV_R6` 을 쓴다.

- 묶음 하나 = `build/toc/ua/<묶음>.py` (`CLUSTER` — 이름 · 세부 업종 · 예시 고객 · 목표, `SHEETS` — 장을 그리는 함수들, `COMPETE` — 경쟁 우위 3장의 업종별 설정). 그리기 도구는 `ua/kit.py`
  (목차 템플릿 장과 같은 디자인 체계 `base.py`, 글자 역할을 처음부터 구운 `typed.TT` — 글자 크기는 역할 크기만 쓴다).
- **숫자는 `00`** — 고객사마다 다른 값이라 작성자가 직접 넣는다(`kit.Z`). `[00]` 같은 자리표시는 쓰지 않는다. 항목 이름 · 예시 글은 그 업종에서 흔한 것을 적어 두었다.
- 새 장의 눈썹 글은 `01 · 시장 분석 (MI) · <항목>` — 목록에서 이 파트를 '시장 분석 (MI)'라고 부른다(2026-11-16: 당사의 이해 → 고객사의 이해 → 시장 분석 (MI). `ua/kit.py` 의 `PART_NAME`, 관리자 `part-flows.js` 의 `PART_CATALOG.names`). 제품 스펙 새 장(`gen_spec_sheets.py`)도 같은 식으로 `04 · 제품 스펙`. 앱의 목차 이름은 아직 '당사의 이해' · 'Spec'이다.
- 묶음을 더하거나 항목을 바꾸면 `python3 build/toc/gen_ua_catalog.py` 로 `admin/web/src/ua-catalog.json` 을 다시 만든다(묶음 하나만 빨리 볼 때는 `… gen_ua_catalog.py md`).
  생성기가 확인하는 것: 세부 업종 44곳이 꼭 한 묶음에 · 장 이름 규칙 · 이미 있는 장과 이름이 겹치지 않음 · 칸 이름이 겹치지 않음 · 경쟁 우위 장의 제품 · 솔루션 · 스펙 · 사례가 앱 자료에 있음. 검사: `node admin/tests/ua-sectors.mjs`.
- **지금은 관리자 「전체 파트 확인하기」 팝업만 읽는다.** 앱 레이아웃 목록(`toc_layouts.js`) · 실제 덱(`toc_templates.js` 의 `B.ua` — 구성마다 고른 기존 장)에는 아직 넣지 않았다.
  장은 같은 빌더 · 칸 이름 규칙으로 그려 두었으므로, 실제 덱에 쓰기로 하면 `layouts.py` 의 `build()` 에 올리고 업종 묶음 → 장 순서를 `B.ua` 에 옮기면 된다
  (이때 숫자 `00` 이 자리표시 규칙 — `app/web/src/domain/slides/placeholders.js` — 에 걸리는지 먼저 확인한다).

## 고객/공간 시나리오 · 서비스 제안 (2026-11-17)

## 규칙
- 요구사항에 따라 더하는 목차(add-on): 고객 요구에 구독 · 렌탈 · 월 납부가 있으면 어느 템플릿에든 '구독 솔루션 제안'만 더한다(`ensureTocScenario(tid, vid, {addons: ['sub']})`, 자리 = 비용 · 구매 뒤 또는 실행 · 사례 · Why 앞). 이것을 기본으로 넣은 템플릿이 표준 제안서 + 구독 솔루션(stdsub) · 투자 효과형 + 구독 솔루션(roisub) — `build/subs/README.md`.
- 같은 목차 이름이면 어느 템플릿에서든 같은 장. 표준 제안서와 같은 이름이면 표준 제안서 장 그대로(공간별 가치 제안의 조감도도 표준 조감도 장).
- 새 장에는 부제 · 각주 · 작은 설명 글을 넣지 않는다. 제목 한 줄 + 사진 · 아이콘 · 숫자.
- 개수가 바뀌는 칸만 변형을 둔다(목차 4–8 · 솔루션 1–4 · 여정 1–3 공간 × 솔루션 1–2 · 수량표 3–8).
- 제품 제안서: 업종 표준 제안서의 대표 제품 하나(업종마다 먼저 고르는 분류 `PREF`, 사양 8줄 이상) + 그 제품과 같은 공간에서 쓰는 표준 솔루션.
  - Value Prop 3 — 제품 + 솔루션이 셋이면 하나씩, 솔루션이 하나면 제품 가치 둘, 없으면 제품 가치 셋, 셋보다 많으면 솔루션을 둘로 추림. 솔루션 이름이 든 제품 가치는 쓰지 않는다. 제목은 간지 한 줄(290px)에 들어가는 길이.
  - 가치마다 상세 장 하나 이상 — 첫 제품 가치는 표준 공간 장(그 제품이 놓인 공간), 다음 제품 가치는 제품 사진 + 한 줄, 솔루션 가치는 표준 솔루션 장 + (제품과 함께 쓰는 공간이 있으면) 그 장면(쓰는 기능만 켬). 간지 줄 하나 = 가치 하나.
  - 유관사례 2 — 같은 제품군 공식 사례(사진 4장 이상), 이 제품 · 같은 업종 · 이 업종 표준 사례 순. 간지 한 줄은 두 사례 모두 이 제품을 쓸 때만 제품 이름, 아니면 제품군(`CASE_FAM`).
  - Spec — 사양 8 + 숫자 3. 괄호 단위는 값으로(`배터리 용량 (mAh)` 390 → 390 mAh), 최소/정격/최대는 정격(최대), 같은 이름 · 포장 · 대기 전력 · 설치 배관/배선 · 모델 코드 · 있음/없음 · 단위 없는 숫자는 뺀다.
- 화면: 목차는 Storyboard 목차 버블(`components/part-bubble.jsx`)을 쓴다 — 유형 아이콘 원 · 순서 · 이름 · 점선. 목록 · 팝업에서는 작은 버블(`.pb-mini`)로 비중을 줄이고 템플릿 이름을 크게. 카드 = 목차마다 한 칸(작은 버블 + 그 목차의 대표 장, 칸 순서 = 목차 흐름 = 덱 순서). 템플릿 카드에 왼쪽 색 띠를 두지 않는다.
- 상세 팝업: 헤더 오른쪽 드롭다운으로 업종(그룹별 44, 찾기 · ↑↓ · Enter · Esc)과 이 양식이 다루는 기존 샘플을 고른다. 그 아래 작은 목차 버블 흐름 한 줄(지금 보는 목차는 유형 색 바탕, 누르면 그 목차 첫 장) → 왼쪽 장 썸네일 세로 목록(목차마다 작은 버블 머리) + 오른쪽 큰 장(← → 로 넘기기, 누르면 크게 보기). 업종을 바꿔도 같은 목차 자리에 머문다.
- 표준 장을 옮겨 쓸 때 장 번호(눈썹 · 간지 · 역할 이름의 'NN')는 이 덱의 목차 번호로 바꾼다.
- 조립: `app/web/src/domain/templates/toc_templates.js` — `ensureTocScenario(템플릿, 업종)`이 시나리오를 시나리오 레지스트리(SC · FILLS · STORY)에 올린다(표준 제안서는 `bs_std_<업종>` 그대로). 검사: `node --test app/tests/toc-templates.mjs`.
