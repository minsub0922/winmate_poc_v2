# 히스토리 예시 개편 — 채우기 가이드 (케이스 담당용)

Winmate v2(삼성 B2B 제안서 작업대) 사이드바의 **제안서 히스토리 예시**를 다시 만든다. 사용자 요구(그대로):
> 히스토리 예시들을 개선해. 제안서 흐름에 맞게 제대로 기승전결을 구성해. 전반적으로 검토 및 개선해. 그리고 각 storyboard 단계마다 하나이상의 layout 이 있어야해. 지금은 너무 하나씩 있어.
사용자가 이미 밝힌 선호: 글만 있는 장은 피로도가 크다 → **사진으로 요소가 채워지는 레이아웃**. 사진은 samsung.com/business · 카탈로그 사진 우선.
그리고 이 히스토리는 **모든 숫자가 정확해야** 한다(이전 작업에서 사용자가 가장 강조한 점).

작업 폴더 `/home/claude/wm` (명령은 모두 여기서). **src/ · data/ · dist/ 는 고치지 않는다.** 쓰는 곳:
- `build/hist/out/<id>.json` — 결과(이 케이스의 새 Storyboard 전체)
- `build/hist/out/<id>.notes.md` — 메모(결정 · 새 사진 · ledger 추가 · 남은 문제)
- 새 사진: `build/hist/newimg/` (addphoto.py 가 씀)

## 1. 받은 것
- 브리프 `build/hist/briefs/<id>.md`: **이번에 만들 Storyboard(PLAN)**, 고객 요구사항 원문, 선택 제품 · 솔루션 · 사례(카탈로그 proof 원문), 이 케이스 **수치 출처 대장**, 공통 공개 자료 · 삼성 공식 사양 · 작성 원칙, **지금 Storyboard 값**(옮겨 쓸 재료 — 정확성 감사를 이미 통과한 값).
- 시작 파일 `build/hist/start/<id>.json` — 지금 값을 결과 형식으로 옮긴 것(참고용. 레이아웃 대부분이 RETIRED 텍스트 장이라 그대로 쓰면 검사에서 오류).
- 레이아웃 고르기: `build/hist/sheets/<파트유형>-N.jpg`(그림 위 f · 사진/글 · 칸 수 · 업종) — 파트 유형별 목록은 `build/hist/sheets/INDEX.md`. 크게 보기 `build/hist/gal/<f>.jpg`.
- 칸 보기: `node build/bs/slots.mjs <f> [f2 …]` — 글 칸 번호 · 예시 글 · 크기 · 글자 크기 · 한 줄 글자 수(대략) · 사진 칸 · 고정 글.
- 사진 라이브러리: `build/bs/lib/catalog.md`(id · addr · 내용 · 크기 · 출처, 업종 묶음별) + 미리보기 `build/bs/lib/sheets/g??-?.jpg`(사진 위 #id). `grep -n '병원\|병실' build/bs/lib/catalog.md` 처럼 찾기.

## 2. 결과 형식 — `build/hist/out/<id>.json`
```json
{
  "id": "p_case_f1",
  "deck": [ { "f": "L_C02", "status": "done", "t": { "0": "…" }, "img": { "0": { "src": "img/ph/…", "name": "…", "keep": true } } } ],
  "parts": [
    { "act": "기", "type": "market", "name": "오르는 전기요금, 절반은 냉난방", "items": ["…", "…"],
      "layouts": [
        { "f": "L_PH_MS_A", "status": "done", "t": { "0": "01 · 시장 환경", "5": { "html": "첫 줄<br>둘째 줄" } }, "img": { "0": { "src": "img/fill/r4-svht.json#3", "name": "무인 매장 내부", "keep": true } }, "r": [["B 호텔", "N 스터디카페"]] },
        { "f": "…", "status": "done", "t": {}, "img": {} }
      ] }
  ],
  "ledger": [ { "n": "27.47", "src": "산출: 450 ÷ 16.38 (제작자 메모)" } ],
  "notes": "한 줄 요약"
}
```
- `act`: 기 · 승 · 전 · 결 (순서가 거꾸로 가면 안 됨). `type`: 파트 유형(PLAN 그대로). `name` · `items`: PLAN 을 따르되 다듬어도 됨(items 2~4개, 슬라이드 내용과 같은 말).
- 자유 주제 파트(E 케이스)는 `"type": "free", "form": "free", "text": "…"` 를 그대로 유지.
- **파트마다 layouts 2~3장.** deck 은 표지 1장(사진 표지: L_C01 · L_C02 · L_C08 또는 업종 표지). 목차 · 간지는 넣지 않는다.
- 장: `f`(레이아웃) · `status`(done · partial · empty) · `t`(글 칸 번호 → 문자열 또는 `{ "html": "…<br>…" }` — `<br>` · `<b>` · `<span style=…>` 정도만) · `img`(사진 칸 번호 → `{ src, name, keep, pos?, fit? }`) · `r`(편집 칸이 아닌 **고정 글**의 예시 고객 이름 · 자리표시 치환 `[[원래, 바꿀]]`).
- 사진 레이아웃(L_PH_* · L_C*)의 사진 칸은 `"keep": true`(칸의 틀 · 배지 · 캡션은 두고 사진만 바꿈). 제품 컷은 `"fit": "contain"`.
- `ledger`: 대장(브리프)에 없는 숫자를 새로 쓰면 반드시 여기에 출처 · 계산식. 검사가 ‘대장 밖 숫자’로 알려 준다.

## 3. 상태(status) 규칙
- **done**: 그 장의 **모든 의미 단위**를 이 케이스 값으로 채운다 — 글 단위마다 칸 하나 이상 값, **사진 칸은 전부 img 값**(레이아웃 기본 사진이 딱 맞아도 같은 주소를 img 로 적는다 — 안 적으면 앱이 ‘예시 그대로’로 센다). ‘01’ · ‘시사점’ 같은 구조 글도 그 단위에 값이 하나도 없으면 같은 글을 다시 적어 둔다. 예시 고객 이름 · [00] · 다른 업종 글이 한 글자도 남으면 안 된다. 검사 `✗` 0.
- **partial**(작성 중 케이스만): 제목 · 머리말과 앞쪽 단위 일부만 채우고 나머지는 예시 그대로 — 실제로 쓰다 만 모습. 채운 칸은 done 과 같은 기준으로 정확해야 한다. 단 **꼬리말 · 사진 · 사진 캡션은 이 케이스 값으로**(다른 업종 사진 · 다른 고객 이름 꼬리말이 채운 글과 모순되지 않게) — 예시 그대로 남기는 것은 뒤쪽 글 단위 일부만.
- **empty**: `t`·`img` 없이 `f` 와 `status` 만(레이아웃만 골라 둔 상태).
- F 케이스는 전부 done. P · S1 · A · E 는 PLAN 의 상태 배치를 따른다.

## 4. 기승전결과 장 고르기
1. PLAN 의 파트 순서 · 장 역할대로. 한 파트의 2~3장은 **같은 말을 되풀이하지 않고** 서로 다른 각도(수치 → 장면, 문제 → 원인, 구성 → 수량 …)로 이어진다. 앞 장의 결론이 다음 파트의 질문이 되게 제목을 쓴다.
2. 레이아웃은 **사진 중심 장 우선**(sheets 의 ‘사진’ 표시). RETIRED 장 금지(검사가 잡음). 글 · 표가 본질인 장(RFP 대응표 L_RM_C · L_SC_B 등)은 그대로 써도 된다.
3. 업종 전용 레이아웃(MI_FB_A · SS_MD_x 처럼 업종 코드가 붙은 장)은 그 업종 케이스에서만. 공통 장은 어디서나.
4. 칸이 이 케이스 사실로 **정직하게 다 채워지는** 장을 고른다. 숫자 칸이 많은데 근거 숫자가 없으면 그 장은 고르지 않는다(지어내지 말 것).
5. 덱 안에서 같은 레이아웃은 두 번 쓰지 않는다(표지 · 마무리 제외하고도 가급적).

## 5. 글 원칙 (정확성 — 가장 중요)
1. 숫자는 다섯 곳에서만: ① 고객 요구사항 · 첨부 · 제작자 메모(가상의 고객이 준 값) ② 그 값의 계산(장에 ‘산출’ 표기, ledger 에 식) ③ 브리프의 공식 통계(장에 ‘출처: 기관 · 자료명’ 표기) ④ 삼성 공식 사양(브리프 B 표 값만 — 카탈로그 spec 이 다르면 B 표가 맞다) ⑤ 카탈로그 사례 proof · scale 원문(사례 이름과 함께, 원문 그대로).
2. 고객 **목표**는 ‘목표’, 가정은 ‘가정’, 측정 안 한 효과는 ‘기대’로 표기. 결과처럼 쓰지 말 것(예: 15% → “15% 절감 목표”, 15.84억 → “영업본부 목표(가정)”).
3. 금지: 삼성 제품 가격 · 견적 · 투자비(고객이 준 예산 상한만), 근거 없는 성능 주장(“업데이트 90% 단축”), SmartThings Pro 의 % 절감, 무풍 61%를 상업용 4Way 에 쓰기(가정용 시험 · 자사 실험치), 서비스센터 수, 장애 대응 시간 약속. 삼성 실험치는 ‘자사 실험치’ 단서와 조건을 함께.
4. 고객 이름은 브리프 그대로(예: “N 스터디카페”). 실존 기업 이름은 **사례 장의 카탈로그 사례 고객명**에서만. 다른 예시 고객 이름 · [00] · [고객사] · [N] 이 화면 어디에도 남으면 안 된다(고정 글은 `r`).
5. 덱 안 같은 지표는 같은 숫자 · 같은 표기. 장 머리말 번호는 파트 순서(01 · 시장 환경 → 02 · … ), 한 파트의 장들은 같은 번호.
6. 길이: 칸의 줄 수 · 한 줄 글자 수 안. 제목 한두 줄(대략 32자 × 2 이내), 칸이 한 줄 고정이면 한 줄. 넘침은 검사가 잡는다.
7. 문체: 지금 값처럼 짧은 명사구 · ‘·’ 구분, 제목은 “~합니다/~입니다”. 느낌표 · ‘혁신적’ · ‘최고의’ 금지. 영어는 제품 · 솔루션 이름만.
8. 꼬리말(예: “B 호텔 · 사진: samsung.com 호텔 도입사례”)도 이 케이스 값으로: “N 스터디카페 · 지점 냉난방 원격 운영 제안 · 사진: samsung.com” 처럼. 담당 · 연락처 칸은 “삼성전자 B2B 영업팀” · “제안 메일로 회신” 같은 일반 표기(가짜 이름 · 전화번호 금지).

## 6. 사진 원칙
1. 모든 사진 칸이 **이 장 내용 · 이 업종**에 맞는 사진. samsung.com 출처(img/ph · img/fill/*.json#k · r9 묶음 · 제품 컷) 먼저, Unsplash(img/bs/bsNN-*) · stock(img/cover)은 맞는 samsung.com 사진이 없을 때만.
2. 고객은 가명이다. **실존 브랜드 로고 · 간판이 크게 보이는 사진**(스타벅스 · 맥도날드 · 은행 · 구단 등)은 그 사례를 다루는 사례 장에서만, 가명 고객의 모습으로는 쓰지 않는다.
3. **한 덱 안에서 같은 사진은 한 번만**(제품 컷 예외). 검사가 잡는다.
4. 라이브러리에 맞는 사진이 없으면 samsung.com 에서 새로 가져온다(케이스당 8장 이내):
   - 후보: `python3 build/hist/caseimgs.py <samsung.com 페이지> <이름표>` → 목록 + `build/hist/tmp/cand-<이름표>.jpg`(Read 로 보기). 페이지 찾기: data/catalog.json cases(url) · samsung.com/sec/business 업종 · 제품 페이지.
   - 가져오기: `python3 build/hist/addphoto.py <images.samsung.com 주소> <케이스코드-이름> "<내용>" <출처 페이지> [--crop x0,y0,x1,y1]` → 주소 `img/hist/<이름>.jpg` 로 쓴다(이름 예: `f2-ward-room`).
   - 글 · 로고가 큰 배너, 얼굴이 크게 잘리는 컷은 피하고 필요하면 --crop.
5. 칸 비율 · 해상도에 맞게(검사 ‘해상도 부족’), 잘리면 `pos`(예: "50% 30%").

## 7. 검사 — 끝내기 전에 반드시
```
node build/hist/check.mjs <id> --shots        # 전체 (한 장만: --only 3,7 — k 번호는 검사 출력 첫 칸)
```
- `✗` 오류(구조 · RETIRED · 넘침 · 잘림 · 겹침 · 빈 사진 칸 · 자리표시 · 다른 고객 이름 · done 인데 예시 그대로 · 같은 사진)는 **0개**까지.
- 다르게 자른 같은 사진 · 흑백 사본은 `python3 build/hist/dupcheck.py <id>` 로 따로 잡는다(SIFT 일치점). `✗`(80 이상)는 같은 사진이니 고치고, `?` 는 눈으로 확인.
- `? 대장 밖 숫자`는 하나씩: 대장 · 요구사항에 있는데 표기만 다르면 표기를 맞추고, 새 계산이면 ledger 에 식, 근거가 없으면 뺀다.
- 그다음 `build/hist/check/<id>-sheet-*.jpg` 를 **Read 로 전부 눈으로 확인**: 사진이 장 내용과 맞는지, 글이 읽히는지, 어색한 줄바꿈 · 빈 곳 · 잘림이 없는지, 기승전결 흐름이 장 제목만 읽어도 이어지는지. 큰 그림은 `build/hist/check/<id>/<kk>.jpg`.
- 컨테이너 CPU 가 둘뿐이고 다른 담당도 같이 돌린다 — 전체 검사는 필요할 때만, 고치는 중에는 `--only`.

## 8. 끝나면
- `build/hist/out/<id>.notes.md`: 파트 · 장 수, 고른 레이아웃 이유(짧게), 새 사진(이름 · 출처), ledger 추가, PLAN 과 다르게 한 것, 남은 문제.
- 마지막 응답: 케이스별 `오류 0` 확인 결과 · 장 수 · 남은 문제를 짧게.
