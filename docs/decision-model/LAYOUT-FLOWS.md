## 1. 요약

- 레이아웃 흐름의 판단형 단계 네 곳에 Decision 버전을 만들었다. 노드 안에서만 바뀌고 앞뒤 입출력은 LLM 분기와 같다. Decision 키가 있고 작업이 켜져 있을 때만 바뀐다(키 없음 · `WINMATE_DECISION=off` · 레이아웃 `off`면 LLM 그대로).

| 노드 | 작업 | Decision이 하는 일 | LLM에 남는 일 | 쓴 레이아웃 |
|---|---|---|---|---|
| 문구 작성 | `layout.cells` | 정해진 보기 칸 1,100개(레이아웃 166장 설계) — ● · 등급 · 상태는 쓴 뒤에(choice · score · noul), n번째 · 복사 · 개수 · 그 장에 묶인 항목 · 모델 코드는 코드. 쓰기 전에 모델이 이름을 고르는 choice도 만들어 쟀으나 블라인드에서 졌다 → 기본 꺼짐(`pre_choice`) | 나머지 칸 작성(정해진 이름은 고정 칸으로 받음) | 105장(쓰기 전, 측정 시) · 35장(쓴 뒤) |

| 파트 검토 | `layout.review` | 장마다 다시 쓸지 · 이유(choice) — 지시는 이유와 코드가 찾은 것(반복 · 빈 칸 · 답 없는 요구)으로 | 다시 쓸 장만 다시 쓰기(`auto_sheet_redo`) | 214장 이상 |

  - **속도** — 장당 모델 시간 11.8초 → 8.4초(−29%). 검수 3.2 → 2.0초, 파트 검토 1.3 → 0.1초, 사진 1.0 → 0.1초, 작성 6.3 → 6.2초. LLM 호출 4.8 → 3.6회, Decision 호출 2.8회(회당 0.2~0.4초).
  - **성능** — 두 분기의 최종 장표를 같은 LLM 검수기로 감사(고침 없이 1회): 남은 문제 1.44 → 1.41건(샘플별 Decision 나쁨 559 · 같음 1,002 · 좋음 553). 문제 0건 장은 517 → 440으로 Decision이 적다.

## 2. 노드별 Decision 버전

공통: `app/api/poc/layout_decide.py`(앱 쪽), 사진은 composer `pictures.py`(앱을 import 하지 않고 `llm.decisions['layout.pictures'].ask(stage, state, questions)`만 씀). Decision 요청이 실패하면 그 노드는 LLM 분기로 간다(규칙 대체 없음). 실제 작업(`adapters/compose.run_auto`)은 작업에 묶인 `JobDecision`(취소 · 사용 기록), 실험실은 `layout_experiments.run(branch='auto' | 'llm')`.

### 2.1 문구 작성 — `layout.cells`

- 레이아웃마다 설계: `app/data/layout_decisions.json` — 칸 설계(`layout_cells.json`)의 역할을 읽은 설계 에이전트 8개가 400장을 나눠 맡고(지침 · 형식 검증), 1,100칸(166장)을 정했다: 이름 고르기 937(공간 276 · 제품 213 · 제품+솔루션 145 · 솔루션 136 · 보기 114 · 모델 35 · 사례 18), 점수 · 표시 159, 개수 4. 쓰기 전 915 · 쓴 뒤 185.
- 칸 명세: `pick`(목록 · `options`) · `nth`(n번째) · `of`(다른 칸 공간의 것 · 그 제품의 모델) · `multi`(‘ · ’ 나열, `max`) · `group`(서로 다르게) · `same`(복사) · `when`(pre · post) · `q`(지시) · `empty` / `dots`(점수 → ●○) / `count`(개수).
- 쓰기 전(pre): 그 장의 고정 칸(템플릿 라벨 — 카드 분류 · 열 머리)과 묶인 항목, 고른 항목 목록을 state로 → 칸마다 choice → 묶음 안에서 확신 높은 칸부터 서로 다르게 배정 → 작성기에 고정 칸으로. 한 장을 위해 만든 장(공간별 제품 · 제품 스펙 · 솔루션 · 사례)은 그 장에 묶인 항목을 코드가 그대로.
- 쓴 뒤(post): 쓴 문구를 state로 → 보기 choice · 점수 score · 표시 noul → 개수는 코드.
- 값은 칸 폭에 맞춘다(나열은 들어가는 만큼, 들어가지 않는 제품 이름은 모델 코드).

### 2.2 사실 · 요구 검수 — `layout.verify`

- state: 고객 · 파트 · 근거/요구 원문(사실 700자씩) · 최종 장표.
- 질문: `cov:R*` choice(쓴 칸 + 없음) — “수행 방법 · 조건 · 승인 요청까지 실제로 답한 칸”, `cell:s:i` choice(문제 없음 · 사실/기능 · 묶인 제품 · 자리표시 · 소제목 불일치).
- 답 → LLM 검수와 같은 `{coverage, issues, fixes}`: P(없음) < 0.95면 답한 칸 인용, 1순위가 문제이고 P(문제 없음) < 0.25면 지적 → 그 칸만 LLM이 고침(요소별 장은 요소 안에서). 두 번째 검수도 Decision.
- 보정(레이아웃 40장 × 2, 같은 장표 그림자 비교): LLM 검수기는 칸 단위 지적을 거의 하지 않는다(293칸 중 1칸 — 지적의 대부분은 ‘요구 답 없음’). 그래서 칸 지적은 확신할 때만, 요구 답변은 목차 · 사례 · 제목처럼 답할 수 없는 장만 ‘없음’이 되게 정했다. ‘같은 말 반복’ 보기는 표의 짧은 라벨을 오탐해 뺐다(반복은 작성기 · orchestrator 코드가 잡는다).

### 2.3 파트 검토 — `layout.review`

- `part_orchestrator.review_part` 안에서: 장마다 choice(문제 없음 · 지시와 다름 · 다른 장과 같음 · 요구 미답 · 검수 지적 남음 · 빈 칸) → P(문제 없음) < 0.5인 장만(최대 3) `{s, why, instruction, cells}` — 지시는 이유와 코드가 찾은 반복 칸 · 빈 칸 · 답 없는 요구로 만든다. 다시 쓰기는 LLM.

### 2.4 사진 — `layout.pictures`

- 검수: 칸마다 choice(맞음 · 다른 공간 · 다른 주인공 · 다른 업종 · 다른 제품군 · 다른 회사 간판)와 choice(대안 ≤3 · 템플릿 원래 사진 · 없음). 1순위가 어긋남이고 P(맞음) < 0.5면 어긋남(보정: LLM 검수와 같은 판정 77%).
- 고르기(LLM 고르기 방식일 때만 쓰임 — 기본은 코드 순위): 칸마다 choice(후보 ≤6 · 없음), 확신 높은 칸부터 같은 사진 없이.

### 2.5 Decision으로 바꾸지 않은 판단과 이유

| 단계 | 이유 |
|---|---|
| 파트 계획(`auto_part_plan`) | 장마다 쓸 ‘파트 지시’ 문장이 출력의 중심(생성형). 요구 · 항목 배분은 판단형이지만 지시문과 한 출력이라 나누면 작성 입력이 바뀐다 — 후속 후보 |
| 작성 · 요소별 작성 · 모으기 · 길이 맞춤 · 빠진 칸 · 고치기 · 다시 쓰기 | 문장 생성 |
| 숫자 칸(칸 설계 `num`) | 근거 수치 중 하나를 고르는 일이지만 단위 · 형식과 함께 써야 하고, 자료에 없으면 비워야 함 — 후속 후보(허용 수치 목록 choice) |
| 사진 순위 · 칸 비율 | 이미 코드(모델 호출 없음) |
| 덱 단위 레이아웃 고르기 | 이미 Decision 분기(`layout.pick` · `layout.best_pick`) |

## 3. 검증 방법

- 입력: 실험실(`app/api/poc/layout_experiments.py`)의 업종별 합성 샘플 5개 — 레이아웃의 업종(업종 이해 장은 그 업종).
- 한 쌍 = 같은 레이아웃 · 같은 샘플 · 같은 프로세스에서 LLM 분기와 Decision 분기. LLM 답은 프롬프트로 캐시해 두 분기의 같은 호출은 같은 답(Decision 분기의 작성이 바뀌면 새 호출).
- 시간: LLM은 HTTP 왕복 시간만(큐 대기 제외 — 처음 측정에 큐 대기가 섞여 다시 쟀다), Decision은 요청 시간. 캐시된 호출은 처음 쟀던 시간.
- 같은 장표 비교(그림자): LLM 분기 실행 중 같은 장표의 검수 · 사진 검수를 Decision에도 물어 답만 기록.
- 감사: 두 분기의 최종 장표를 같은 LLM 검수 프롬프트로 한 번(고침 없음) — 남은 문제 수. LLM 분기 장표는 이미 같은 검수기를 통과했으므로 LLM 쪽에 유리한 지표다.
- 블라인드: 두 분기 문구가 다른 장표를 A/B 무작위로 섞어 판정 에이전트가 고름(충실성 · 칸의 일 · 쓸모).
- 반복: 1차 블라인드 → 칸 Decision의 약점(고정 라벨을 못 봄 · 약한 ‘없음’으로 이름 칸 비움 · 칸 폭 초과 · 정한 이름을 다른 칸에 되풀이) 수정 → 칸 설계 레이아웃 다시 돌림(2회).

### 4.3 블라인드 판정

- 1차(칸 수정 전, 모든 종류 60장): Decision 30 · LLM 27 · 비김 3.
  - Decision이 낫다: 근거 없는 KPI · 치수 · 지어낸 고객 현장을 고치기로 걸러 냄, 고른 이름을 제 칸에, 행 상태와 개수가 맞음.
  - LLM이 낫다: 쓰기 전에 고른 이름이 카드 분류와 어긋남(옥외 칸에 실내 제품), 고른 항목이 남았는데 이름 칸이 빔 — 둘 다 고쳤다(고정 라벨을 state에, ‘없음’은 확신 0.6 이상일 때만).
- 2차(칸 수정 뒤, 칸 Decision이 있는 레이아웃만 45장): Decision 18 · LLM 27.
  - Decision이 낫다: 표 모양 장 — BOM · 스펙 · 활용 맵 · 여정의 열 머리와 행이 고른 항목과 맞음(LLM은 고르지 않은 제품 · 중복 열 · 지어낸 사양), 행 상태와 개수가 맞음.
  - LLM이 낫다: 서술 카드 — 공간 카드 · 제품 태그 · 여정 단계에서 쓰기 전에 고른 이름과 작성기가 쓴 설명이 어긋남(JBL 카드에 LED 설명, 연회장 장이 키오스크로), 이름 칸이 빔, 시리즈 코드('IFR')가 이름 자리에.
  - 결정: 쓰기 전 이름 choice는 기본 꺼짐(`layout_decisions.json`의 `pre_choice: false` — 그 칸은 LLM 분기처럼 작성기가 씀). 코드가 정하는 이름(n번째 · 그 장의 항목 · 복사 · 모델)과 쓴 뒤 판정(보기 · 점수 · 개수)은 Decision. 모델 코드로 줄이기는 숫자가 든 모델명만. 크레딧 소진(아래 5.2)으로 이 설정의 재측정은 하지 못했다 — 꺼진 칸은 LLM 분기와 같은 경로라 그 부분은 LLM 분기와 같다.

## 5. 반영 · 남은 일

### 5.1 반영 상태

- 운영 서버에 반영하지 않았다. 반영하면 Decision 키가 있고 `WINMATE_DECISION=auto`이므로 네 작업이 켜진다. 끄려면 `WINMATE_DECISION_TASKS`(작업 목록) 또는 `WINMATE_DECISION=off`, 레이아웃 하나만은 `layout_decisions.json`의 `off`.
- admin 레이아웃 관리 흐름도: Decision 분기가 있는 노드에 ‘D’ 칩, 단계 팝업의 ‘Decision 분기’에 질문 형식 · 지시 · 보기 · 사용 여부.

### 5.2 남은 일

- **OpenRouter 크레딧**: 이번 검증(LLM 호출 약 3만 회)으로 계정 크레딧 $25 중 $24.05를 썼다(오늘 $17.18). 남은 약 $0.95로는 운영 앱의 LLM 호출도 곧 실패한다(HTTP 402) — 충전이 필요하다. 마지막 재측정 179건이 402로 실패해 그 레이아웃 · 샘플은 직전 측정값을 썼다.
