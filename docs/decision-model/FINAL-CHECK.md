# 최종 점검 · ReAct — 모든 레이아웃 흐름의 마지막 단계

- 작성일: 2026-11-18
- 요청: “각 레이아웃 흐름은 ReAct 방식으로 돌아야 해(하나 이상). 모든 흐름의 마지막 단계에서 반드시 제품 · 솔루션 · 이미지 등 부적절한 매칭 · 중복이 없는지, PPT 레이아웃의 기존 콘텐츠 대비 적절한 내용이 들어갔는지 — 내용이 비슷한지가 아니라 레이아웃 측면의 적절성 — 를 본다. 이 적절성 판단에도 Decision 분기를 쓴다.”
- 코드: `app/api/poc/layout_final.py` · 흐름 모듈 `final`(`app/api/layout_flows.py`) · 훅 `app/api/poc/layout_flows.install` · Decision 작업 `layout.final`
- 레이아웃별 기록: `layouts/<레이아웃>.md`의 「최종 점검 · ReAct」 절 · 원자료 `results/final-check.json`

## 1. 무엇이 바뀌었나

- **모든 흐름이 `최종 점검`으로 끝난다.** 흐름 모듈 `final`(순서 11, `lock` 다음)은 고정 단계라 지울 수 없고, 저장된 흐름에도 다시 들어간다(`normalize`). admin 흐름도에서 이 단계와 사용자 정의 단계에 ‘ReAct’ 칩이 붙는다. 흐름 등록부에 있는 357장은 모두 `… → lock → final`. 등록부 밖의 구성 전용 장 111장(DSS · 고객사의 이해)도 합성할 때 같은 점검을 거친다. 점검은 흐름 등록 여부가 아니라 파트의 마지막 단계(`enforce_linked`)에 걸려 있다.
- **ReAct 고리**: 관찰 → 판단 → 고침 → 다시 관찰, 최대 3회.
  - 관찰(코드, 늘): 다 쓴 장을 칸 · 카드(요소) · 사진으로 읽고 문제를 찾는다(2장).
  - 판단:
    - Decision 분기(`layout.final`): 쓴 칸마다 Decision 모델이 이 칸의 일을 하고 같은 카드의 항목을 말하는지 판단한다(choice). 걸린 칸만 LLM이 다시 쓴다(`auto_final_fix`). 걸린 칸이 없으면 LLM을 부르지 않는다.
    - LLM 분기(Decision이 없거나 꺼졌을 때): 모델이 장 전체와 관찰을 읽는다(`auto_final_check`). 도구를 부르고 그 결과를 본 뒤 고친다. 도구는 item(고른 항목 자료) · image(사진 칸 대안) · template(그 칸의 원래 레이아웃 내용 · 형식)이다.
  - 고침: AI 칸만, 칸 폭 안에서. 잠금 칸 · 고정 장 · 코드가 정한 칸은 건드리지 않는다. 고르지 않은 항목 이름을 들이는 고침은 버린다. 같은 사진은 숨긴다. 카드와 다른 제품 사진은 카드 제품의 컷으로 바꾼다(코드).
  - 다시 관찰: 판단이 거절한 문제(칸을 그대로 둠)는 다시 묻지 않는다. 고친 것이 없거나 새 문제가 없으면 끝낸다.
- **결과가 남는 곳**:
  - 장의 `final_check`(전 과정 trace)
  - 레이아웃 출력 `final`(상태 · 회차 · 바꾼 수 · 남은 것 · 단계 요약)
  - 장 trace의 `final` 노드 상태: clean · fixed · remaining · fixed_remaining
  - 실험실 결과 `final`
  - 남은 문제는 장의 검토 항목(‘최종 점검 · …’)으로 들어가고 상태가 review가 된다. 점검이 고친 문구는 ‘검수 후 변경’으로 보지 않는다(textKey 갱신).

## 2. 무엇을 보나 — 레이아웃 측면의 적절성

내용이 원래 레이아웃 문구와 비슷한지는 보지 않는다. 원래 내용은 다른 고객의 것이다. 칸마다 원래 레이아웃이 그 자리에 둔 내용의 **형식**과 칸의 **일**(칸 설계 역할)을 기준으로 본다.

| 관찰 | 기준 |
|---|---|
| 고르지 않은 이름 | 고객이 고르지 않은 제품 · 솔루션 · 브랜드 이름. 예외는 `enforce_linked`와 같다: 사례 장, 시장 근거 칸, 고른 솔루션 장의 원래 문구, 덱에 나온 사례 · 고른 솔루션의 다른 이름. |
| 카드 매칭 | 항목 카드(요소 단위 product · solution · case)의 이름 칸이 말하는 항목과 다음이 다를 때: 같은 카드의 설명이 말하는 같은 종류의 다른 항목, 또는 카드 사진의 제품 · 솔루션. 제품 카드가 그 제품이 돌리는 솔루션을 말하는 것은 정상. |
| 중복 | 두 칸에 같은 문장, 형제 이름 칸에 같은 항목 이름, 장 안에 같은 사진(사진 정체성 기준). 레이아웃 원래 내용이 되풀이하는 칸 · 사진은 예외. |
| 형식 | 원래 내용의 형식(빈칸 · 기호 · 코드 · 숫자 · 목록 · 문장 · 라벨 · 구)을 기준으로 다음을 잡는다. 숫자 칸에 숫자가 없는 글('—'는 ‘값 없음’으로 정상, 역할이 ‘없으면 …’이면 예외). 짧은 라벨 칸에 긴 문장. 문장 칸에 낱말 하나. 기호 칸에 다른 형식. 내용이 있는 칸이 빔(역할이 ‘없으면 빈칸’이면 예외). 칸 폭을 넘음(허용 폭은 칸 예산과 원래 내용 길이 중 큰 쪽). 모델 코드(OH55C 등)는 숫자가 아니라 이름이다. |

## 3. Decision 버전 (`layout.final`)

| 형식 | 질문 | 보기 | 걸리는 기준 |
|---|---|---|---|
| choice | 쓴 칸마다 — 이 칸의 일을 하고 같은 카드의 항목을 말하는가 | 맞음 · 이 칸의 일이 아님 · 다른 항목 | ‘이 칸의 일이 아님’ p ≥ 0.8 · ‘다른 항목’ p ≥ 0.6 |

- state: 고객 · 고른 제품/솔루션(덱이 쓰는 이름) · 공간 · 장 이름 · 말할 것 · 칸마다(일 · 원래 내용 · 형식 · 지금 값 · 카드) · 사진(보이는 것 · 카드) · 코드가 찾은 것
- 다음은 Decision에 묻지 않는다:
  - 형식 · 중복 · 고르지 않은 이름 · 사진 — 처음에는 Decision에도 같은 기준(형식 · 중복 · 고르지 않은 이름 · 사진)을 물었다. 레이아웃 원래 내용(맞는 장)에서 Decision은 장당 1.95건을 잘못 걸었고 코드는 0.03건이었다.
  - 사진 맞음 — 원래 사진 181장을 ‘다른 항목’이라 했다.
  - 그래서 Decision은 코드가 못 보는 의미 판단만 맡는다.
- 기준값은 같은 날 앞선 탐지 측정(아래 4.1과 같은 방법)에서 정했다. 둘 다 0.6이면 코드가 놓친 오류를 42건 잡지만, 맞는 장마다 0.18건을 잘못 건다(한 건마다 작성기 호출 한 번). ‘일 아님’ 0.8 · ‘다른 항목’ 0.6이면 37건을 잡고 잘못 거는 것은 0.07건이다.

## 4. 검증

OpenRouter 크레딧이 거의 없어(계정 $25 중 $24.07 사용, 남은 $0.93 — 운영 앱과 같은 키) LLM 호출 없이 검증했다. 코드 관찰 · Decision 모델(별도 과금) · 고리 동작만 쟀고, LLM이 실제로 고쳐 쓰는 문구의 질은 재지 않았다(크레딧 충전 뒤 과제).

방법:
- 「사용 중」 레이아웃 468장마다 그 레이아웃의 원래 내용을 다 쓴 장으로 놓았다. 원래 내용은 그 자리에 맞는 내용이라 ‘맞는 장’으로 본다. 그 안의 고른 항목은 원래 내용이 말하는 항목이다.
- 오류를 한 번에 하나씩 넣고, 최종 점검이 찾는지 · 고치는지를 쟀다.
- AI가 쓰는 칸이 없는 69장(통째 고정 · 정적 장)은 코드 관찰(사진)만 하므로 빼고 399장을 쟀다.
- 도구: `admin/runtime/layout-final/bench.py`(run · report · `--loop` · `--no-decision`) · `doc.py`(레이아웃별 기록 · `results/final-check.json`).

### 4.2 고치기 (관찰 → 판단 → 고침 → 다시 관찰)

같은 장들에서 최종 점검 단계 전체를 돌렸다. 작성기 자리에는 ‘완벽한 작성기’를 두었다. 걸린 칸을 받으면 그 칸의 맞는 내용(레이아웃 원래 내용)을 돌려주는 대역이다. 그래서 이 측정은 문구의 질이 아니라 다음을 잰다: 고리가 무엇을 누구에게 묻는지, 고침 적용 규칙, 다시 관찰, 멈춤.

고침은 엄격하게 셌다. 넣은 오류가 바꾼 칸 · 사진이 모두 맞는 내용으로 돌아왔거나(사진은 숨김도 인정) 해야 고친 것이다. ‘더 나빠짐’은 오류와 상관없는 칸 · 사진이 맞는 내용에서 바뀐 수다.

Decision 분기(`layout.final`, 기본):
- 맞는 장 399장: LLM 호출 장당 0.07회(LLM을 부르지 않은 장 371 / 399 = 93%), 바뀐 칸 0, 1회차에서 끝, 단계 시간 중앙값 237ms.

  - 찾았지만 그대로 남음 14건. 대역 작성기가 돌려준 맞는 내용이 레이아웃의 안내 문구 그 자체였다(‘핵심 제안 제목’ · ‘○ 확인 필요’ · ‘단계 3’ 등). 그래서 기존 칸 규칙(`unusable`: 견본 · 안내 문구가 남음)이 거절했다. 실제 작성기는 새 문구를 쓰므로 대역의 한계다.
  - 고쳤지만 원래 카드로 돌아오지 않음 14건. 모두 두 카드 이름 맞바꿈이다. 코드가 카드 사진을 이름 쪽 항목의 제품 컷으로 바꿔 카드는 일관되게 되었지만, 원래 배치로 되돌리지는 않았다.

LLM 분기(Decision이 없거나 꺼졌을 때). 작성기와 판단 자리에 같은 대역을 두었다. 대역은 코드 관찰이 걸어 준 칸만 맞는 내용으로 돌려준다 — 실제 모델이 장을 읽고 하는 의미 판단은 대역이 할 수 없다.
- 맞는 장 399장: LLM 호출 장당 1.00회(모든 장을 한 번은 읽는다), 바뀐 칸 0.
- 넣은 오류 1,700건: 고침 1,544건(90.8%), 더 나빠짐 0건. 오류 한 건에 LLM 호출 1회.
- 두 카드 이름 맞바꿈은 11 / 122 — 이 오류를 잡는 것은 Decision(또는 실제 모델의 읽기)이다.
- 실제 모델이 이 분기에서 얼마나 더 찾고 고치는지는 크레딧 충전 뒤 잴 일이다.

## 5. 반영 · 남은 일

- 운영 서버에는 아직 반영하지 않았다. 반영하려면 다음 둘이 필요하다:
  - 서버 재시작(`make restart`)
  - admin 화면 빌드(`node admin/build.mjs`)
- 반영하면 Decision 키가 있고 `WINMATE_DECISION=auto`라 `layout.final`이 켜진다(Decision 분기).
- 끄는 방법:
  - Decision 분기만 끄기: `WINMATE_DECISION_TASKS`에서 `layout.final`을 빼거나, `layout_decisions.json`에서 그 레이아웃을 `off`로. 그러면 LLM 분기로 돈다.
  - 단계 자체: 끌 수 없다(모든 흐름의 고정 단계).
- 비용:
  - Decision 분기 — 장마다 Decision 1회(약 0.3초)를 쓴다. LLM은 걸린 칸이 있을 때만 1회 부른다(맞는 장 기준 7%).
  - LLM 분기 — 장마다 LLM 1회 이상이다.
- 남은 일:
  - 크레딧 충전 뒤 실제 모델로 두 분기의 고친 문구 질을 잰다(블라인드 판정 포함).
  - 두 카드 이름 맞바꿈처럼 설명이 항목 이름을 말하지 않는 카드 어긋남은 44%만 찾는다.
  - 흐름 등록부 밖의 구성 전용 111장(`flow_for` KeyError — 원래부터)은 admin 흐름도에 나오지 않는다. 합성할 때는 점검을 거친다.
