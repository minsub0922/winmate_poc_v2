# Winmate v2 이전 — 확인 사항

조사 기준은 2026-10-19에 공식 Export ZIP으로 확보한 `reference/live/`다. 아래 항목을 추측으로 구현하지 않았다. 질문은 0단계 검토 시 한 번에 확인한다.

## Q01. DB 교체 가로 카드가 포함된 기준 버전

**확인 사실:** 다운로드한 최신 실행 스크립트와 현재 라이브 runtime 스크립트 해시가 같다. 그 스크립트·CSS에는 `wmDbFind`, `wmAlts`, `wmRail`, `wmSwapDb`, `.wm-rl*`, `.wm-db-*`가 없다. 로컬에도 `dbswap-patch.py`를 발견하지 못했다. 실제 제품 3개 레이아웃에서 QM55C를 선택하면 ‘제품 바꾸기’ 전체 탐색기 모달이 열린다.

**질문:** 이 게시본의 기존 교체 모달을 1단계 기준으로 확정할까, 가로 카드 패치가 포함된 다른 게시본/파일을 먼저 기준으로 받아야 할까?

**영향:** 후자라면 새 게시본을 별도로 보관하고 차이를 다시 조사해야 한다. 원래 목표가 가로 카드라면 현재 모달만 옮기고 동일 재현 완료라고 보고할 수 없다.

근거: `evidence/screens/live-layout-unit.*`, `live-product-swap.*`, `semantic-change-hunks.json`.

## Q02. media 인덱스와 게시 이미지 묶음 불일치

**확인 사실:** 게시된 이미지 JSON bytes는 로컬과 같으나 라이브 번들의 media 메타데이터와 소스 `data/media.json`은 257개 값이 다르다. 라이브 인덱스는 `g0` 범위 15개, `t` 범위 228개가 실제 JSON 문자열 경계와 맞지 않는다. 소스 인덱스는 전부 맞는다. 실제 라이브에서 `범위가 맞지 않아요: img/media/t.json` 경고도 나왔다.

**질문:** `reference/live`는 그대로 보존하고 **새 앱의 media 메타데이터만 검증된 소스 값으로 교정**하는 것을 1단계 예외로 허용할까, 실패 상태까지 라이브대로 유지할까?

**제안:** 원본 기준 파일은 불변으로 두고, 교정은 사용자가 허용한 별도 차이로 기록한다. 사진 설명·순서도 함께 바뀌므로 단순 콘솔 정리와 동일하게 취급하면 안 된다. 재게시한 정상 번들이 있다면 그것을 새 기준으로 받는 방법도 있다.

원인을 만든 과거 게시 작업은 확인되지 않았다. 단순히 잘못된 URL로 추정해서 경로를 고치지 않았다.

근거: `media-data-differences.json`, `source-media-range-check.json`, `live-media-range-check.json`, `live-app-console.json`.

## Q03. 기존 브라우저 사용자 데이터의 실제 이관 범위

**확인 사실:** 현재 proposal/My/review/sim/fav 저장 형식은 확보했다. 하지만 Claude iframe origin과 `127.0.0.1:포트`는 다른 저장소를 쓴다. 같은 DB 이름·키를 써도 기존 브라우저 데이터가 자동으로 보이지 않는다. IndexedDB의 Blob 이미지를 빼면 My 템플릿도 완전히 복원되지 않는다.

**질문:** 1단계는 기존 키·형식 호환까지로 할까, 아니면 기존 Claude origin의 제안서·My·검토·시뮬레이션·찜을 내보내고 로컬로 가져오는 별도 이관 절차도 포함할까?

**제안:** 후자를 선택하면 주 UI 디자인을 바꾸지 않는 별도 이관 도구로 다룬다. 인증·키·Claude 계정 정보는 이관 대상이 아니다. 이번 0단계에서는 개인 저장소 값을 추출하거나 원격 전송하지 않았다.

## Q04. PoC 데이터 시점의 차이 — 2단계 설계 시 확정

Layout Agent snapshot은 전체 레이아웃 820, 제품 40, 시나리오 21이고 현재 앱은 835/1,068/22다. PoC의 `sync_source.py`는 원본 PoC 디렉터리에 쓴다. 요청한 읽기 전용 원칙 때문에 실행하지 않았다.

새 `app/data` 쪽으로 동일 형식 사본을 만들고 KB 어댑터에서 주입하는 것이 기본 제안이다. 기존 검증 결과가 그대로 적용된다고 주장하지 않으며, 새로운 데이터에서의 회귀 결과를 별도로 보고해야 한다. **모듈 버그로 확인된 것은 없고**, 원본 PoC 코드를 바꿀 필요가 생기면 별도 보고한다.

## Q05. 기준 고정 이후의 라이브 변경

조사 중 아티팩트 셸과 일부 파일이 갱신되는 정황이 있어 다운로드 시점과 runtime 해시를 보관했다. 1단계는 이번 고정 스냅샷을 기준으로 진행하고, 이후 라이브 수정은 새 버전 차이로 받는 것을 제안한다. Q01/Q02에서 새 게시본이 제공되면 해당 버전으로 기준을 다시 고정한다.

## Q06. 조사 중 폴더에 추가된 제품 이미지 라이브러리

17:10 이후 검사에서 원본 **14개 수정, 4개 누락, 1,778개 추가**를 감지했다. 새 `src/imglib.js`와 이미지 5,088개 인덱스, picker·제품 갤러리 확장, SQLite image/FTS 테이블, 제품 pack 병합이다. 이 작업의 쓰기는 `.gitignore`, `docs/migration`, `reference`에 한정되어 있고 원본 변경은 되돌리지 않았다. 초기·말미 소스 사본을 각각 보관·빌드했다.

**확인 사실:** 현재 라이브 runtime JS는 처음 받은 export와 같고 이 새 이미지 라이브러리는 포함하지 않는다. 현재 폴더 소스로 새로 빌드한 번들은 라이브와 또 달라진다. 정확한 변경 주체는 확인하지 않았다.

**질문:** 라이브 우선 원칙에 따라 이 추가 기능은 1단계에서 제외하고 초기 고정 소스를 쓸까, 다른 작업의 게시·정리가 끝난 새 라이브를 기준으로 다시 고정할까?

**제안:** 기존 기준을 유지하면 새 기능을 실수로 이전본에 섞지 않는다. 새 기능이 필요한 경우 원본 작업을 멈추거나 되돌리지 말고 게시본을 새로 받아 별도 차이로 다룬다. 다음 단계에서 작업할 때도 원본 편집과 동시에 최신성을 쫓지 않도록 기준 시점을 확정한다.

## 해소한 조사 질문

- 이미지 파일 해시 차이 408개: decoded pixels 모두 동일. 시각적 내용 차이로 분류하지 않는다.
- RFP `KeyError:'file'`: Python 3.9에서만 재현. 격리된 Python 3.12.13에서 원본 테스트 25 passed/3 skipped. 1단계 Python 기준을 3.12로 두는 것으로 해소 가능하다. 원본 코드는 변경하지 않았다.
- 소스의 예전 화면 정의: `SufficiencyModal`, `ContextCards`는 현재 호출처가 없다. `ScenarioDetail`은 시뮬레이션에서 여전히 호출하므로 실제 화면 목록에 남겼다.
- 붙여넣은 `_blob` 경로: 확보한 라이브 앱 번들에서 `/_blob/` 0회. 관련 레거시 이미지 매핑은 남아 있어 이 모듈을 지우면 안 된다.

## 이전 작업에 적용한 진행 기준 (2026-10-19)

사용자의 ‘시작해’ 이후 사전에 안내한 기본안을 적용했다. Q01/Q05/Q06은 확보한 라이브 snapshot으로 고정하고 폴더의 후속 변경을 섞지 않았다. Q02는 reference를 불변으로 보존하면서 앱만 정상 media 인덱스로 교정한 예외로 기록했다. Q03은 같은 저장 형식과 별도 백업/가져오기 도구까지 구현했으며 개인 원격 저장소를 직접 추출하지 않았다. Q04는 앱 쪽 정본 KB(835/1,068/22)를 만들어 명시적으로 주입했고 원본 PoC는 수정하지 않았다.

남은 선택은 새 라이브 버전 수용, 자동 추천 제품 범위 확대, My의 서버 RAG, 작업 체크포인트의 디스크 저장, 인터넷/다중 사용자 배포다. 현재 고정 기준 이전과 로컬 실행을 막는 미확인 차이는 없다. 원본 PoC의 확인된 한계·장수 목표 초과 동작은 02 보고서에 남겼다.
