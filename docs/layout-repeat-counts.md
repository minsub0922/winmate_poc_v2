# 레이아웃별 반복 항목 개수 수정

편집 UI는 이후 [프롬프트 편집](layout-prompt-editing.md)으로 전환했다. 아래 개수 분석·저장 계약은 그대로 사용하며, 숫자 입력·영역 선택·비교 팝업 대신 에이전트의 계획과 승인·취소로 진행한다.

2026-10-20. 개요의 ‘사진 카드 6’이 3개로 표시되던 문제를 수정했다.

원인은 `meta.pc || 3`을 입력 초기값으로 사용하던 코드였다. `pc`는 제품 칸 수이므로 개요·사진·사례 카드에서는 0이 정상이다. 또한 편집 DOM이 만들어지기 전에 초기값을 잡고 이후 실제 구조를 반영하지 않았다.

## 동작

- 현재 장의 실제 논리 항목을 세고 **사진 카드 현재 6개**처럼 유형과 현재 수를 표시한다. 사용자가 입력하는 **변경할 개수**와 구분한다.
- 제품 3개에 설치 사진·제품 컷이 각각 있어도 6개 제품으로 세지 않는다. 사진 모자이크의 큰 타일도 한 항목이며, 별도 히어로 사진은 반복 카드와 구분한다.
- 카드 틀·사진·문구가 서로 다른 형제로 그려진 템플릿은 실제 칸 ID로 논리 항목을 연결한다. `layout-repeats.js`의 정의는 고정 count 숫자가 아니라 항목별 실제 슬롯 묶음이다. 현재 DOM에 남은 묶음 수를 센다.
- 데이터 카드/처리 단계처럼 반복 영역이 여러 개면 변경할 영역을 선택한다. 현재 항목 목록도 펼쳐 확인할 수 있다.
- 구조가 확실하지 않으면 임의로 3을 넣지 않는다. **AI로 반복 영역 확인**에서 실제 모델 분석으로 대상을 확인한 후 변경한다. 반복 대상이 없는 표지는 없음을 표시한다.
- 적용·undo·redo·수동 삭제/숨김·재접속 시 개수를 다시 읽는다. 편집 도중 숫자만 입력했을 때는 이름 수정이나 화면 배율 변경 때문에 입력값을 되돌리지 않는다.
- My에는 `repeat: {count, unit, label}`을 별도 저장한다. 사진 카드의 `pc`는 계속 0이다. 개수가 바뀌면 별도 My로 저장하고 원래 My와 이전 칸 번호를 유지한다. 수동 변경에 과거 AI 평가 점수를 재사용하지 않는다.
- 모델도 사용자가 고른 영역의 실제 수·단위·사진/문구 칸을 사용한다. 다른 영역이나 제품 수를 대신 세지 못하도록 검증한다. 개요/사진 카드의 추가 칸은 제목·설명·페이지 등 원래 구조를 이어가며 모델명 입력 칸으로 바꾸지 않는다.

변경 가능 개수는 1~16개다. 모든 내용 밀도에서 그 수가 항상 들어간다는 뜻은 아니며, 실제 글자·영역·사진 크롭 검사를 통과한 개선안만 제공한다. 원본 수가 범위 밖이면 현재 수는 그대로 보여주고 변경 수는 사용자가 정하도록 비워둔다.

## 조사와 검증

현재 등록 원본 835개와 숨긴 업종 표지 17개, 총 852개를 실제 DOM으로 조사했다. 원본 HTML을 변경하지 않는지도 확인했다.

| 범위 | 자동 구조/항목 정의 확인 | 추가 AI 확인 대상 | 반복 대상 없음 |
|---|---:|---:|---:|
| 전체 852개 | 779 | 48 | 25 |
| 활성 라이브러리 594개 | 550 | 36 | 8 |

숫자가 붙은 이름을 그대로 count로 쓰지 않는다. 이미 검출된 실제 후보를 구분하는 힌트로만 사용하며, 대응하는 구조가 없으면 추가 확인 대상으로 처리한다. 복합형에 단일한 반복 개수가 있다고 가정하지 않는다. 조사 원본은 `app/tests/output/layout-counts/catalog-audit.json`에 기록했다.

24개 대표 레이아웃의 의미상 개수를 명시적으로 검사했다. 예:

| 레이아웃 | 실제 변경 단위 |
|---|---|
| 목차 · 사진 카드 6 (`L_AIS_02`) | 사진 카드 6 |
| 전제 조건 · 현장 사진 카드 (`L_PH_OV_I`) | 사진 카드 6 |
| 제품 3 · 컷 + 설치 장면 (`L_PH_P3_A`) | 제품 3 (사진/컷 6장과 구분) |
| 공간 · 설치 중심 (`L_P3B`) | 제품 3 (공용 공간 사진과 구분) |
| 공간 사진 격자 (`L_PH_OV_F`) | 사진 카드 5 (큰 타일 1개 포함) |
| 과제 4행 표 (`L_PH_CH_I`) | 과제 행 4 (셀 8개와 구분) |
| 장면→화면→결과 (`L_PH_SO_B`) | 시나리오 행 3 (사진 6장과 구분) |
| 고객 분석 마케팅 (`L_PH_AIS_25`) | 데이터 카드 4 / 처리 단계 3 선택 |
| 서비스 카드 2×2 (`L_AIS_27`) | 서비스 카드 4 |
| 네 공간 · 솔루션 2개 (`L_VC_42`) | 공간 4 |
| 업무 공간 제품 카드 (`L_SOL_08`) | 제품 4 (검색 메타 pc=0과 구분) |

실제 편집 UI에서는 다음을 검증했다.

- 개요 레이아웃에 잘못된 pc=3이 있어도 사진 카드 6개로 표시.
- 제품/사진 카드/지표/데이터 카드의 명칭·개수, 복수 반복 영역 선택.
- 가져온 My 페이지의 첫 행이 y=70에 있어도 누락하지 않고 4개로 집계.
- 개수를 4로 입력한 뒤 이름 수정·배율 변경에도 4 유지.
- My의 낡은 count=999를 무시하고 실제 6개 표시, 숨김 5→표시 6→삭제 5 갱신.
- 수동 변경한 사진 카드 5개를 pc=0/반복 수=5로 새 My 저장, 이전 My 불변.
- 미확인 구조/API 오류에서는 숫자를 추정하거나 개선안으로 성공 처리하지 않고 원본 유지.

실제 Gemini API로 ‘사진 카드 6→4’, ‘개요 전제 카드 6→4’, ‘사례 카드 6→8’, 기존 제품 3→4를 확인했다. 초기 실패 기록도 남겼으며, 파노라마 원본의 가시 비율·문구 높이에 맞는 배치를 보완했다. 실제 UI에서 사진 카드 6→4의 비교/적용/undo6/redo4/My 저장(pc0·repeat4)/reload4/수동 삭제3/별도 My 저장(repeat3)을 통과했다. 성공 응답을 가짜로 주입하지 않았다. 기존 편집 회귀 검사와 프런트 빌드도 통과했다.

원본 catalog/슬롯 의미는 바꾸지 않았다. 개인 My의 새 구조에만 새 f와 반복 메타를 부여한다. 고정 카탈로그 항목 수 및 Agent KB의 제품 pc 계약은 그대로다.

## 재현과 산출물

```sh
node app/tests/layout-repeat-counts.mjs --ui
# 아래는 실제 API를 호출한다.
WINMATE_REFLOW_OUTPUT=app/tests/output/layout-counts/live-final node app/tests/layout-reflow.mjs L_AIS_02:4 L_PH_OV_I:4 L_CL_D:8
WINMATE_REFLOW_OUTPUT=app/tests/output/layout-counts/ui-live node app/tests/layout-reflow.mjs --photo-ui
node app/tests/layout-editor.mjs
npm --prefix app/web run build
```

- `app/tests/output/layout-counts/ui-live/photo-ui-comparison.png`: 실제 사진 카드 6→4 비교 화면.
- `app/tests/output/layout-counts/ui-live/photo-ui-save.json`: 실제 적용/저장/복원/별도 My 메타.
- `app/tests/output/layout-counts/live-final/`: 실제 모델 설계·DOM 검사·1280×720 PNG.
- `app/tests/output/layout-counts/catalog-audit.json`: 전체 원본별 대상·현재 수·칸 ID.
- `app/tests/output/layout-counts/verification.json`: 최종 집계.
