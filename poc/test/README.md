# RFP → 고객 요구사항 정리 실험 (poc/test)

Winmate 히스토리에 넣은 금융권 RFP 4건을 테스트 케이스(TC)로 삼아, **RFP 원문이 들어왔을 때 LLM이 요구사항을 빠짐없이 · 원문 그대로 · 사업별로 정리하는지**를 실험합니다. 긴 문서는 조각(chunk)으로 나누되 조각 사이에 맥락을 이어 붙여 정리합니다.

## 사용하는 키 (`poc/.env.example` 기준)

| 키 | 쓰는 곳 |
|---|---|
| `GEMINI_API_KEY` · `GEMINI_MODEL` | 추출 · 통합 LLM (기본 `gemini-3.1-flash-lite`, REST `generateContent` + JSON 응답 스키마) |
| `TAVILY_API_KEY` | 선택(`--enrich`): 요구사항에 나온 인증 · 법 조항(WHQL, TPM 2.0, 국가계약법 시행령 제27조 등)의 출처 수집. 요구사항 본문에는 섞지 않고 따로 저장 |

Gemini 주소를 직접 못 쓰는 환경(사내 게이트웨이 · 프록시)이라면 `.env` 에 `GEMINI_BASE_URL=<.../v1beta 에 해당하는 주소>` 를 더하면 그 경로로 호출합니다.
`.env` 값은 코드가 직접 읽고 출력하지 않습니다. 표준 라이브러리만 써서 `pip install` 없이 돌아갑니다(Python 3.9+).

## 파이프라인 (`rfp_pipeline.py`)

```
원문 ─▶ 0 chunk ─▶ 1 profile ─▶ 2 extract(조각마다, 맥락 이월) ─▶ 2b gap fill ─▶ 3 consolidate(ID 기반) ─▶ 4 guard ─▶ Winmate 입력 폼
```

1. **구조 인식 분할** — 제목 경로(예: `Ⅳ. 사업자 선정 > 3. 입찰조건 상세내용`)를 유지하고 제목 경계에서 우선 자릅니다. 표는 행 단위로만 자르고, 표 중간에서 시작하는 조각에는 **표 머리행을 다시 붙입니다**. 모든 줄은 정확히 한 조각에 들어갑니다(테스트로 확인).
2. **profile(전역 맥락)** — 원문 전체가 아니라 *문서 지도*(제목 줄 + 첫 줄 + 연락처 줄, 6천 자 이내)로 사업 목록 · 고객 · 담당 부서 · 시작 줄을 먼저 잡습니다. 한 파일에 RFP가 여러 건 묶여 있어도 사업별로 나눕니다.
3. **extract(맥락 이월)** — 조각을 순서대로 읽을 때마다 다음을 함께 넣습니다.
   - 전역 맥락: 사업 목록 · 담당 부서
   - 지금 위치: 조각 번호 · 제목 경로 · 어느 사업 문서인지
   - **원장(ledger)**: 지금까지 뽑은 항목의 ID · 분류 · 요약(예산 2,600자, 최근 항목 우선) → 중복을 만들지 않고, 같은 항목에 세부가 이어지면 `updates`로 덧붙임
   - **이월 메모(carry)**: 직전 조각이 남긴 1~3문장(예: "표 (3) 노트북 상세 스펙이 이어짐")
   - **미해결 참조**: "붙임 3 참조" 같은 항목 → 붙임이 나오는 조각에서 해소
   - 각 항목은 원자 단위(한 항목에 한 조건) · 숫자 원문 그대로 · 강도(필수/불가/이상/이하/할 수 있음) 유지 · **근거 인용(quote)** 필수
   - v2 규칙: 제출서류 목록 · 제출처 메일 주소 · 표의 수량/비고 열 · 법 조항 번호 · 들여쓴 하위 항목을 빠짐없이(실험에서 반복해 빠지던 다섯 유형)
3b. **gap fill(갭 채우기)** — 조각을 뽑은 뒤, 요구사항처럼 보이는데(숫자 · 필수 · 불가 · 제출 · 까지 …) 어떤 항목에도 반영되지 않은 원문 줄만 골라 다시 묻습니다. 글자가 대부분 반영됐어도 그 줄의 두 자리 이상 숫자가 항목에 없으면 일부만 옮겨진 줄로 봅니다(예: 표의 예상수량 500).
4. **consolidate(ID 기반)** — 통합 단계에는 원문을 주지 않고 원장 ID만으로 키맨 배정 · 중복 병합 · 요약 · 평가 구조 · 확인 필요를 정하게 합니다. 요구사항 본문은 원장에서 그대로 조립하므로 이 단계에서 내용이 빠지거나 바뀌지 않습니다. 병합은 *버리는 항목의 숫자가 남기는 항목에 모두 있고 글이 충분히 비슷할 때만* 적용하고, 배정되지 않은 항목은 '미배정' 키맨으로 보존합니다. 읽기 좋게 주제가 같은 항목은 2~6개, 남은 항목은 같은 분류 4개씩 한 줄로 이어 붙입니다(원장 문장 그대로). 사람용 글에 남은 id 는 항목 내용으로 바꾸고, 통합 호출이 실패하면 규칙 기반 배정으로 대체해 폼을 잃지 않습니다.
   - 작은 모델의 반복 폭주(JSON 한 칸에서 같은 문장을 끝없이 되풀이)를 막으려고 단계별 출력 상한 · 폭주 감지 · 온도를 올린 재시도(0.1→0.6→0.9)를 둡니다.
5. **guard** — 근거 인용 대조(grounded), 출력 숫자의 원문 존재 확인(unsupported numbers), 중복 근사 검사.

## 실험 조건

| 조건 | 설명 |
|---|---|
| `single` | 문서 전체를 한 번에 추출(조각 없음) |
| `chunk_nocarry` | 조각을 독립적으로 추출 — 원장 · 이월 메모 · 사업 목록 없이, 사업 귀속은 위치 기준 |
| `chunk_carry` | 위 맥락 이월 전부 |
| `chunk_carry_gap` | **권장** — 맥락 이월 + 갭 채우기 |

`--max-chars` 로 조각 크기를 바꿔(예: 1500 · 3000) 길이에 따른 맥락 유지를 비교할 수 있습니다.

## 테스트 케이스 (`tc/rfp_tc.json`)

| TC | 입력 | 길이 | 체크포인트 |
|---|---|---|---|
| TC1 | 신한은행 흑백프린터 152대 | 5.8천 자 | 30 |
| TC2 | 삼성생명 데스크탑 표준 모델 | 7.3천 자 | 33 |
| TC3 | 신한은행 27인치 모니터 980대 | 6.1천 자 | 30 |
| TC4 | KB손해보험 개인전산장비 단가계약 | 7.5천 자 | 40 |
| TC5 | **4건이 한 파일에 묶인 통합 문서** — 긴 입력 · 사업별 귀속 | 2.7만 자 | 133 |

체크포인트는 Winmate 히스토리에 정리하고 원문과 따로 대조까지 마친 요구사항(`tc/golden_forms.json`)에서 뽑은 *반드시 들어가야 할 사실*입니다(수량 · 규격 수치 · 마감 일시 · 메일 주소 · 평가 기준 · 자격 · 보증금 등). 출력의 공백을 없앤 뒤 정규식으로 대조합니다. TC5는 각 체크포인트를 **맞는 사업 안에서만** 인정하고, 다른 사업에 들어가 있으면 `misattributed` 로 셉니다. 정답 폼은 모든 TC에서 recall 1.0을 받습니다(테스트로 확인).

TC를 다시 만들려면: `python3 tc/build_tc.py <원문 묶음.md> --samples ../../src/rfp_samples.json`

## 실행

```bash
cd poc/test
python3 -m unittest -v test_rfp_pipeline          # 오프라인 테스트 + (키 · 네트워크가 되면) Gemini 라이브 테스트
python3 run_experiment.py --backend gemini --max-chars 1500 3000   # TC1~5 × 4조건 × 조각 크기 2개 (무료 등급이면 --rpm 10)
python3 run_experiment.py --backend gemini --cond chunk_carry_gap --max-chars 1500   # 권장 설정만
python3 run_experiment.py --rescore 20261012-gemini-final   # 호출 없이 저장된 폼을 지금 채점 기준으로 다시 채점
python3 run_experiment.py --backend replay        # 기록된 Gemini 응답으로 네트워크 없이 같은 결과 재현
python3 run_experiment.py --backend rules         # LLM 없는 규칙 기준선
python3 run_experiment.py --backend gemini --enrich   # + Tavily 출처 수집
```

결과는 `results/<run_id>/` 에 쌓입니다.
- `summary.md` · `summary.json` — TC × 조건 표, 놓친 체크포인트, 조건별 평균 (`results/LATEST.md` 는 마지막 실행 사본)
- `<TC>/<조건>/result.json` — 조각 · 원장(근거 인용 · grounded) · 추적(조각별 이월 메모 · 미해결 참조) · 가드 · 점수 · 비용
- `<TC>/<조건>/winmate_form.json` — Winmate 고객 요구사항 입력 폼과 같은 모양(사업명 · 고객사 · 최종 제안대상 · 키맨별 [분류] 요구사항 · 자유형식 · 제작자 의견)
- `results/cache/<모델>/` — Gemini 응답 기록(replay 용, 같은 프롬프트는 다시 호출하지 않음)

## 결과 (자세한 내용: `results/REPORT.md`)

`gemini-3.1-flash-lite` · 프롬프트 v3.1 · 최종 실행 `results/20261012-gemini-final` (35회) · 테스트 28개 모두 통과(Gemini 라이브 3개 포함)

| 조건 | 단건 RFP 4건 평균 recall | 통합 문서(2.7만 자) recall · 사업 분리 · 잘못된 귀속 | 단건 호출 · 토큰 |
|---|---|---|---|
| single | 0.592 | 0.083 · 1/4 · 0 | 3 · 10K |
| chunk_nocarry @3000 | 0.971 | 0.962 · 4/4 · 1 | 5.5 · 21K |
| chunk_carry @3000 | 0.946 | 1.000 · 4/4 · 0 | 5.5 · 25K |
| chunk_carry_gap @3000 | 0.984 | 0.977 · 4/4 · 0 | 9 · 34K |
| **chunk_carry_gap @1500 (권장)** | **0.984** | **1.000 · 4/4 · 0** | 13 · 45K |

- 통째로 넣으면 요약이 되어 세부가 빠집니다(통합 문서는 사업 4개 중 1개만). 나눠 읽기가 필수.
- 맥락 이월은 긴 문서에서 사업별 귀속을 지키고 recall을 올립니다. 단건(6~8천 자)에서는 차이가 잡음 범위.
- 조각은 작을수록, 그리고 갭 채우기를 더할수록 안정적으로 높습니다. 근거 인용 확인 97~99%.
- 남은 누락(권장 설정): 신한 모니터 RFP 제출서류 10번째 `시력보호기능 인증공문` 1건 — 모델이 '10가지 지정 서류'로 뭉뚱그림.
