# Storyboard 설계 에이전트 — 설계

요구사항 · 제품/솔루션 선택 결과 · 업종 · (있으면) 이전 storyboard 를 받아 **storyboard 전체(파트 순서 · 이름 · 말할 내용)** 를 설계한다.
Best Scenario 21개를 레퍼런스로 쓰되, **논리 골격만 빌리고 내용은 이 고객의 입력에서만** 가져온다.

지금 앱의 'AI로 나머지 구성'(`src/ai.js` `aiStoryboard`)은 업종별 고정 순서(규칙) 또는 레퍼런스 없는 한 번의 LLM 호출이다. 이 에이전트는 그 자리를 대체하는 것을 목표로 한다(같은 출력 모양 · 같은 스트리밍 방식).

---

## 1. 입력 · 출력

### 입력 `proposal` (앱 `store.js` 제안서 모양 그대로)

| 필드 | 쓰는 곳 |
|---|---|
| `req.free` · `req.form`(사업명 · 고객사 · 최종 제안대상 · 키맨별 요구 · 가중치 · 제작자 의견) · `req.files`(이름 · 메모 · 본문) | 요구 원장(R1…Rn), 상황 판정, 근거 수치 |
| `ctx.products` · `ctx.solutions` · `ctx.cases` | **선택 결과** — storyboard 에 나올 수 있는 제품 · 솔루션 · 사례는 이것뿐 |
| `ind` | 업종(없으면 요구 원문에서 추론) |
| `parts` (있으면) | **이전 storyboard** — 유지 · 이어 쓰기의 기준 |
| `options` (선택) | `mode`: `continue`(이전 파트 유지, 빈 곳만 설계 · 기본) / `redesign`(잠기지 않은 파트는 고쳐도 됨) · `strategy`: 사용자가 고른 전략(있으면 그대로 따름) · `max_parts` |

### 출력

```json
{
  "strategy": {"key": "pain", "why": "...", "confidence": 0.62, "alternatives": ["roi", "value"]},
  "thesis": "이 제안 한 줄",
  "ending": "pilot",
  "parts": [
    {"type": "challenge", "name": "객실에서 생기는 문제", "goal": "문제의 크기를 숫자로 합의",
     "items": ["고장 접수 월 평균 46건", "..."], "answers": ["R2", "R5"],
     "origin": "new", "ref": {"id": "bs07", "stage": "문제", "adapted": "호텔 객실 → 이 고객의 병동"}}
  ],
  "coverage": {"R1": [0, 3], "R7": []},
  "questions": ["확인 필요한 정보"],
  "issues": [{"code": "uncovered", "detail": "R7"}],
  "trace": {"references": [...], "calls": [...]}
}
```
앱에는 `parts` 를 `{type, name, items, done: false, layouts: []}` 로 넣는다(표지는 storyboard 파트가 아님 — 앱 규칙 그대로).

## 2. 원칙

1. **요구가 먼저, 레퍼런스는 다음.** 모든 파트는 요구(R id) · 선택(제품/솔루션/사례) · 전략이 요구하는 단계 중 하나로 존재 이유를 대야 한다. 레퍼런스는 *순서와 논증 방식*의 근거이지 내용의 출처가 아니다.
2. **레퍼런스는 추상화해서 보여 준다.** 모델에게 원문 시나리오(장표 역할 문장 · 메시지)를 그대로 주지 않고, 단계 골격 · 단계 목적 · 왜 비슷한지 · **무엇이 다른지** · **가져오면 안 되는 그 사례 고유 표현**을 담은 *패턴 카드*로 준다.
3. **여러 레퍼런스를 섞는다.** 상위 1개를 복제하지 않도록 서로 다른 전략 · 요구 유형의 카드 3장을 주고, 어느 카드의 어느 단계를 빌렸는지(`ref`)와 어떻게 바꿨는지(`adapted`)를 파트마다 적게 한다.
4. **이전 storyboard 는 사용자의 작업이다.** `continue` 모드에서 기존 파트는 지우거나 고치거나 순서를 바꾸지 않는다. 새 파트는 앞 · 사이 · 뒤 어디든 넣을 수 있다. 레이아웃까지 채운 파트(`done` · 채운 장표)는 `redesign` 모드에서도 잠근다.
5. **근거 없는 것은 쓰지 않는다.** 숫자는 입력(요구 · 첨부 · 선택한 제품 사양 · 사례 성과)에 있는 것만, 제품 · 솔루션 이름은 선택한 것만, 다른 업종 표현은 쓰지 않는다. 지키지 못한 것은 검증 단계가 잡아 고친다.
6. **LLM 은 규칙이 찾은 후보 안에서 고른다.** 레이아웃 에이전트 live1 에서 LLM 이 규칙이 맞힌 업종 · 전략을 덮어쓴 문제가 있었다 → 전략은 규칙이 근거를 찾은 후보 3개 안에서(사용자가 고르면 그것), 업종은 입력 우선.

## 3. 구성

```
proposal ─▶ ① 요구 원장 ─▶ ② 상황 판정 ─▶ ③ 레퍼런스 검색 · 패턴 카드 ─▶ ④ 설계(LLM | 규칙) ─▶ ⑤ 검증 ─▶ ⑥ 수리 ─▶ storyboard
                │              │                     │                                  ▲            │
                └── 이전 storyboard 분석(잠금 · 빈 단계) ──────────────────────────────────┘            └─ 1회 LLM 수리 → 남은 것은 규칙으로
```

| 단계 | 하는 일 | LLM |
|---|---|---|
| ① 요구 원장 | 키맨 요구(가중치) · 자유형식 문장 · 제작자 의견 · 첨부 메모를 원자 요구 R1…Rn 로. 분류(18종 → 선호 파트 유형), must/should, 수치 사실, 일정 · 단계 · 평가 구조 신호. 선택한 제품 · 솔루션 · 사례를 카탈로그 설명으로 풀어 둔다 | 없음 |
| ② 상황 판정 | 요구 유형(신규 · 교체 · 경쟁 · 운영 · 확산 · 브리프) · 맥락 수준(거의 없음 · 모호 · 복잡) · **전략 후보 3개**(7종 점수) · 결말 후보 · 분량 예산 | 없음(④에서 후보 안에서만 선택) |
| 이전 storyboard 분석 | 기존 파트의 유형 · 단계, 잠금 여부, 이미 다룬 요구, 빠진 단계 | 없음 |
| ③ 레퍼런스 | Best Scenario 21개 점수(요구 유형 · 전략 후보 · 업종 · 제품/솔루션 겹침 · 상황 문장 유사도) → 다양성을 둔 상위 3개 → 패턴 카드(단계 골격 · 목적 · 비슷한 점 · 다른 점 · 쓰지 말 표현) | 없음 |
| ④ 설계 | 전체 storyboard JSON(전략 · 한 줄 · 결말 · 파트[유형 · 이름 · 목적 · 내용 · 답하는 요구 · 빌린 단계]) | **1회** (없으면 규칙 설계) |
| ⑤ 검증 | 아래 표 — 규칙으로 판정 | 없음 |
| ⑥ 수리 | 문제 목록을 주고 고친 storyboard 를 다시 받음(1회). 남은 문제는 규칙으로 고침 | 0~1회 |

> 실험 결과([REPORT.md](REPORT.md) §4.4): LLM 수리는 효과가 없었고, 요구만 있는 과제에서는 요구 반영을 떨어뜨렸다. 기본값에서 빼고 규칙 수리만 쓰는 것을 권장한다.

규칙 설계(LLM 없음 · 오프라인 대체): 고른 전략의 레퍼런스 단계 골격 → 요구 분류가 요구하는 파트 유형 · 선택 결과가 요구하는 파트(제품 → 제품/구성, 사례 → 사례/Why) 추가 → 예산에 맞게 자름 → 요구 문장 · 선택 결과로 내용 채움.

### 레퍼런스 패턴 카드 (예)

```
[R1] bs07 · 교체·리뉴얼 · 문제 해결형 · 결말: 파일럿 승인 · 업종: 호텔(이 고객: 요양병원)
골격: 맥락(customer) → 문제(challenge) → 장면(solution) → 구성(products) → 실행(execution) → 근거(effect) → 결정(closing)
단계 목적: 문제 — 근본 원인을 고객의 숫자로 · 실행 — 영업 중단 없는 교체 …
비슷한 점: 요구 유형 같음 · 전략 후보 1위와 같음 · 솔루션 겹침 1(hvac)
다른 점: 업종 다름 · 이 사례 제품 4개 중 3개는 선택에 없음
쓰지 말 것: 객실, 투숙객, 체크인, LYNK, 호텔 TV …  (그 사례에만 있고 이 고객 입력에는 없는 말)
```

### 검증 항목

| 코드 | 검사 | 고치는 방법 |
|---|---|---|
| `type` | 파트 유형이 목록에 없음 · 표지 | 버림 / free |
| `keep` | 이전 파트가 빠짐 · 바뀜 · 순서가 바뀜 | 원본으로 되돌림 |
| `dup` | 같은 이름 · 같은 유형의 겹치는 파트 | 합침 |
| `budget` | 파트 수가 예산 밖 | 요구와 연결 안 된 파트부터 뺌 |
| `uncovered` | 가중치 높은 요구가 어느 파트에도 없음 | LLM 수리 → 선호 유형 파트에 항목 추가 |
| `stray` | 선택하지 않은 제품 · 솔루션 이름 | 항목 삭제 |
| `number` | 입력에 없는 수치 | 수치를 `[확인 필요]` 로 |
| `leak` | 레퍼런스 고유 표현(쓰지 말 것 목록) 사용 | LLM 수리 → 항목 삭제 |
| `flow` | 마무리(다음 단계)가 끝에 없음 · 단계 역행 | 마무리 이동 · 추가 |

## 4. 앱 연결

- `aiStoryboard(pr, {onPart})` 와 같은 자리 · 같은 스트리밍(`streamedObjects`)으로 바꿀 수 있게 출력 파트 모양을 맞춘다. ①②③⑤는 규칙이라 브라우저 JS 로 옮기기 쉽고, ④⑥만 `window.claude` sample 호출이다.
- 사용자가 전략을 고른 경우(전략 수립 단계) `options.strategy` 로 받아 후보 판정을 건너뛴다.
- 출력의 `ref` · `answers` 는 storyboard 버블의 "왜 이 파트?" 설명과 요구 → 파트 추적에 쓴다.

## 5. 평가 계획

| 세트 | 내용 | 정답 |
|---|---|---|
| **처음부터**(14) | 히스토리 샘플 중 storyboard 가 있는 케이스(F1–F8 · P1–P5 · S1)의 요구 · 선택 · 업종만 주고 전체 설계 | 샘플 히스토리의 storyboard |
| **이어서**(14) | 같은 14건에서 앞쪽 절반 파트를 이전 storyboard 로 주고 나머지 설계 | 뒤쪽 절반 |
| **정답 없음**(10) | storyboard 가 없는 요구 단계 샘플 8건(RFP 4 · R1–R3 · B 호텔) + 작성 중인 A 커피 · E 오피스 이어 쓰기 | 없음 — 규칙 지표 · 독립 심사 |

비교 조건: 앱 규칙(`fallbackStoryboard`) · 레퍼런스 복제(상위 1개 그대로) · 앱 AI 방식(레퍼런스 없는 LLM) · 레퍼런스 원문을 그대로 준 LLM · 에이전트(규칙만) · **에이전트(LLM)**. LLM 조건은 3회씩.

지표
- 정답 대비: 파트 유형 F1 · 순서 일치(LCS) · 단계 묶음 커버 · 파트 수 차이 · 정답이 쓴 입력 사실(수치 · 모델 · 솔루션)의 재현율 · 전략 일치(메타 라벨)
- 정답 없이: 요구 반영률(키맨 요구가 어느 파트 글에 들어갔는가) · 선택 반영률 · 선택 밖 제품/솔루션 · 근거 없는 수치 · **레퍼런스 복제율**(레퍼런스 문장과 거의 같고 입력에는 근거가 없는 항목 비율) · 다른 업종 표현 · 형식(유형 · 중복 · 마무리) · 이전 파트 보존
- 독립 심사: 정답 · 에이전트 · 비교 조건 storyboard 를 섞어 이름을 가리고, 이 코드를 만들지 않은 별도 에이전트가 요구 적합 · 흐름 · 구체성 · 고객 적합(복제 흔적)으로 채점

주의: 정답 storyboard 도 한 사람(이 프로젝트에서 만든 샘플)의 한 가지 답이다. 정답과 다르다고 틀린 것이 아니므로 정답 대비 지표는 구조 근접도로만 읽고, 품질 판단은 정답 없는 지표 · 독립 심사와 함께 본다. 샘플의 제작자 의견에 전략 이름("가치 선도형: …")이 적힌 경우가 있어, 전략 정답을 그대로 흘리지 않도록 평가 입력에서는 전략 이름만 가린다.
