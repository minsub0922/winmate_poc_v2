# Storyboard 설계 에이전트 · 실험 보고 (live-v2 · 2026-10-18)

설계는 [DESIGN.md](DESIGN.md), 실행 방법은 [README.md](README.md)에 있다. 숫자의 원본은 `results/live-v2/` 에 있다: `summary.md`(지표) · `stats.md`(신뢰구간) · `judge.md`(독립 심사) · `outputs.jsonl`(모든 storyboard).

## 1. 요약

- **독립 심사(이름 가림, 2벌 × 22과제)에서 에이전트가 앱의 지금 AI 방식보다 분명히 낫다.**
  - 처음부터 짠 14과제: '바로 쓸 수 있는가' 점수가 +0.71 [+0.46, +0.96] 높았고, 순위 비교에서 27승 1패였다.
  - 요구만 있는 8과제: +1.00 [+0.69, +1.25], 15승 1패였다.
- **샘플 히스토리 storyboard(정답 역할)와는 차이가 없었다.**
  - 평균 순위는 에이전트 1.86, 샘플 2.21이고 15승 13패였다.
  - 단, 샘플은 출처를 확인한 외부 통계를 담고 있는데 심사자는 출처를 볼 수 없어 이를 감점했다(§7).
- **구조 지표에서도 앱 AI 방식보다 낫다.** 정답과의 파트 유형 일치(F1)는 0.537 대 0.323(+0.21 [+0.13, +0.30])이었다. 에이전트는 모든 결과가 결정 · 다음 단계로 끝났다(앱 AI 방식은 10%).
- **레퍼런스를 '따라가지 않는다'는 요구를 지켰다.**
  - 레퍼런스를 그대로 가져온 비교 조건은 문장의 87%가 Best Scenario 문장의 복제였고, 다른 고객 · 업종 표현이 평균 1.1개 남았다. 예: 스터디카페 제안에 '빈 타석', 야구장 제안에 '정류장 · 상황실'.
  - 에이전트는 복제 1.3%, 다른 업종 표현 0이었다.
  - 구조 일치는 복제 조건과 같은 수준(F1 0.537 대 0.505, 차이 없음)이면서, 고객 수치 재현은 0.57 대 0.01이었다.
- **LLM 수리 단계(⑥의 LLM 1회)는 빼는 것이 낫다.** 전체 실행의 절반쯤에서 호출을 1번 더 쓰지만, 정답형 과제에서는 효과가 없었다. RFP 과제에서는 요구 반영을 오히려 떨어뜨렸다(−0.074 [−0.136, −0.022]). 내용은 그대로 두고 '이 요구에 답함' 표시만 붙여 검증을 통과했기 때문이다.

## 2. 무엇을 만들었나

`poc/test/storyboard_agent/sbagent` — 표준 라이브러리만 쓰는 Python 패키지다. LLM 은 Gemini REST(`poc/.env`)를 쓴다.

```
제안서 ─▶ ① 요구 원장 ─▶ ② 상황 판정 ─▶ ③ 레퍼런스 검색 · 패턴 카드 ─▶ ④ 설계(LLM | 규칙) ─▶ ⑤ 검증 ─▶ ⑥ 수리 ─▶ storyboard
```

1. **요구 원장** — 키맨별 요구(R1…) · 자유 입력 · 제작자 의견 · 첨부 메모 · 제품/솔루션/사례 선택 · 이전 storyboard 를 하나의 근거 묶음으로 모은다.
2. **상황 판정** — 요구 유형 · 맥락 수준 · 전략 후보 3개 · 결말 유형 · 분량을 정한다. 단서는 규칙 점수로 보고, 레퍼런스의 전략 투표를 더한다.
3. **레퍼런스** — Best Scenario 21개 중 3개를 고른다. 유사도 + 요구 유형/전략/업종 일치로 점수를 매기고, 같은 전략 · 요구 유형은 감점해 다양하게 고른다. 레퍼런스는 원문 대신 **패턴 카드**로 넘긴다. 카드에는 단계 골격, 단계 목적, 이 고객과 같은 점 · 다른 점, '쓰지 말 것'(그 사례 고유의 업종 · 공간 · 고객 · 제품 이름) 목록이 들어간다.
4. **설계** — LLM 이 JSON 스키마로 storyboard 전체를 짠다. 전략은 후보 3개 안에서 고르고, 이전 파트는 `{"keep": "P1"}` 로 잠근다. 파트마다 답하는 요구 · 참고한 레퍼런스(`ref` · `adapted`)를 기록한다. LLM 이 없을 때는 규칙 설계를 쓴다.
5. **검증** — 중복 · 분량 · 요구 미반영 · 선택 밖 제품/솔루션 · 근거 없는 수치 · 레퍼런스 고유 표현 · 흐름(마무리)을 본다.
6. **수리** — 문제를 넘겨 LLM 이 1회 고치고, 남은 문제는 규칙으로 고친다. 근거 없는 수치는 `[확인 필요]` 로 가리고, 이전 파트는 원래 순서 그대로 되돌린다.

`agent.to_app_parts()` 가 앱 storyboard 파트 모양 `{type, name, items, done:false, layouts:[]}` 으로 바꾼다.

에이전트는 정답과 같은 전략(투자 회수형)을 골랐고, 레퍼런스 bs13(다점포 무인 매장 에너지 절감)의 골격을 빌렸다. 내용은 고객 수치로 채웠다. 같은 레퍼런스를 그대로 가져오면 스크린골프용 표현 '빈 타석'과 레퍼런스의 파일럿 규모(3개 매장 · 4주)가 남는다. 이 고객의 실제 계획은 6곳 · 8주다.

## 5. 실험 중 고친 것

첫 실행(live-v1) 결과를 하나씩 보다가 검증기의 오탐을 찾았다. 고친 뒤 다시 돌린 것이 live-v2 다. 고친 내용은 모두 회귀 테스트 `tests/test_agent.py` 14개에 넣었다.

- **다른 업종 표현 오탐**
  - 'A/S 체계'를 고객 이름 'S 체계'로 읽었다.
  - 이 고객 이름에 조사가 붙은 'K 리조트의'를 다른 고객으로 보았다.
  - '스마트' 안의 '마트'를 잡았다.
  - TV '시청'을 관공서 시청으로 보았다.
  - 이 때문에 에이전트가 멀쩡한 항목을 지우고, 지표도 틀렸다.
- **수치 근거 대조**
  - 같은 값을 다르게 쓴 것을 다른 값으로 보았다. 예: 1억 9,000만 원 = 1.9억 = 1억 9천만, 11.16 = 11/16 = 11월 16일, 46곳 = 46개, 2027.3 = 2027년 3월.
  - 이제 금액 · 날짜 · 연월 · 월 · 연도 · 단위 분류(개수 · % · 기타)를 '주장' 단위로 맞춘다. 가릴 때도 그 주장만 `[확인 필요]` 로 바꾼다.
- **이전 storyboard 를 근거로 인정**
  - 사용자가 앞 파트에 쓴 통계(출처 포함)가 근거로 인정되지 않았다.
  - 이제 이전 파트의 항목 · 채운 장표 값 · 출처를 근거에 넣는다.
- **규칙 수리가 이미 있는 유형을 또 만들던 것** — 유지한 '공간 시나리오'와 새 '공간 시나리오'가 생기던 문제를 고쳤다.

수치 · 업종 표현 규칙은 이 샘플들을 보며 고쳤으므로, 새 데이터에서는 다른 오탐이 나올 수 있다.

## 6. 심사자가 지적한 에이전트의 약점

- **조건 · 단서가 빠지거나 목표를 결과처럼 씀**
  - "민원 제로화", 가정 표기 없는 "+65%", 작성 중 기능 · EHS · '5년 무상'을 확정처럼 쓴 경우가 있었다.
  - 수치 검사는 숫자만 보므로 이런 표현을 못 잡는다.
- **사례 성과 왜곡** — 스타벅스 DT 사례를 '매출 증대'로, 패스트파이브를 '예약률 향상'으로 바꿔 썼다. 사례 성과는 선택한 사례의 proof 원문만 쓰게 해야 한다.
- **규칙 수리가 넣은 잘린 문장** — 요구 원문을 45자에서 자르면서 문장이 끊겼다(RFP 과제에서 지적됨).
- **RFP 지정 목차를 따르지 않음** — 삼성생명 RFP 의 ①~⑦ 순서를 따르지 않았다. 다른 후보도 모두 마찬가지였다.
- **빠진 범위** — B 호텔의 냉방, F2 · F5 의 구성 · 수량 파트, P4 의 게이트 수치가 빠졌다.

## 7. 한계

- **정답 역할의 storyboard 는 이 프로젝트에서 시드로 쓴 샘플 히스토리다**(실제 영업 담당자가 쓴 것이 아님).
  - 14건이고, 같은 작성 원칙으로 Best Scenario 와 함께 만들어졌다. 그래서 레퍼런스와 과제가 실제보다 가깝다.
  - 심사자(Claude)와 샘플 작성자가 같은 계열 모델이다.
- **심사자는 샘플 storyboard 의 장표 근거(출처 링크)를 보지 못했다.** 그래서 샘플의 외부 통계를 '입력 밖'으로 감점했다. 샘플의 '사실' 점수는 낮게 나온 값이다.
- **심사 묶음의 고객 입력이 4,500자에서 잘렸다(RFP 4과제).** 그래서 심사자 일부가 선택된 사례(캠프 험프리스 · 신한은행)를 '지어낸 사례'로 보았다. 그래도 에이전트는 이 4과제의 8개 심사 모두에서 1위였다. `judge_pack.py` 는 이후 12,000자로 고쳤다.
- **전략 판정 규칙(단서 세기 · 사전 확률)은 이 샘플을 보고 조정했다.** 전략 일치 0.857 은 낙관적인 값이다.
- **'요구 반영' 지표는 낱말 기준이라 원문을 옮길수록 높다**(규칙만 0.94). 질은 심사로 판단했다.
- LLM 은 Gemini 3.1 flash-lite 하나만 썼다. 심사자도 사람(영업 담당자)이 아니라 LLM 이다.

## 8. 앱 적용 제안 · 다음 단계

1. **앱 'AI로 나머지 구성'(`src/ai.js` `aiStoryboard`)을 에이전트로 교체한다.**
   - 지금 프롬프트는 레퍼런스 없이 한 번에 짜고, 처음부터 짤 때 결과의 90%가 결정 파트 없이 끝난다.
   - 에이전트의 ①–③(원장 · 상황 · 패턴 카드)과 ⑤–⑥(검증 · 규칙 수리)은 결정적 코드라 JS 로 옮기기 쉽다. LLM 호출은 설계 1회만 쓴다.
   - 결과의 `ref` · `adapted` · `answers` 를 파트 카드에 '참고한 사례 · 답하는 요구'로 보여 준다.
2. **LLM 수리를 빼고**, 요구 반영 검사를 '선언만 한 경우는 인정하지 않음'으로 강화한다. 규칙 수리는 요구를 자르지 말고 요약해 넣는다.
3. **단서 보존 검사** — 입력에서 '목표 · 가정 · 작성 중 · 확인 필요'로 표시된 값이 출력에서 확정형으로 바뀌면 잡는다. 사례 성과는 proof 원문만 쓴다.
4. **RFP 목차 감지** — RFP 가 목차를 지정하면 그 순서를 골격으로 쓴다.
5. **리서치 단계 연결** — 샘플 storyboard 의 강점(출처 있는 시장 통계)은 에이전트가 만들 수 없다. 기존 근거 · 리서치 기능과 이어서 `[확인 필요]` 자리를 채우게 한다.
6. **평가 보강** — 실제 제안서 storyboard 로 정답을 늘리고, 영업 담당자 심사를 소수라도 받아 LLM 심사와 맞춰 본다.
