# Scenario Composer — 샘플 버티컬 시나리오 기반 제안서 자동 구성

성능 제한 모델(Gemini flash-lite)로 샘플 버티컬 시나리오(프런티어 모델이 만든 완성 덱) 수준의 Storyboard를 만드는 PoC다.
모델이 흐름 · 장표 · 사진을 **창작하지 않고**, 미리 분리해 둔 케이스(샘플 버티컬 시나리오의 파트 모듈 · 장 · 사진 칸) 중에서 **판단 · 선택**만 하게 한다.

```
고객 입력 ─▶ A. 상황 판정 ─▶ B. 파트 추천 ─▶ (사람이 파트를 고르고 고침) ─▶ C. 레이아웃 ─▶ D. 문구 ─▶ E. 사진
             업종·요구유형    상황 순위 1위 샘플 버티컬 시나리오   출처 모듈(src)을 기억          모듈의 장을   장별 원문을   칸마다 '원래 덱의
             (+2순위)·전략    = 뼈대, Gemini는 뺄 파트     새 파트는 가장 가까운 모듈     이 고객에 맞게 이 고객으로   사진' 설명 → 후보 5
             ·결말(enum)      (≤2)·빌릴 파트(≤2) 판단     을 Gemini가 선택              변형           옮겨 쓰기     → Gemini 선택
                              → 파트 이름
```

| 단계 | Gemini가 하는 일 | 코드가 보장하는 것 |
|---|---|---|
| A 상황 판정 | 업종 16 · 요구 유형 7(+애매하면 2순위) · 전략 7 · 결말 8 중 고르기, 공간 · 요구 구 추출 | enum 스키마, 고객이 정한 업종 고정 |
| B 파트 추천 | 뺄 파트(≤2) · 빌릴 파트(≤2, 2·3순위 시나리오에서) 결정, 파트 이름 · 항목 다시 쓰기 | 뼈대 = 상황 순위 1위(요구 유형 3 · 전략 2 · 결말 1 · 업종 1 · BM25 4 · 프런티어 덱 +1, 85개 leave-one-out으로 맞춘 가중치), 요청 분량("10장")과 먼 덱 감점, 뼈대 순서 유지 · 표지 앞 · 마무리 뒤 |
| C 레이아웃 | (출처 없는 파트만) 모듈 4개 중 선택 | 폐기 → 사진 버전, 다른 업종 변형 → 이 업종 변형, 고르지 않은 솔루션 전용 장 → 고른 솔루션의 같은 역할, 제품 그리드 → 제품 수만큼(같은 제품을 되풀이하는 둘째 그리드 제거), 고르지 않은 제품 장 제거, 덱 내 중복 → 뒤 장이 쓸 레이아웃은 피해서 가장 가까운 미사용 장 |
| D 문구 | 파트 단위로 원문(ref)을 이 고객 내용으로 옮겨 쓰기 | 칸 길이 상한, 다른 고객 이름 · 근거 없는 수치 · 레이아웃 견본의 작성 안내문("…사진으로 교체", "자리표시") 검사 → 1회 수정 요청 → 그래도 남으면 이름은 고객명, 수치는 [00], 안내문은 삭제 |
| E 사진 | 칸마다 후보 5개 중 선택(빈 칸 없이) | 칸 종류(제품 컷 · 장면 · 화면 · 구성도) 필터, 다른 업종 장소 · 다른 업종에서 찍은 사진 제외, '고객 자기 공간' 칸은 그 업종 사진만, 타사 간판 · 로고 · 외관은 사례 파트에서만(고객 자신의 것은 허용), 표지 · 마무리는 다른 회사 현장 사진 금지, 제품 칸은 그 제품만, 덱 내 중복 회피(제품 컷만 재사용 허용) |

- r1: 사진 브랜드 필터 · 중복 연쇄 수정. Gemini가 후보 5개 중 뼈대를 고르게 했더니 같은 업종 템플릿(버티컬)을 9/13번 골라 상황(교체 · 경쟁 등)이 다른 흐름이 됨.

- r3: 뼈대를 상황 1순위로 고정(Gemini는 빼기 · 빌리기 · 문구 · 사진만), 요청 분량 반영, 빈 사진 칸 없앰, 표지 · 마무리 중립 사진, 견본 안내문 차단.
- 남은 차이(심사 사유): 고객 고유 요구(TCO 비교, 구독/설치 비교, 확산 물량, 분량)를 다루는 장이 없음 · 업종이 다른 뼈대의 장 내용 잔재 · 세부 업종이 다른 사진(마트에 백화점, 사이니지 제안에 에어컨) · 사진 설명의 타사 이름 · 근거 없는 수치를 [00]으로 비워 둠(정답 덱은 가상의 수치를 씀).
- 덱 1개 ≈ Gemini 호출 25회, 입력 약 6만 · 출력 약 1.8만 토큰(flash-lite), 약 2분.

## 데이터 (library.json)

`python -m composer.library` — 앱 KB(`app/data/runtime/kb`)와 샘플 버티컬 시나리오 내보내기(`scripts/export_library.mjs`)로 만든다.

- 시나리오 85개(bs01–22 · 버티컬 40 · 표준 20 · 어카운트 3) → 파트 모듈 624개 → 장 1,356개(채운 문구 · 사진 그대로)
  - 위 수치와 실험 결과는 2026-11-11 기준. 2026-11-12부터 앱 시나리오는 107개(bs01–20 · 버티컬 40 · 업종별 표준 44 `bs_std_<버티컬>` · 어카운트 3) — bs21 · bs22 · 예전 표준 20종은 삭제됨. `library.json`은 지금 KB로 다시 만들고, `run.sh` · `eval/report.py`의 평가 묶음은 삭제된 덱을 빼고 예전 표준 5개를 같은 업종의 새 표준 덱으로 바꿈.
- 레이아웃 838개: 칸(data-tb 역할 · 원문 · 글자 크기, data-img 종류 · 힌트 · 크기 · fit · 샘플 사진), 업종 변형 패밀리, 고정 문구
- 사진 3,702장: 도입사례 · 솔루션 미디어(설명 · 종류), 사진 레이아웃 · 채움 묶음 · 제품 갤러리 · 제품 라이브러리.
  업종은 출처(사례 업종 · 파일 접두사 · 시나리오)로, 보이는 장소는 캡션의 장소 단어로(출처명 제거 후) 따로 기록한다.

## 실행

```bash
cd poc/test/scenario_composer
python -m composer.library                       # 라이브러리 (KB가 바뀌면 다시)
bash scripts/run.sh smoke                        # 12개 덱 (키: poc/.env 의 GEMINI_API_KEY — 출력하지 않음)
bash scripts/run.sh composer r4 rank base        # Layout Agent 와 같은 40개 덱 재구성 (all = 85개)
bash scripts/run.sh baseline                     # 현재 Layout Agent, 정답 덱 숨김 (runs/base-ho)
bash scripts/run.sh judge r4 base-ho             # 1:1 블라인드 심사 (상대 생략 시 정답 대비) — Pro 호출이 비싸니 덱 수를 줄여서
bash scripts/run.sh report gold,base-ho,r4       # 같은 덱 기준 비교표 (지표는 저장된 덱으로 다시 계산 — 호출 없음)
python -m eval.render runs/r4/bs01.json          # 장표 HTML (팩 이미지 해석) · --gold 로 정답 덱
```

앱에서는 `kind: compose` 작업(`app/api/poc/adapters/compose.py`)으로 쓴다 — `step: parts`(파트 추천) → 사람이 고침 → `step: layouts`(장표 완성).
빈 Storyboard의 '자동 구성'은 파트 추천을, 파트가 있으면 '장표 자동 완성 · 파트 N개' 버튼이 장표 완성을 부른다.
라이브러리는 `app/data/runtime/composer`에 만들어진다(poc/ 아래에는 쓰지 않음). `WM_COMPOSER_BASE=llm` 이면 뼈대를 Gemini가 상위 3개 중에서 고른다.

## 레이아웃 자동 구성 (`step: auto`) — 목차 템플릿 기반, 오케스트레이터 + 파트 병렬 (2026-11-13)

목차 템플릿(표준 제안서 · 과제 해결형 …)으로 Storyboard에 깔린 장(파트마다 `exemplar` = 템플릿 장 + 채운 값)을 이 고객의 제안서로 바꾼다.
코드: `composer/auto.py`(계획 · 장 구성 · 문구) · `composer/pictures.py`(사진) · 작업: `app/api/poc/adapters/compose.py` `step: auto`.

```
요구사항(+요약) · 연결한 제품/솔루션/사례 · 공간 구성 · 템플릿 파트
  └▶ 1. 오케스트레이터 (모델 1회 + 코드 보정)   thesis · storyline · 요구 포인트(R1…)와 그 답이 되는 제품/솔루션 ·
                                                파트별 message · 주인인 요구 · 제품 · 솔루션 · 사례 · 공간     → event plan
  └▶ 2. 장 구성 (코드, 계획대로)                 공간 장 = 계획한 공간 수 · 솔루션 장 = 연결한 솔루션(없는 것 빼고 빠진 것 더함) ·
                                                사례 장 = 연결한 사례 · 조감도/Map/간지/목차 = 개수에 맞는 변형 · 쪽 · 장 번호
  └▶ 3. 파트마다 병렬: 문구(모델, 칸 단위 수리 1회 · 길이 줄이기) → 사진(코드 + 모델 검수)               → event part started/done/error
```

| 단계 | 모델이 하는 일 | 코드가 보장하는 것 |
|---|---|---|
| 계획 | 요구 포인트 추출 · 파트별 메시지 · 배정 | id는 입력에 있는 것만 · 연결한 제품/솔루션/사례는 그것을 보여 줄 수 있는 파트에 반드시 · 요구 포인트의 주인은 한 파트(당사의 이해 · 요약은 '과제로 짚기'만) · 공간 파트는 공간 구성 그대로 · 템플릿 순서 · `avoid`(다른 파트가 맡은 것) |
| 문구 | 칸 다시 쓰기(파트 1회 호출, 45칸마다 분할) | 칸 정책 = 앱의 slot_modes.json(고정 → 유지 · 목차 번호 → 코드 · 제품/솔루션/사례 → 같은 항목이면 유지, 바뀌면 그 항목 사실로) · 장마다 '이 장이 답할 요구'(니즈 3열 ↔ 핵심 제안 1·2·3) · 검사: 길이 · 다른 고객 이름 · 근거 없는 수치 · 연결하지 않은 제품/솔루션 · 견본 그대로 옮김 · 한자 → 어긴 칸만 다시 요청 1회 → 줄이기/가리기 |
| 사진 | 순위 1위가 문구와 맞는지 검수(대안 제시) | 칸 종류와 묶인 대상: 제품 칸 = 그 제품의 컷(없으면 빈 칸) · 솔루션 장 = 그 솔루션 미디어 · 사례 장 = 그 사례 사진(포인트별 매칭) · 조감도 = 고객 조감도 · 공간/장면 = 후보 검색. 금지 규칙: 다른 업종 장소 · 같은 업종의 다른 세부 업종(마트에 백화점) · 다른 회사 간판 · 문구와 다른 제품군 · 사진이 아닌 그림. 덱 전체에서 같은 장면 사진 한 번(스레드 안전 레지스트리) · 고른 이유는 `agent.img[칸]` |

**사진 메타데이터** — `scripts/tag_images.py`가 장면 사진 2,500장을 한 번씩 보고(비전 모델, 빌드 때 1회) 실제로 보이는 것 · 장소 종류 · 보이는 간판 · 제품군을
`image_facts.json`에 적는다(라이브러리의 `images[src].vf`). 캡션만으로는 알 수 없던 것(전통시장 · IT 매장 · 타사 간판)을 여기서 거른다.
칸 옆 문구는 레이아웃 HTML의 좌표로 찾는다(`htmlslots` x · y — 그림 아래/옆/위의 글).

**사진 속 정확한 제품(품목)** (2026-11-18 사용자 지시 — "공간 이미지의 경우 정확한 품목이 포함된 이미지야. 세탁기여도 다른 세탁기면 에러 … 공간인데 제품이
없을 수도 있는데 이러한 경우는 상관없는거야")
- 메타데이터(`composer/items.py`, 라이브러리 VERSION 7): 사진마다 `items` = 그 사진의 **출처가 말하는** 정확한 제품 — 제품 이미지 라이브러리(img/lib: 그 제품의
  제품 페이지 · e-카탈로그 쪽 · 도입사례), 앱 이미지 DB의 모델, 제품 갤러리, 그 밖엔 설명의 모델 코드(QM55C) · 큐레이션 제품의 전체 이름(360 카세트)만.
  '메뉴보드 · 세탁기 · 사이니지' 같은 일반 단어는 제품이 아니다. `shows` = item(그 제품) · none(비전도 설명도 제품 없음) · unknown(제품이 보이는데 무엇인지 모름),
  `item_fams` = 보이는 제품군. 같은 제품 = 같은 행이거나 자기 모델 코드(model · specModel)를 공유하는 다른 카탈로그 행(`item_keys`, 'laundry' ↔ WF18A9100KV) —

**연결한 것만 · 틀의 잔재 없이** (2차, 2026-11-13 — 실제 구성 덱을 읽고 고친 규칙. 모두 코드가 지키고 `app/tests/test_compose_auto.py`가 확인한다)
- 솔루션 장 · 여정 장 · 기능 아이콘은 연결한 솔루션의 것만. 연결한 솔루션이 없으면 그 장들을 빼고 파트는 제품 장(공간 장 또는 `L_TOC_PFEAT`)으로 채운다. 핵심 기술 장의 열은 열마다 그 솔루션의 블록 · 아이콘(`sol_tech`), 없으면 빈 아이콘.
- 사례는 연결한 것 먼저. 연결한 사례가 없으면 템플릿 사례는 같은 업종이거나 연결한 제품이 나올 때만 남고, 아니면 같은 업종의 다른 사례 → 그것도 없으면 사례 장과 간지 · 목차의 그 줄을 뺀다.
- 꼬리말은 `고객사 · 구성 이름`. 제목에 고객사가 이미 있으면 다시 붙이지 않고, 기본 제목 '새 제안서'는 쓰지 않는다. 견본 고객 이름(업종 이름)은 고객을 가리키는 자리에서만 바꾼다(`swap_cust`).
- 요구에도 연결 항목에도 없는 주제(에너지 · 냉난방)는 연결하지 않은 제품 종류와 같이 다룬다 — 다시 쓰게 하고, 남은 짧은 칸은 비운다(`agent.emptied`).
- 숫자 · 단위 칸: 단위 칸에는 단위만(줄 이름과 종류가 다르면 맞춤), 숫자 칸에는 숫자만, 큰 숫자 칸은 고객 자료에 있는 숫자만(없으면 `[00]`). 사양 장은 열마다 그 제품의 사실만 — 견본 제품의 값이 남으면 비우고,
  제품이 없는 열은 지운다. 단일 제품 사양 장의 항목/값 짝이 밀리면 카탈로그 사양으로 다시 채운다. 간지의 줄 이름에 수치가 오면 템플릿의 줄 이름 또는 그 장의 제목으로 되돌린다.

### 업종 트렌드 장 · 시장조사 근거 (2026-11-15)

당사의 이해의 업종 트렌드 장(`L_TOC_TRLINE` 연도별 추이 · `TRSHARE` 구성비 · `TRSTAT` 핵심 지표 · `TRKEY` 키워드)은 값이 고객 자료에도 제품 DB에도 없는
바깥 사실이라, 문구 단계(`fill_part_text`)가 쓰면 전부 `[00]`으로 남거나 지어내게 된다. 그래서 이 장들은 `composer/market.py`가 맡는다.

- `run_auto(..., market=hook)` — `hook(spec, want) -> {'sheets': [...], 'research': {...}}`. 앱은 `app/api/poc/market_research.py`(실제 웹 검색 → 원문 대조 검증 → 장 구성)를
  넘긴다. composer는 검색 수단을 모른다 — hook이 없으면 지금까지처럼 템플릿 장 그대로다.
- 조사는 덱 계획과 나란히 돌고, 트렌드 장이 든 파트만 그 파트의 문구 단계 앞에서 결과를 기다린다(다른 파트는 기다리지 않는다).
- 결과가 고른 종류가 템플릿과 다르면(추이 자료가 없어 추이 막대 대신 핵심 지표 등) 요청의 `market.sheets`(이 업종의 종류별 견본)로 장을 바꾸고, 칸 값은 `lock`으로 건다.
  lock이 걸린 칸은 문구 단계가 다시 쓰지 않고 `enforce_linked` · `_fix_counts`도 건드리지 않는다(`sl['market']`).
- 출력: 장마다 `ev`(칸 번호 → 근거 [{title, url, sub(인용)}])와 `research`(고른 종류 · 이유 · 검색어 · 조사 시각 · 안내). 근거가 모자란 장은 손대지 않고
  `status: 'partial'` · `research.ok: false`로 내보낸다(값을 지어내지 않는다). 조사가 실패 · 시간 초과여도 파트는 실패하지 않는다.
- 테스트: `app/tests/test_compose_auto.py` `MarketResearch`(가짜 hook) · `app/tests/test_market_research.py`(검증 규칙).
