## 알게 된 것

1. **통째로 한 번에 넣으면 정리가 아니라 요약이 된다.** 단건도 평균 0.59, 2.7만 자 통합 문서는 0.08에 사업 4개 중 1개만 찾았습니다. 출력 항목이 15~20개로 줄어들며 제출서류 · 보증금 · 무효 사유 같은 세부가 통째로 빠집니다. 긴 RFP는 반드시 나눠 읽어야 합니다.
2. **놓치는 건 무작위가 아니라 유형이 있었다.** v1에서 반복해 빠진 것은 ① 제출서류 목록 ② 제출처 메일 주소 ③ 표의 예상수량 열 ④ 법 조항 번호 ⑤ 들여쓴 하위 항목. 이 다섯을 규칙으로 명시한 v2부터 조각 조건 단건 recall이 평균 0.91~0.92 → 0.95~0.99로 올랐습니다.
3. **맥락 이월은 긴 문서에서 값을 한다.** 통합 문서(3000자 조각)에서 맥락 없이 0.962 · 잘못된 귀속 1건 → 맥락 이월 1.000 · 0건. 같은 은행 RFP 두 건처럼 문구가 거의 같은 문서가 섞여도 사업별로 갈라 담았습니다. 단건 RFP(6~8천 자)에서는 차이가 잡음 범위입니다.
4. **조각은 작을수록 recall이 높다.** 모든 조건에서 1500자가 3000자보다 같거나 높았습니다. 큰 조각에서는 모델이 항목을 덜 뽑습니다(같은 첫 조각에서 19개 vs 21개, 그 차이에 마감 · 추첨 · 마스킹 규칙이 들어 있었음).
5. **갭 채우기가 가장 안정적인 보강이다.** 조각을 뽑은 뒤 '요구사항처럼 보이는데(숫자 · 필수 · 불가 · 제출 · 까지 …) 어떤 항목에도 안 들어간 원문 줄'만 다시 물어봅니다. 3000자 조건 단건 평균 0.946 → 0.984. 숫자 인지(줄의 두 자리 이상 숫자가 항목에 없으면 일부만 옮겨진 줄로 판단)를 넣은 뒤 KB 표의 예상수량(500 · 360)까지 잡았습니다. 대가는 호출 약 1.6배.
6. **작은 모델의 반복 폭주를 막아야 한다.** JSON 응답의 한 문자열 칸에서 같은 문장을 끝없이 되풀이하는 일이 TC3에서 재현됐습니다(출력 한도까지 3천 토큰). 단계별 출력 상한 · 폭주 감지 · 온도를 올린 재시도(0.1→0.6→0.9) · 통합 단계 실패 시 규칙 기반 대체로 실행이 멈추지 않게 했습니다(최종 실행에서 대체 사용 0건).
7. **본문은 모델이 아니라 원장에서 조립한다.** 통합 단계는 id로 키맨 배정 · 병합 · 주제 묶음만 결정하고, 요구사항 문장은 원장 그대로 이어 붙입니다. 그래서 통합 단계에서 내용이 빠지거나 바뀌지 않고(같은 숫자 · 비슷한 문장일 때만 중복 병합, 나머지 원장 항목은 모두 폼에 들어감), 사람용 글에 남은 id는 항목 내용으로 바꿉니다. 묶음은 2~6개, 남은 항목은 같은 분류 4개씩 → 단건 폼이 조건별 평균 21~34줄로 사람 정리(24~33줄)와 비슷해졌습니다.
