# proposal_score — 제안서 평가 모듈 (PoC)

앱의 평가 기준 54개(`src/review/criteria.js`)로 제안서를 평가한다. 모든 기준을 매번 채점하지 않는다. 기준을 그래프로 묶어 2단 계층(GraphRAG 의 community · community compression)을 만들고, 제안서의 전체 맥락(요구 유형 · 결정권자 · 전략 · 고객 요구)과 장별 구성요소(텍스트 상자 · 글자 크기 · 위치 · 넘침 · 이미지 칸)를 보고 **어떤 기준으로 볼지 먼저 고른 뒤** 그 기준만 LLM 으로 1~3점 채점한다.

모든 기준에는 `1점: … / 2점: … / 3점: …` 정의가 따로 있다(`criteria/rubrics.json`). "~를 평가해 1~3점" 같은 문장은 테스트가 막는다.

## 파이프라인

```
제안서(장별 텍스트 상자 · px · 위치 · 넘침 · 이미지 칸 · 거래 맥락)
 │
 ├─ gate      기준별 적용 여부 (제품이 있나 · 수치가 3개 이상인가 · 경쟁 언급이 있나 …)       criteria.py
 ├─ checks    결정론 자동 점검 → 기준별 메모 + 위험 신호                                   checks.py
 │            (고객명 · 수치 충돌 · 출처 · 자리표시 · 칸 단위 사양 대조 · 글자 크기 · 어절 수 · 빈 이미지 칸 …)
 ├─ route     ① local seeds: 거래 맥락 → 개념 노드 → 기준, 기준 그래프 간선으로 1번 확산         router.py
 │            ② L1(LLM): 상위 커뮤니티 4개 관련도 0~3 (위험 기준이 있는 묶음은 무조건 내려감)
 │            ③ L2(LLM): 세부 커뮤니티 관련도 + 기준별 우선순위 0~3
 │            ④ 확정: 예산 12개(최소 10) · 위험 기준 우선순위 +1.5 · 위험 없는 위생 기준은 '규칙 통과'
 ├─ score     세부 커뮤니티마다 1번 호출: 루브릭 1/2/3 정의 중 하나 + anchor · 근거 인용 · 고칠 점      scorer.py
 │            인용 문구를 장 본문과 대조(grounding), 실패 · 누락이면 규칙 점수로 대체
 └─ aggregate 1·2·3 → 0·50·100, 기준 가중치 w → 앱 분류 가중치 → 총점 · 등급(앱과 같은 85/70/50)   pipeline.py
```

계층(`taxonomy/taxonomy.json`, `python3 -m proposal_score taxonomy` 로 다시 만듦)
- 노드: 기준 54개 + 개념 56개. 기준–기준 가중치 = 공유 개념 수 + 1.2 × TF-IDF 코사인 + 0.35 × 같은 앱 분류 + 0.25 × 같은 범위. 0.30 이상 간선과 노드마다 상위 3개 간선(286개)을 남긴다.
- 결정론 Louvain 두 번: 기준 → 세부 커뮤니티 12개(모듈러리티 0.436) → 상위 커뮤니티 4개(0.505).
- Gemini 요약: 세부 커뮤니티는 기준에서, 상위 커뮤니티는 하위 요약만으로 만든다. 세부 12개 중 9개가 앱의 7개 분류를 가로지른다.

| 상위(L1) | 세부(L2) |
|---|---|
| C1 제안서 품질 및 정합성 | F01 정보 정합성 · 보안 · F06 수치 · 데이터 정합성 · F09 제품 · 브랜드 표기 · F12 표현 · 문체 |
| C2 제안서 이행 및 실행 체계 | F02 형식 · 요구사항 준수 · F10 실행 계획 · 운영 |
| C3 제안 논리 및 타당성 검증 | F03 경영진 의사결정 · 비용 · F04 고객 · 업종 적합성 · F05 시장 데이터 · F07 논리 · 신뢰성 |
| C4 제안서 완성도 및 전달력 | F08 논리 · 스토리 구성 · F11 시각 디자인 · 가독성 |

## 실행 (`poc/test` 에서)

```bash
python3 -m proposal_score score bs01 bs07                     # 몇 건 평가 → 화면 요약
python3 -m proposal_score best --run <id> \
    --stability 6 --perturb bs01,bs04,bs10,bs19 --full all    # 전체 + 안정성 · 교란 · 전체 기준 대조군 → results/<id>/REPORT.md
python3 -m proposal_score report <id>                         # 저장된 JSON 으로 REPORT.md 다시 만들기
python3 -m proposal_score best --backend replay --run <id>    # 저장된 Gemini 응답만으로 재현(네트워크 없음)
python3 -m proposal_score best --backend rules --run <id>     # LLM 없이 규칙만(파이프라인 확인용)
python3 -m proposal_score taxonomy                            # 계층 · 요약 다시 만들기 (taxonomy.json 을 덮어씀)
```

- 공통 옵션: `--model` · `--budget 12` · `--min-k 10` · `--temperature 0` · `--rpm 30` · `--workers 3`.
- 키는 `poc/.env` 의 `GEMINI_API_KEY` · `GEMINI_MODEL`(기본 `gemini-3.1-flash-lite`)를 읽는다. 키 값은 출력하지 않는다.
- 같은 프롬프트의 응답은 `results/cache/<모델>/` 에 저장된다. 실행이 중간에 끊겨도 같은 명령을 다시 돌리면 이어서 진행한다.
- 입력 데이터 다시 만들기 (winmatev2 루트에서, `npm install` 후): `node poc/test/proposal_score/tools/export_best_scenarios.mjs`. 앱의 `applyOverrides` · `fillOf` · `bgOfSlide` 로 21개 시나리오(308장)를 headless Chromium 에 그려 `data/best_scenarios.json` 으로 낸다. `CHROMIUM_PATH` 로 브라우저를 지정할 수 있다.
- 기준을 바꿨으면 `python3 -m proposal_score.tools.sync_criteria` 로 `criteria/criteria.json` 을 다시 만든다(테스트가 앱과의 일치를 확인).

## 테스트

`python3 -m unittest proposal_score.tests.test_proposal_score` — 20개(Gemini 실호출 1개는 `PS_LIVE=1` 일 때만).

- 기준: criteria.js 와 54개 일치, 모든 루브릭이 서로 다른 1 · 2 · 3점 정의를 가짐, gate.
- 계층: 구조 · 결정론 · Louvain.
- 입력 · 점검: 교란을 자동 점검이 잡음, 수치 충돌 교란이 진짜 충돌이고 위험 신호로 잡힘, 칸 단위 사양 대조(앱 규칙 오탐 재현 사례).
- 라우팅: 관련도 · 우선순위 · 예산, 위험 기준이 예산이 차도 남음, 위생 기준 규칙 통과, 맥락 seed, LLM 실패 시 규칙 대체.
- 채점 · 집계: 응답 파싱 · 근거 대조 · 집계 계산, 21개 전부 오프라인 end-to-end.

## 결과 — Best Scenario 21개 (`results/20261018-gemini-v6/REPORT.md`)

`gemini-3.1-flash-lite`, 온도 0. 덱 1개당 호출 약 10회(라우팅 2 + 채점 7~9), 입력 약 5.6만 · 출력 약 4천 토큰. 실호출로는 덱당 40~60초가 걸린다(분당 45회 제한, 4개 병렬). 실험 전체(본 실행 · 안정성 · 교란 68건 · 전체 기준 대조군)는 958회 호출이다(기록 재사용 포함). 오류는 0건.

## 한계 · 다음 단계

1. **총점의 의미.** 고른 기준만으로 낸 총점은 문제 쪽으로 기울어 있다(전체 평가보다 평균 17점 낮다). 고른 기준이 바뀌면 서로 비교할 수 없다. 화면에는 "핵심 점검 점수"로 보이고, 같은 덱의 수정 전후를 비교할 때는 기준을 고정해 다시 채점(`same` 모드)하는 게 맞다. 전체 등급이 필요하면 전체 기준 평가가 호출 1.25배 정도로 가능하다.
2. **재현율.** 규칙으로 위험이 보이는 기준은 98% 고르지만, 규칙 신호가 없는 문제(WR8 · SB5 · DS8 · MK1)는 놓친다. 이 기준들에 위험 신호를 더하고 예산을 12 → 16 으로 늘리는 쪽을 검토한다.
3. **비용 절감은 작다.** 채점을 세부 커뮤니티 단위로 묶어 부르므로 기준 수를 줄여도 호출은 0.81배다. 라우팅의 가치는 비용보다 "이 거래에서 무엇을 먼저 볼지"에 있다.
4. **정답 라벨이 없다.** 지금 검증은 교란 · 안정성 · 내부 일치뿐이다. 사람이 매긴 점수 소량(예: 덱 5개 × 54개 기준)으로 루브릭과 DS3/DS4 기준값을 보정해야 한다. 배포용(leave-behind)과 발표용 덱은 밀도 기준이 다를 수 있다.
5. 입력은 앱이 그린 Best Scenario 다. 업로드 PPT 는 도형 · 글자 크기 추출기를 붙이면 같은 파이프라인을 쓸 수 있다(gate 가 `geometry` · `font_sizes` 를 본다).
