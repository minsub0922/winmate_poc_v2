# 실험 · 평가 · 개선 기록

평가 세트
- **cases (30 TC)** — 10개 case(업종 × 전략) × 3개 요구 복잡도. 개선에 사용한 개발 세트.
- **holdout (6 TC)** — 개발 세트에 없는 업종(TP · PB · VN · AD · OE). v9 까지 열어 보지 않았고, v9 결과를 보고 v10~v13 을 고쳤다(→ 그 뒤로는 블라인드가 아님).
- **holdout2 (6 TC)** — holdout 결과를 보고 고치기 **전에** 써 둔 두 번째 블라인드 세트(ID · VN · TP · PB · AD · FB). v13 에서 처음 돌렸다.

> 블라인드 주장의 한계: TC 파일은 `make_cases.py` 한 번으로 모두 다시 만들어졌고 실행 기록도 같은 날 몇 시간 안에 몰려 있어, '먼저 써 두고 나중에 열었다'는 순서를 타임스탬프로 증명할 수는 없다. 일반화 추정치로는 holdout2 **첫 실행(0.968)** 만 쓰고, 그 뒤 수치는 그 세트를 보고 고친 결과로 읽어야 한다.

v0 ~ v14 는 **오프라인(결정론) 백엔드** 결과다(처음 작업 환경에서는 Gemini 가 막혀 있었다). v15 부터는 사용자 컴퓨터에서 **Gemini(gemini-3.1-flash-lite) 로 같은 평가**를 돌렸다.

## 반복별 변경

**v0 → v1**
- 맥락 판정: '서술형 목표 문장' 신호(n_goal_sent) 추가 — 명사 나열(①)과 모호한 요구(②)를 가름. 제품명 속 '스마트'를 목표로 오인하던 문제 제거. L2 오판 6건 → 0건.
- 요구 분류: 첫 매치 → **점수 방식**(strong 2 · weak 1 · 날짜/원격 등 extra) + 동점 순서. 새 분류 3종(교육·지원 · 시스템 연동 · 가치·브랜드).
- 덱 중복 장표 제거(assemble 단계에서 이미 쓴 장표 제외, 시나리오 적응 시 같은 장표로 모이면 RAG 로 재선택).
- 모호(②)에는 value 파트를 반드시 둔다.
- 값 입력: 다른 업종 샘플 문장 → 파트 내용 · 요구 · 자리표시.
- 라벨 오류 1건 수정: C04_L3 의 기대 충돌을 '물량 vs 일정' → '가격 vs 규격'(RFP 원문상 실제 충돌).

**v1 → v2**
- 복잡(③) storyboard 재설계: 다른 업종 시나리오에서 빌린 파트의 이름 · 역할 문장을 걷어냄(예: 병원 덱에 '창구와 방문 상담'이 들어가던 문제), 서사는 맥락 · 문제 · 가치 · 장면 단계만 차용, 기준(dimension)별 대응 파트는 요구가 있는 기준 전부 후보로 두고 우선순위로 자름.
- 전략별 대표 시나리오를 match_best 점수(업종 · 요구 타입 · 유사도)로 고름.
- '시공 vs 영업 유지' 충돌 규칙을 시공어 근접 패턴으로(‘야간 낙상 알림’ 오탐 제거).
- 평가 항목 · 배점 추출(‘화질 · 밝기 30점, CMS 20점 …’).

**v2 → v3**
- 요구 → 파트 연결을 '요구가 선호하는 파트 유형 순서' 우선으로(기준별 대응 파트가 운영 요구를 가로채던 문제).
- 전략별 필수 장표(투자 회수형 → EF-B · CO-A, 단계 확산형 → PL-A …), 제품이 있으면 공간별 제품 장표 필수.
- 범위 · 수량 오분류(‘18개월’의 ‘개’) 수정, 파일럿 문장은 확산으로.

**v3 → v9 (지표 포화 후 — 미리보기 렌더를 보고 고침)**
- 값 입력 전면 재작성: 칸 종류(수치 · 모델 · 라벨 · 칩 · 설명) 판별 → 숫자 칸에 글자를 넣거나 라벨을 잘라 먹지 않음.
- 샘플 고객명 정규식(A 커피 · B 호텔 · T 은행 …) + 조사 자동 교정(‘신한은행가’ → ‘신한은행이’).
- 파트 유형별 헤드라인 템플릿, 아이브로 = 번호 · 파트명.
- 데이터 그룹(제품 · 사례 · 요구 · 키맨 · 가치 기둥 · 공간)은 못 채운 칸을 자리표시로 — 샘플 사례 · 샘플 제품이 남지 않음.
- **샘플 수치 지우기**: 원문 · 카탈로그에 없는 숫자가 샘플 문구에 남으면 `[00]` (예: 주거 덱에 ‘320개 매장’이 남던 문제).
- 카탈로그 밖 모델 코드 · 연결 안 된 제품명(OH55C · Flip Pro · 투명 OLED …) → `[제품]`.
- 요구 대응 표 전용 채우기(RM-A 키맨 · RM-B 요구 전수 · RM-C 평가 배점 · SC-B 규격 · SE-A 보안).
- 첨부 원문 줄 정리(글머리 · 표 기호 · 제목 줄 · 붙임 안내 제거), 제출 절차 요구는 could(덱 우선순위에서 내림).
- 레이아웃 메타데이터에 **편집 불가 문구(static_text)** 와 그 업종(static_ind) 추가 — 446개 중 280개가 data-tb 밖 한글 문구를 가짐. 다른 업종 고객에게는 -1.5 감점, 검토 리포트에 표시.
- 복잡(RFP)에는 솔루션을 자동 추천하지 않음(범위는 고객이 정함).

**v9 → v13 (holdout 결과 반영)**
- 업종 단서 보강(야구장 · 구단 · 과학관 · 구청 · 민원실 …), 단서 1개라도 경쟁 업종이 없으면 채택.
- 모호한 목표 문장(‘바꿀 방법을 찾고’, ‘~였으면 좋겠다’)도 요구로 추출.
- 전략 판정: 단서가 적을 때 비율이 과장되지 않도록 신뢰도 가중 + 가장 비슷한 Best Practice 의 전략을 사전값으로(통신사 전용 단말 → 단계 확산형).
- 일정 · 실행 기준의 대응 장표를 내용으로 고름(개발 · 양산 → CU-B, 파일럿 → PL-A, 무중단 → IP-C).
- 업종 표준 시나리오가 그 업종에 지정한 장표(P-R 유닛 패키지 · VP-U 업종판 …)에 +2 가산.

**v13 → final (holdout2 결과 반영)**
- ‘수익 · 최소 보장’ → 비용, ‘휘도 · 구조 안전’ → 규격, ‘중단 없이 · 하룻밤’ 시공 충돌 패턴.

**v13 → v14 (독립 검토 반영)** — 코드를 쓰지 않은 별도 에이전트에게 코드 · 결과 검토를 맡겼고, 지표가 1.0 인데도 화면에 문제가 남은 곳을 찾았다.
- 지표 정의를 엄격하게: 핵심 요구 반영 · 원문 수치는 **슬라이드에 실제로 채운 글자**만 본다(이전엔 storyboard 이름 · items · 푸터까지 봐서 '980' 이 프로젝트명으로 점수를 받았다). 파이프라인 검사와 따로 구현한 **stray** 지표(최종 화면 — 채운 칸 + 남은 샘플 칸 + 고정 문구 — 에 고르지 않은 제품 · 솔루션 이름이 없는 슬라이드 비율)를 더했다. flow · layout_part · violations · fill_clean 은 여전히 파이프라인 자체 검사를 쓴다.
- 인터뷰 답이 실제로 반영되게: 빈 정보에 값을 답하면 요구(I01…) · 수치 근거 · 원문에 추가(값 입력에서 그 숫자를 쓸 수 있음), 충돌 C1~C5 선택지마다 다른 대응 장표, '키맨 관심사 분산'에서 한쪽을 고르면 그 키맨 우선, LLM 질문 답 기록. CLI `--ask` 에서 '값을 입력' 을 고르면 값을 받는다.
- 요구 정리: 연락처 · 담당자 줄 제거, 입찰 절차 · 계약 조건 판정 확대(청렴 · 부정당 · 추첨 · 보증금 · 무효 사유 · 재무제표 · 실명번호 …) → could + RM-B 대응표에만 연결 + 반영률 분모에서 제외(제출 체크리스트). **v3~v9 의 '제출 절차 요구는 could' 는 일부(R31 · R33 · R43 · R45 등)가 must 로 남아 있어 사실과 달랐다** — v14 에서 바로잡음. RFP 의 요약 줄 · 상세 줄 중복을 수치 포함 관계로 제거(C04: 46 → 39개, 그중 20개가 제출 절차). 영업 메모는 필수로 올리지 않는다.
- 연결: 평가 · 선정 요구 → RM-C, 키맨 요구 → RM-A, 나머지 → RM-B. 요구가 모두 다른 파트로 가서 비어 버린 '기준별 대응' 파트는 뺀다. 제출 절차는 파트 우선순위를 끌어올리지 않는다.
- 검토: 요구 크기(27인치)와 제안 제품 크기(32")가 하나도 안 맞으면 high 이슈.
- 값 입력: BM-A 구성표(제품 · 사양 · 원문 수량 980대, 안 쓰는 행은 비움) · SM-B 공간×제품표 · VP-D 이해관계자표 전용 채우기. 솔루션 이름 교체를 한 번에(‘SmartThings Pro Pro’ 이중 치환 버그 수정) · 같은 역할의 솔루션으로만. 정량 효과(“응답 시간 30% 감소”)를 효과 표 변화 칸에. 문장 앞 몇 낱말만 남는 라벨 조각(‘이 결과로’) 금지. 다른 업종 샘플의 반복 행 라벨(‘가격 표기 오류’) 제거. 제품 공간은 고객 업종에 맞는 것만(주거 고객에게 ‘객실’ · 병원에 ‘픽업대’ 제거). 요구 닻(부제).
- 재현성: 집합 순서에 기대던 곳(키맨 쌍 선택 · 단어 정렬 · 정규식 대안 순서)을 고쳐 `PYTHONHASHSEED` 를 바꿔도 42 TC 결과가 같다. 이전 실행들은 같은 코드라도 실행마다 조금씩 달랐을 수 있다.

**v14 → v15 (Gemini live 실행 — 사용자 컴퓨터에서)**
- 첫 live 실행(live1)에서 규칙 경로에는 없던 약점이 드러났다.
  - 최저가 입찰(C04 · 배점표 있음)인데 LLM 이 전략 후보를 다시 매기며 rfp 를 3위 밖으로 빼서 기본 전략이 value 가 됐다.
  - 규칙이 맞힌 업종을 LLM 이 덮어썼다(K05 광고 매체 → 공공).
  - LLM 이 요구의 '답할 파트' 를 바꿔 추적성(key_trace)이 깨졌다(‘내부망 보관’ → 솔루션 장표).
  - LLM 채우기가 요구 닻(부제) · 표의 요구 원문 같은 고객 자료 칸을 덮어썼고, 연결 안 된 솔루션 이름을 썼다.
  - 칸 길이 맞추기가 'SmartThings Pro' 를 'SmartThings' 로 잘랐다(다른 솔루션처럼 보임).
  - deepagents 전략 코파일럿을 실제로 돌려 보니(도구 순서: get_decomposition → set_answers → preview_storyboard → finalize) 사용자가 고른 rfp 가 후보 3개 밖이라 버려지고 value 로 바뀌었다.
- 고친 것: LLM 은 규칙이 근거를 찾은 후보 안에서 순서만 정하고, 배점표가 있는 입찰 · 근거가 뚜렷한 전략은 첫 후보로 둔다 / 업종은 규칙이 없거나 약할 때만 LLM / 같은 분류면 규칙 파트를 앞에 두고 LLM 제안은 뒤에 / 고객 자료로 채운 칸은 LLM 에 locked 로 보내고 받지 않는다 / LLM 문장에도 솔루션 이름 검사 / 제품 · 솔루션 이름은 자르지 않는다 / 사용자가 고른 전략은 후보 밖이어도 따른다.
- live2: cases 0.988 · holdout 0.991 · holdout2 0.986. 남은 것: K05 업종(규칙 신뢰도가 낮아 LLM 판단을 따름 — 고객이 공공기관이 운영하는 광고 매체라 둘 다 말이 됨), C09_L3 에서 effect 파트가 빠진 1회(LLM 실행마다 다를 수 있음).
- 주의: live2 는 holdout 세트를 이미 본 뒤의 실행이고, LLM 출력은 실행마다 다르다(temperature 0.2, 각 1회 실행).

## 남은 한계
- 오프라인에서는 값 입력의 '서술 문장'(가치 설명 · 장점 문장 · 표의 대응 방안)을 쓰지 않는다 — 근거가 없으면 자리표시. Gemini 를 켜면 이 칸을 고객 맞춤 문장으로 채운다(근거 없는 숫자 · 샘플 고객 · 다른 업종 · 연결 안 된 제품/솔루션이 있으면 받지 않음).
- 원본 레이아웃 280개에 data-tb 밖 샘플 문구가 있다(예: RM-A 의 ‘↳ 해석’ 줄). 앱에서도 편집되지 않으므로 원본 보완이 필요하다.
- 평가 지표는 사람이 정한 gold 라벨 기준이며, 같은 사람이 규칙도 만들었다 — 블라인드 holdout2 첫 실행(0.968)을 일반화 추정치로 본다.
- 일부 지표(flow · layout_part · violations · fill_clean)는 파이프라인이 스스로 검사한 값을 그대로 쓴다. 값 입력 품질은 지표가 다 잡지 못하므로 미리보기(`eval/reports/final-cases/cases/*/preview.html`)를 눈으로 봐야 한다.
