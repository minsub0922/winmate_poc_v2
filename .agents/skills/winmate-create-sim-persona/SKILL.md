# 제안 시뮬레이션 고객 페르소나

[공통 데이터 계약](../../references/winmate-contracts.md)과 [페르소나 스키마·연동](references/persona-contract.md)을 먼저 읽는다. 외모·이름만 다른 인물이 아니라 실제 영업 대응을 다르게 연습할 수 있는 의사결정자를 만든다.

## 범위 결정

- 사용자의 입력과 기존 요구사항/제안서/Best Scenario에서 업종, 고객 규모, 최종 결정자와 영향자, 운영 과제, 제한 조건, 제품·솔루션·사례, 목표 난이도를 파악한다.
- 기본은 현재 앱에서 선택해 사용할 페르소나 1명과 요청 난이도다. 난이도 미지정이면 앱 기본인 2단계(첫 고객)를 사용한다. 3단계나 데이터셋을 요청한 경우 같은 인물·조직·사업 과제를 유지한 채 난이도별 관계·증거 요구·경쟁·예산·우려를 다르게 만든다.
- 산출물이 앱 저장용 인물인지, 요구사항까지 포함한 연습 패키지인지, 평가용 corpus인지 구분한다. 불명확하면 요구사항과 저장용 인물을 함께 제공하고 앱 연동 범위를 설명한다. 사용자의 기존 브라우저 저장소에 임의 주입하지 않는다.

## 페르소나 설계

1. 가상 고객명, 역할·결정 권한, 경력, 성향, 말투 예시를 만든다. 외모·성별·나이를 난이도나 성향의 근거로 삼지 않는다.
2. `situation`, 고객 발언, 현재 과제, 목표, 제약, 평가 기준, KPI를 구분한다. 공식 사례의 사실과 가상 고객의 가정·목표를 분리한다. 실존 사례의 성과를 이 고객의 실적으로 옮기지 않는다.
3. 요청 난이도에 맞는 관계·삼성 인식·경쟁·예산·의사결정·말투를 만든다. 기본 우려 수는 1/2/3개, 시작 만족도와 승패 기준은 현재 `LEVELS`를 따른다. 사용자가 다른 규칙을 요청하지 않았다면 바꾸지 않는다.
4. 우려마다 왜 걱정하는지, 어떤 근거·운영 계획·검증이 있어야 해소되는지와 다음 행동(`ask`)을 구체화한다. 고객은 우려를 자연스럽게 드러내고 먼저 정답을 알려 주지 않는다.
5. 제품·솔루션·사례·업종 ID를 현재 앱 레지스트리에서 대조한다. 평가 corpus의 `extraProducts`가 앱에도 있다고 가정하지 않는다. 관련 Best Scenario는 적합도를 보고 연결하며 없으면 강제로 붙이지 않는다.

## 실제 앱과 연결

- 저장용 인물은 `repositories/personas.js`의 `clean` 계약, 얼굴은 `looks.js`·`Portrait`가 지원하는 형태를 따른다.
- `clean`이 버리는 회사·요구사항·우려·`levels`를 인물 객체에 넣고 동작한다고 보고하지 않는다. 요구사항은 setup으로, 대화용 상세는 최종 profile로 전달하는 경로를 확인한다.
- `profile.lv`는 엔진이 일부 필드만 읽는 확장점이다. 저장→`buildProfile`→`newSim`→프롬프트→화면에서 보존되는지 확인한다. 인물별 관계·예산 등을 실제 적용해야 하는 요청이면 app 소유 경로에 필요한 adapter와 저장 계약을 함께 구현한다.
- 현재 기본 앱 경로는 persona의 `levels/lv/concerns/ask`를 최종 profile로 전달하지 않는다. 생성한 난이도별 조건을 실제 대화에 적용하는 요청은 이 adapter 구현과 왕복 검증까지 필수다. JSON 생성과 미구현 필드 설명만으로 그 요청을 완료했다고 보고하지 않는다.
- 기본 6개 key와 저장 기록을 유지한다. 새 프로필을 등록해도 기존 세션 얼굴·우려·과거 대화를 소급 변경하지 않는다.

## 검증과 전달

직렬화/다시 읽기, 필드 길이, ID 참조, 각 난이도 우려 수·초기 상태·성공 조건, 얼굴 렌더, 첫 대화와 우려 제시·해소·결정 요청 흐름을 확인한다. 연동한 경우 실제 Gemini를 사용하는 현재 앱으로 표본 연습을 검증하고, 실패를 가짜 대사·점수로 대체하지 않는다. 데이터만 생성한 경우 연동·LLM 검증을 했다고 주장하지 않는다.

페르소나와 setup/profile 매핑, 가상 가정/공식 근거, 저장·선택 방법, 시나리오 연결, 검증 범위와 미구현 필드를 전달한다.
