# Winmate Admin

별도 React 앱과 FastAPI 관리 API를 같은 서버의 `/admin/`에 연결한다. 일반 Winmate 앱은 `/`에서 그대로 제공한다. 관리자 소스·테스트·실행 설정은 이 `admin/` 디렉터리에서 버전 관리한다. DB·인증·업로드·로그·선택 의존성이 있는 `admin/runtime/`과 재생성 가능한 `admin/web/dist/`는 Git에서 제외한다.

## 실행

저장소 루트에서 실행한다. 기존 `app/.venv`와 `app/web/node_modules`가 준비되어 있어야 한다.

```sh
./admin/start.sh
```

기본 포트는 기존 앱과 같은 `8788`이다(루트 `.env.example`의 `WINMATE_API_PORT` · `WINMATE_BIND_HOST`). 하나의 프로세스가 `/`와 `/admin/`을 모두 제공한다. 저장소에 포함된 `admin/.enabled`에 따라 일반 `./start.sh`도 같은 결합 서버를 실행한다. 로그인 후 다른 포트로 이동하지 않는다. 실행 중인 이전 일반 앱 서버는 재시작해야 새 경로를 제공한다. 기존 서버를 유지하며 별도로 확인할 때만 다른 포트를 지정한다.

```sh
WINMATE_API_PORT=8794 ./admin/start.sh
```

일반 앱의 `admin` 로그인 세션을 공유한다. 관리자 API는 일반 앱 인증이 꺼진 환경에서도 유효한 관리자 세션을 요구한다. 다른 계정·비로그인 접근·다른 출처의 쓰기 요청은 거절한다. 비밀번호를 바꾸거나 별도 인증 우회를 만들지 않는다.

`admin/start.sh`는 관리자 프런트만 빌드하고 PDF·이미지 판독기를 `admin/runtime/python`에 설치한다. 기존 앱의 패키지 파일과 Python 환경은 수정하지 않는다. 이미 준비된 기존 앱 데이터·웹 빌드를 사용한다. 일반 `app/start.sh`에는 `admin/.enabled`와 관리자 파일이 모두 있을 때 결합 진입점을 선택하는 조건이 있다. 이 표시 파일도 버전 관리하므로 새 체크아웃에서 일반 시작 스크립트를 실행하면 관리자 의존성과 화면을 준비하고 `/admin/`을 제공한다. 관리자 없이 실행하려면 표시 파일을 제거하거나 기존 `app.api.main:app` 진입점을 직접 사용한다.

## 화면과 기능

- **관리 개요**: 실제 자산 건수, 주요 원본 상태, 원본 최신성 점검, DB 최신화, 최근 작업.
- **데이터 소스**: 삼성 B2B, e-카탈로그, 솔루션·도입사례, 이미지, 제안서·평가 자료, 공간 라이브러리, 추가 자료. URL 소스 연결, 사용 중지, 점검 주기, 원본과 DB 를 대조한 점검 근거, 원본 주소 · 리소스 링크. 아래 '데이터 소스 최신성 점검' 절.
- **에셋 라이브러리**: 제품·사진·레이아웃·시나리오·카탈로그·문서·공간 에셋·정적 파일과 pack. 검색, 유형·출처·상태 필터, 페이지 탐색, 출처·해시·시각 확인, 메모·태그, 일괄 보관·복원, JSON 내보내기.
- **에셋 추가**: 파일 또는 공개 HTTPS URL을 보존하고 서버에 설정한 실제 LLM으로 구조화한다. 추출한 제품·솔루션·사례도 각각의 에셋 행으로 등록하여 유형 필터와 모델 검색에서 찾을 수 있다. 각 행에는 부모 원본과 인용 근거가 연결되며 재분석해도 ID를 이름·모델에 따라 보존한다. PDF, PPTX, DOCX, UTF-8 텍스트·Markdown·CSV·JSON·HTML, PNG·JPEG·WebP. 파일당 25MB, 한 번에 10개. 원문 합계 35만 자 이하. PDF는 쪽, PPTX는 장별 인용을 보존하며 제품명·모델과 인용을 대조한다. 스캔 PDF는 성공으로 가장하지 않고 텍스트 PDF 또는 이미지 입력을 안내한다.
- **작업 내역**: 한 개의 작업 큐, 중복 요청 병합, 진행률, 취소, 재시도, 오류, 수집 로그, 실제 반영·누락 범위. 새로고침 후에도 기록을 조회할 수 있다. 재시작된 미완료 작업은 `interrupted`로 표시한다.
- **Provider**: LLM · Decision 모델 연결 전부(작은 카드), 켜기 · 끄기 토글과 역할별 대표(대표 실패 시 켠 순서로 대체), 연결 상태, 사내 서빙 주소 수정 · 재연결, 같은 입력의 병렬 실험. 아래 「Provider」 참고.
- **시스템**: 원본·앱·관리자 SQLite 테이블 조회, 무결성/FK 검사, 상세 pack 연결과 Agent KB 입력 해시 검증, DB 백업, 릴리스 변경표, 이전 버전 복구, 관리 활동 이력, 선택적 자동 점검.

- **소스 점검 · 업데이트**(`/admin/dss`): 실제 DSS DB(`proddb` · `app/data`)를 원천 소스와 맞춘다. 아래 '소스 점검 · 업데이트' 절.

- **레이아웃 구성 관리**(`/admin/layouts`): Storyboard '레이아웃 구성'이 추천하는 구성(목차 흐름)의 운영 값을 바꾸고, 목차별 레이아웃 · 샘플 시나리오를 본다. 아래 '레이아웃 구성 관리' 절.

- **레이아웃 관리**(`/admin/layout-library`): 전체 시트(활성 · 내용 후보 · 이전/숨김 · 삭제됨)를 탐색하고 이름·코드·본문 검색, 목차·업종·채움 방식 필터로 찾는다. 카드 hover는 시트만 확대한다. X를 누르면 확인 후 새 선택·추천에서 삭제한다. 상세 팝업에서 기본 문구를 시트 위에서 직접 편집하고 이름·목차 구분을 바꾼다. 시트는 평소 아무 표시 없이 보이고, 마우스를 올린 영역에 바로 테두리와 그 영역의 상태 · 전환 버튼(AI 작성 | AI 잠금)이 붙어 마우스를 따라 바뀐다(다른 영역은 0.1초 머물면, 빈 곳은 0.22초 뒤 — 버튼줄로 옮겨 가는 동안 사라지지 않게; 고정 영역은 주황 · 자물쇠, ‘영역 보기’로 전체 표시). 머리의 ‘입력 n’ 드롭다운은 그 시트의 입력(input param, 기본 접힘), 오른쪽 칸 전체는 채우기 흐름(agentic flow) — 아래 ‘입력 · 흐름’. 이미지 영역을 누르면 그 이미지 옆에 팝업이 뜬다 — 지금 이미지 · 관련 이미지(사진 라이브러리 `composer/library.json` images 에서 샘플 시나리오의 같은 칸에 쓰인 사진 · 같은 종류 · 공간 · 제품 · 업종 · 설명 · 같은 묶음 · 칸 비율 순, 라이브러리에 없는 아이콘 · 표지는 같은 폴더) · 검색(설명 · 이름 우선) · 원래 이미지 · AI 작성/AI 잠금. 고르면 시트에 바로 보이고(`draft-preview`, 저장 안 됨) ‘수정 반영’으로 저장되어 앱 · Storyboard 의 기본 사진이 된다(`edits.img`). API `GET /layout-library/{f}/images/{칸}?src=&ratio=&q=&offset=` · 썸네일 `GET /layout-library/{f}/images/file?src=`(라이브러리 사진 · 관리 자원 폴더의 이미지 파일만) — `admin/layout_images.py`. 변경이 있을 때만 ‘수정 반영’이 활성화되며 확인 팝업을 거쳐 저장된다. ‘활용 예시’ 드롭다운은 샘플 시나리오의 실제 문구·이미지로 채운 해당 장을 보여 준다.

세부 내용과 원문·설정·버전 비교는 팝업으로 연다. 데스크톱·태블릿·모바일에서 동작하며 팝업은 Escape, 초점 순환·복원을 지원한다.

## 데이터 범위

에셋 수집·색인 화면은 **관리자 격리 DB**를 갱신한다. 아래 DSS 업데이트, 레이아웃 구성 관리, 레이아웃 관리는 실제 앱과 연결된 예외다. 에셋 릴리스는 기존 production 제품 SQLite, 앱 JSON, Agent KB, 이미지 pack을 덮어쓰지 않는다. 각 에셋 릴리스에 `sync.admin_database=true`, `production_database=false`, `production_agent_kb=false`를 기록한다. 관리 DB의 자료와 전체 JSON을 내려받을 수 있다.

### 레이아웃 관리의 실제 반영

`app/api/layout_library.py`가 `app/data/runtime/layout_library.json` 한 파일을 관리한다(`WINMATE_LAYOUT_LIBRARY`로 경로 변경). 관리자 API, 앱 bootstrap과 `/api/layout-library`, 레이아웃 Agent KB, Storyboard 자동완성 composer가 모두 같은 값을 읽는다. 기본 메타·HTML·칸 구분은 재생성 가능한 KB/앱 모듈에 유지하고, 관리자의 수정은 안정된 `f`·`data-tb`·`data-img`에 대한 덮어쓰기로 저장한다. KB를 다시 export하거나 앱을 다시 빌드해도 관리자 수정은 보존된다.

- 칸별 `AI 작성 / 고정 / 제품 교체 / 솔루션 교체 / 사례 교체 / 후보 선택 / 목차 번호`를 설정한다. 기존 장·파트의 고정 규칙은 ‘기본 규칙’에서 유지된다. ‘칸별 설정 적용’은 이 장의 명시적 설정을 우선하고, ‘장 전체 고정’은 AI 채움을 막는다. 사람이 제안서를 편집하는 것은 계속 가능하다.
- 같은 구조의 업종별 내용 후보는 칸별 채움 설정을 공유한다. 대표 또는 후보 어느 쪽에서 바꿔도 같은 버전으로 함께 저장하며, 각 후보의 기본 문구·사진·이름은 해당 시트에서 수정한 것만 바꾼다.
- 수량별 레이아웃은 `app/web/src/domain/templates/layout_count_groups.json`의 명시적 묶음으로 표시한다. VP-F의 제품 2·3·4개 버전처럼 같은 목적의 항목 수 변형을 한 카드로 보여 주고, 겹친 시트 모양과 `3종` 배지, 각 버전의 hover 미리보기·선택 창을 제공한다. 관리자·웹앱 라이브러리·키워드/AI 검색·Storyboard 추천과 추가가 같은 규칙을 읽는다. 검색은 모든 버전의 코드·문구를 함께 색인하며, AI 검색 후보도 묶음당 하나다. 각 수량 버전의 `f`·칸 번호·AI 정책·저장된 시트는 개별 보존하고, 관리자에서 수정·삭제할 때 실제 버전을 먼저 고른다. 새 수량 변형은 이 명세에 추가하고 `app/tests/layout-count-groups.mjs`로 ID·검색·필터 정합성을 확인한다.
- 저장은 파일 잠금·원자적 교체·버전 비교로 처리한다. 다른 창이 먼저 저장했으면 409로 거절하고 최신 값을 다시 열게 한다. 관리자 활동 이력에는 사용자·버전·변경 칸을 남긴다.
- 열려 있는 앱은 같은 브라우저의 변경 알림과 포커스 복귀, 3초 주기 조회로 화면·검색·시트·내보내기의 기본값을 갱신한다. 서버 Agent는 요청 시 버전 변경을 감지해 KB·추천·composer 캐시를 갱신한다. 관리 목록은 5초 주기와 포커스 복귀 때 갱신한다. 연결이 끊긴 동안에는 마지막으로 받은 버전을 유지한다.
- 삭제는 새 라이브러리·검색·추천·자동구성에서 제외한다. 대표 레이아웃을 삭제하면 내용 후보도 함께 제외한다. 기존 저장 제안서와 샘플 시나리오의 HTML·ID는 보존하고 사용자가 저장한 문구·이미지 overrides를 덮어쓰지 않는다.
- 실제 활용 예시는 `export_agent_data.mjs`가 함께 내보내는 `kb/layout_examples.json.gz`의 시나리오 채움 값과 실제 장 순서를 읽는다. 관리자 시트 프리뷰는 스크립트를 차단한 sandbox에서 렌더한다.

### 디자인 코드 (Export · Upload · 비교)

상세 팝업의 시트 도구줄 왼쪽 `Export` 는 그 장의 디자인 코드(`{f}.design.html` — 지금 디자인 + code agent 용 규칙)를 내려받는다. code agent 가 고친 결과본을 `Upload` 하면 서버가 검사하고(`app/api/layout_library.design_check`: 칸 `data-tb`/`data-img` 번호 · 개수 그대로, 최상위 1280×720 요소 하나, 인라인 style 만, `<script>`·`<style>`·`<iframe>`·이벤트 속성·`javascript:` 금지, `data-fix` 는 기본 장 값으로 맞춤) 「디자인 비교」 팝업에서 지금 디자인과 같은 크기로 나란히(또는 겹쳐 밀어 보기) 보여 준다. 한쪽 칸에 마우스를 올리면 다른 쪽 같은 칸도 표시된다. `올린 디자인 적용` → `layout_library.json` 의 그 장 `design`(html · version · 파일 이름 · 누가 · 언제) — `apply_html`(composer · KB · 관리자)과 `applyLibraryHtml`(웹앱 화면 · 채우기 · PPTX)이 그 장의 틀로 쓰고, 글 · 칸 정책 수정은 그 위에 그대로 얹힌다. 도구줄의 `올린 디자인 ×` 로 기본 디자인으로 되돌린다. API: `GET /{f}/design` · `POST /{f}/design/check` · `PUT /{f}/design` · `DELETE /{f}/design`.

- 팝업 위에 여는 팝업(비교 · 확인 · 실험 …)은 아래 팝업의 본문 자리 안쪽에만 놓인다 — 깊어질수록 작아지고 아래 팝업의 머리 · 바닥을 가리지 않는다(`components.jsx` `useNestedBox`).
- 시트 iframe 은 스크립트를 막은 sandbox 라서 Safari 는 그 안의 이벤트 리스너를 부르지 않는다 — 시트 영역 hover · 클릭 편집 · 글 변경은 모두 부모 쪽(투명 덮개 + 잰 영역 상자 + MutationObserver)에서 처리하고 iframe 안에는 리스너를 두지 않는다.

### 입력 · 흐름 (레이아웃별 input contract · agentic flow)

`app/api/layout_flows.py`가 레이아웃마다 ① 입력 `inputs:[{param, source, required}]`과 ② 흐름 `nodes:[{id, module, label?, prompt?, reads?}]`을 정의한다. 기본 정의는 레이아웃 자체(종류 · 카탈로그 `req` · 칸 정책)에서 만들고 지금 composer 가 그 장에 하는 일과 같다. 관리자 수정은 `app/data/runtime/layout_flows.json`(`WINMATE_LAYOUT_FLOWS`)에 대표 레이아웃 단위(내용 후보 공유)로 저장되고, 다음 자동 구성부터 바로 쓰인다(재시작 불필요).

- 입력 소스(Storyboard 에서 레이아웃이 받을 수 있는 정보 전체)도 같은 파일에서 관리한다 — 레이아웃 관리 상단 ‘입력 소스’ 또는 상세 머리 ‘입력 n’ 드롭다운의 톱니. 분류: Storyboard 맥락(요구사항 요약 · 원문 · 요구 포인트 · 고객 · 제목 · 업종 · 세부 업종 · 키맨 · 첨부) · 파트 orchestrator(파트 지시 · 덱 메시지 · 앞뒤 파트 · 목차 번호) · DSS(제품 · 솔루션 · 사례 · 구독 · 서비스 ID) · 공간(공간 목록 · 공간별 활용 · 조감도) · 요구사항 추출 값(고객 수치 · 규모 · KPI · 과제 · 현재 운영 · 사용자 · 일정 · 예산 · 수량 · 경쟁사 · 평가 기준 · 담당자) · 시장 근거 · 덱 · 자산(견본 · 이미 쓴 사진 · 일자 · 로고). 공급: 지금 전달됨 / 외부 정제 후 전달 / 미연결.
- `requirement_summary`(요구사항 요약 context)와 `part_directive`(파트 orchestrator 지시)는 글을 쓰는 흐름의 필수 입력이다(제품 스펙처럼 데이터만 채우는 장은 예외). 꺼진 소스는 흐름에서 빠진다.
- 외부에서 정제한 값은 자동 구성(`/api/jobs` kind compose · step auto) 요청의 `layout_inputs: {소스 키: 값}`으로 보낸다. 레이아웃별 요구는 `GET /api/layout-flows?f=L_X&f=L_Y`.
- 도구(레이아웃 관리 홈 ‘도구’): 여러 레이아웃이 다시 쓰는 tool calling 도구. 종류 = RAG(DSS 지식 · 샘플 시나리오 문구) · 웹 검색(정책브리핑 · 경제지 자체 검색) · 검색(DSS 카탈로그 · 사진 · 근거 DB) · DB 조회(연결한 DSS 사실). 설정(JSON) · 켜기/끄기 · 시험 실행 · 새 도구(종류 + 설정)를 관리하고, 실행기는 `app/api/poc/layout_tools.py`. 흐름의 문구 작성에 붙인 도구는 작성 호출 전에 `query` 틀로 불려 결과가 그 장 지시에 들어가고, 사용자 정의 단계에 붙인 도구는 모델이 직접 부른다(calls → 결과 → items, 최대 2회). 파이프라인이 이미 부르는 조회(DSS 사실 · 사진 후보 · 시장 근거)는 '내장' 도구로 표시만 한다. 단계 팝업의 ‘로직’은 그 장에서 단계가 읽는 DB · 오브젝트와 처리(`layout_flows.logic_for`).
- 요소별 작성(fan-out / fan-in): 한 장에 서로 다른 항목(제품 · 솔루션 · 공간 · 요구)이 섞인 장은 ‘문구 작성’ 대신 ‘요소 나누기 → 요소별 작성 → 모으기 · 제목’으로 쓴다. 요소(카드 · 행 · 열)는 `app/api/layout_elements.py`가 찾는다 — 구성에 쓰는 장은 설계(니즈 3행 · 핵심 제안 2행 · 공간별 제품 카드), 생성 장은 이름 붙은 칸(nm0 · kw0_1 …), 나머지는 같은 크기 칸이 일정 간격으로 반복되는 모양. 항목이 하나뿐이거나 주제형 요소(단계 · KPI)만 있는 장은 칸이 36개 이상일 때만 나누고, 칸 설계의 `split`이 레이아웃마다 이 기본값을 정한다. 실행(`app/api/poc/layout_fanout.py`): 코드가 요소마다 담당(니즈 열 ↔ 요구 · 답하는 항목, 핵심 제안 행 ↔ 항목 — 칩은 코드가 씀, 카드 j ↔ 제품 j, 시나리오 ↔ 공간)을 정한 뒤 요소마다 따로 · 동시에 쓴다(그 요소 칸 · 담당 항목 자료만 · 맡은 요구 · 요소 지시 · 다른 요소 이름). 모으기는 같은 말 · 다른 요소 항목 이름 · 미선택 이름 · 항목 이름만 쓴 칸 · 빈 칸을 찾아 그 칸만 다시 쓰고(2회차는 피할 문구 명시), 요소가 맡지 않은 요구는 제목 · 부제가 답한다. 파트 검수의 고침도 요소 칸이면 그 요소 안에서 다시 쓴다. 흐름도에서 요소 상자를 누르면 그 요소 지시(비우면 공통 지시), 요소별 작성 · 문구 작성 팝업에서 ‘한 번에 쓰기’ ↔ ‘요소별로 나눠 쓰기’.
- Decision 분기(`app/api/poc/layout_decide.py`, 작업 `layout.cells` · `layout.verify` · `layout.pictures` · `layout.review`, `settings.DECISION_TASKS`): 판단형 단계마다 Decision 모델(System One — choice · score · noul) 버전이 있고, Decision 키가 있고 작업이 켜져 있을 때만 노드 안에서 바뀐다 — 앞뒤 입출력은 LLM 분기와 같다. 문구 작성: 정해진 보기 칸(`app/data/layout_decisions.json`, 레이아웃마다 설계 — 고른 제품 · 솔루션 · 사례 · 공간 · 모델 이름은 쓰기 전에 정해 작성기에 고정 칸으로, ● · 등급 · 상태는 쓴 뒤 판단, n번째 · 복사 · 개수는 코드)만 Decision이 채우고 나머지 칸은 LLM이 쓴다. 사실 · 요구 검수: 요구마다 답한 칸(choice) · 칸마다 문제(choice) → 걸린 칸만 LLM이 고친다. 사진: 칸마다 맞음 · 어긋남과 대신 쓸 사진(choice). 파트 검토: 장마다 다시 쓸지 · 이유(choice) → 다시 쓸 장만 LLM이 다시 쓴다. 레이아웃별 5샘플 검증에서 LLM보다 못한 단계는 그 레이아웃만 `off`(LLM 유지). Decision 요청이 실패하면 그 노드는 LLM이 맡는다. 흐름도 노드의 ‘D’ 칩 · 단계 팝업의 Decision 탭에서 질문 형식 · 지시 · 보기 · 사용 여부와 실제로 보내는 state · questions 를 본다. 검증 기록: `docs/decision-model/LAYOUTS.md` · `docs/decision-model/layouts/<레이아웃>.md`.
- 최종 점검 · ReAct(`app/api/poc/layout_final.py`, 흐름 모듈 `final`, Decision 작업 `layout.final`): 모든 흐름의 마지막 단계(지울 수 없음). 다 쓴 장을 관찰(코드: 고르지 않은 이름 · 카드 이름과 다른 항목의 설명 · 사진 · 같은 문장 · 같은 항목 이름 · 같은 사진 · 레이아웃 원래 내용 대비 칸 형식 — 숫자 · 기호 · 라벨/문장 길이 · 빈칸 · 칸 폭) → 판단(Decision: 쓴 칸마다 ‘칸의 일 · 같은 카드 항목’ choice, 걸린 칸만 LLM `auto_final_fix` / Decision이 없으면 LLM `auto_final_check`이 도구 item · image · template을 불러 읽고 고침) → 고침(AI 칸만 · 칸 폭 안 · 고르지 않은 이름을 들이는 고침은 버림 · 같은 사진은 숨김 · 카드와 다른 제품 사진은 카드 제품 컷으로) → 다시 관찰(최대 3회). 남은 것은 장의 검토 항목(‘최종 점검 · …’). 흐름도 노드의 ‘ReAct’ 칩(사용자 정의 단계 · 최종 점검). 결과: 레이아웃 출력 `final` · 장 trace. 검증 기록: `docs/decision-model/FINAL-CHECK.md`.
- 프롬프트 예산(`app/api/poc/prompt_budget.py`): 레이아웃 흐름의 모델 호출은 한 번에 칸 8개(작성) · 12개(판단) 이하, 프롬프트 3,200자 이하 — 더 많으면 장 · 카드 단위로 나눠 동시에 보내고 답을 모은다(작성 `sheet_writer.py` · 검수 `sheet_check.py` · 파트 계획 · 검토 · 사진 · 최종 점검 · 사용자 정의 단계). 흐름도 단계 팝업의 ‘로직’에 묶음 크기가 보인다. 전 · 후 측정: `docs/prompt-budget.md`.
- 칸 설계(`app/data/layout_cells.json`, `app/api/layout_cells.py`): 사용 중인 쓰기 레이아웃 400장마다 AI가 쓰는 칸 하나하나의 역할(무엇을 · 어떤 형식으로) · 그대로 둠(서수 · 열 머리 · 범례 같은 구조 표지) · 숫자만(고객 · 제품 자료에 있는 수만, 없으면 빈칸)과 장 단위 `say`(이 장이 말할 것 — 기본 장 지시) · `split` · `element`. 실험실 결과를 칸마다 읽고 고친 설계다. composer는 칸 설명에 역할을 쓰고(파트 호출 · 요소 작성 모두), 그대로 둠 칸은 잠그고, 숫자 칸에 자료에 없는 수가 들어가면 비우고, 선택 항목 이름 칸은 고른 이름만 받으며(변형은 고른 이름으로 맞춤), 한자 · 칸 역할 문구를 그대로 쓴 답은 다시 받는다. 상세 머리의 ‘칸 설계 n/m’ 드롭다운에서 레이아웃별로 고치고(흐름 레지스트리 `cells`에 저장, `PUT /layout-library/{f}/cells`), 설계와 같아지면 수정 기록이 지워진다.
- 흐름도 읽기: 흐름의 첫 단계는 `input` — 누르면 팝업에 머리 ‘입력 n’ 팝업과 같은 JSON 편집기(`{param: {source?, type, required}}`)가 열린다. 흐름도 카드에는 단계 이름 · 종류만 있고, JSON 과 단계마다의 `in` · `out`(그 장의 상태에서 읽고 쓰는 것 — `layout_flows.io_for`, 칸 번호는 그 레이아웃의 실제 칸)은 단계 팝업에서 본다. Decision 분기가 있는 단계(문구 작성 · 요소별 작성 · 사진 · 검수 · 최종 점검)는 팝업이 **LLM | Decision** 탭으로 나뉜다(노드의 ‘D’ 칩을 누르면 Decision 탭으로 열림, 앞뒤 in/out 은 같다). **모델 입력**: 저장된 흐름을 샘플 입력(`layout_experiments.samples`, 업종 고르기)으로 실제 composer 코드에 돌려 각 단계가 보내는 호출을 그대로 보인다 — LLM `generate_json` 의 system · prompt · 출력 schema · temperature · max_tokens, Decision `POST {base}/systemone` 의 state · questions(질문마다 question_type · instructions · criteria)와 question_type 정의(choice · score · noul). 모델은 부르지 않는다: 대역이 기록하고, LLM 대역은 프롬프트가 요구한 칸에 레이아웃 원래 문구를 max 안에서 넣어(나머지는 빈 값 — 문제 · 도구 호출 없음) 뒤 단계가 실제와 같은 모양의 장을 보게 하며, Decision 대역은 ‘ok’(없으면 첫 보기)로 답한다. 그래서 걸린 칸이 있을 때만 도는 후속 호출(고침 · 다시 쓰기)은 샘플에 따라 보이거나 안 보인다. 파트 계획(`auto_part_plan`, 이 장 지시 part_directive 를 만드는 orchestrator 호출)은 ‘입력 정리’에 보인다. 저장 안 됨(텔레메트리 ephemeral · 요청 범위 스냅샷). API `GET /layout-library/{f}/flow/trace?industry=` → `app/api/poc/layout_trace.py`.
- composer 반영(`app/api/poc/layout_flows.py`, grounded 엔진에만 설치): 문구 작성 프롬프트와 읽는 입력 → 그 장의 지시로 파트 작성 호출에 들어감 · 요약 입력이 있으면 요약이 파트 호출에 들어감 · 없는 필수 값은 '없음 — 지어내지 않음'으로 명시 · 사진 프롬프트 → 사진 선택 지시 · 사용자 정의 단계(`auto_flow_agent`) → 글 작성 뒤 그 장의 AI 칸만 고침. 수정된 흐름에서 문구 작성 · 칸 길이 맞춤 · 사진 고르기 · 검수를 빼면 그 장에서 그 단계가 돌지 않는다(기본 흐름은 동작 그대로).

### 원본별 갱신

**Samsung Business**: 현재 탐색 메뉴와 기존 분류의 합집합을 수집한다. 원래 수집기를 작업 폴더용으로 변환하여 실행하며 원본 수집기 자체는 수정하지 않는다. 목록·필터 전체 페이지, 옵션별 사양, PDP 특장점을 수집한다. 빈 사양·차단·페이지 누락·파서 오류가 있으면 반영하지 않는다. AI가 변경과 누락 후보를 검토하고 기존 제품 ID와 관리자 메모를 유지하여 관리 DB에 반영한다. 사라진 항목은 검토 후보이며 물리 삭제하지 않는다.

**e-Catalog**: 현재 공개 목록과 기존 권의 합집합을 확인한다. `b2b:272`와 `b2c:272`처럼 경로와 Dir를 함께 식별한다. 점검은 '데이터 소스 최신성 점검' 절의 방식으로 한다. 신규 발견일과 실제 업로드일을 혼동하지 않는다. 기존 ID를 새 순번으로 재할당하지 않는다. 최신화에서는 모든 쪽을 다시 조회하고 쪽별 원문에서 제품·모델·인용을 추출한다. 중복 엔터티는 동일 문서·모델·이름 기준으로 합친다. 이미지 전용 쪽, 사진 crop·PDF 개정 비교·영상은 미검토 범위로 명시한다. 텍스트 전체 수집을 전체 시각 자료 검증으로 표시하지 않는다.

**솔루션·사례**: 현재 등록된 공식 원문 URL을 각각 조회하고 구조화한다. 연결된 모든 영상·PDF·신규 목록 페이지를 수집했다고 표시하지 않는다. 추가 URL 소스는 해당 페이지의 공개 본문을 대상으로 한다.

**로컬 자료**: 기존 원본·템플릿·배경·공간 라이브러리를 재색인한다. 이미 새 원문으로 갱신한 소스와 관리자 메모·보관 상태는 이전 저장소 값으로 덮어쓰지 않는다.

### 보존과 복구

모든 갱신은 `runtime/releases/<job>-<source>/`에서 수행한다. 원문, 수집 인벤토리, 변경표, 반영 데이터, 소스별 복구본을 보존한다. SQLite 반영과 FTS 갱신·버전 기록은 하나의 `BEGIN IMMEDIATE` 트랜잭션으로 처리한다. 수집 확인 시각이나 모델 사용량만 달라진 행은 사실 내용 변경과 구분한다.

복구는 소스의 활성 릴리스에만 허용한다. 반영 이후 메모·태그·내용·상태·에셋 구성이 바뀌면 복구를 중단하여 뒤의 작업을 보존한다. 여러 소스를 갱신하다 취소한 경우 이미 완료한 소스는 유지하고 그 결과를 작업에 남긴다.

자동 점검은 기본적으로 꺼져 있다. 화면에서 켜면 소스별 주기에 맞춰 최신성 점검을 수행하며, DB 갱신은 직접 실행한다. 접속 실패나 일부만 확인한 원본을 '최신'으로 바꾸지 않는다.

## 데이터 소스 최신성 점검

데이터 소스의 「점검하기」는 **실제 DB 기록을 그 자료를 받아 온 실제 원본과 대조**한다(`admin/origins.py`). 홈 메뉴나 허브 페이지의 글을 AI 가 읽고 추정하지 않으며, 판정에 AI 를 쓰지 않는다.

| 소스 | 실제 원본 | 대조 기준 |
|---|---|---|
| Samsung Business | samsung.com/sec/business 분류 목록 · 옵션 · 사양 · 상품 페이지 특장점(점검 채널 `site`, 약 10분) | `proddb/raw` |
| e-Catalog | 목록의 권 · 쪽 수 · 뷰어 제목 · 쪽 이미지 파일 수정 시각(채널 `ecat`, 1분 이내) | `proddb/ecat` |
| 솔루션 & 도입사례 | 솔루션 · 분류 · 근거 페이지(채널 `solutions`, 약 7분) + 도입사례 목록 전체(번호 · 제목 · 주소) | 솔루션 레지스트리 · 버티컬 근거 · 제품군 분류의 주소, `app/data/catalog.json` 의 사례 |
| 연결한 URL 소스 | 등록한 주소의 본문(메뉴 · 푸터 제외) | 마지막 「DB 최신화」가 보존한 원문 |

- **판정**: 다른 항목이 하나라도 있으면 `갱신 권장`, 확인하지 못한 원본이 있으면 `확인 필요`, 모두 같을 때만 `최신 확인`. 소스 상세의 「점검 근거」에 원본별 대조 기준 · 확인 범위 · 다른 항목(링크 · 이유) · 확인하지 못한 주소가 나온다.
- **한 가지 기록**: 채널 대조는 「소스 점검 · 업데이트」의 일일 점검과 같은 실행 · 같은 기록(`dss_checks`)이다. 일일 점검이 끝나면 소스 카드도 함께 바뀌고(도입사례 목록 · 넣은 링크까지 확인), 서버를 다시 켜도 마지막 대조 결과로 맞춘다. 채널을 쓰는 점검은 원천 소스 작업과 같은 전용 대기열에서 하나씩 돈다.
- **원본 주소 · 리소스 링크**(소스 상세 「원본 · 링크」): 원본 주소는 바뀔 수 있다 — e-카탈로그는 호가 바뀌면 권 주소(Dir)가 바뀌고, 목록에 없는 권도 있다.
  - e-Catalog: 목록 주소를 바꿀 수 있고, 권 링크(`…ecatalog5.php?Dir=번호`)나 다른 목록 페이지를 넣으면 채널 점검이 함께 대조한다(`watch.py --links`). DB 에 없는 권이면 새 권으로 나와 `갱신 권장`이 되고, 열리지 않는 링크는 `확인 필요`가 된다. 목록에 없는 기존 권은 링크를 넣으면 '목록에서 빠짐'으로 보지 않는다.
  - 그 밖의 소스: 넣은 주소는 처음 점검한 본문을 기준으로 잡고, 이후 주소 이동 · 제목 · 본문이 달라지면 `갱신 권장`으로 표시한다(바뀐 줄을 함께 보여 준다). 「바뀐 내용 확인 · 새 기준으로」를 누르면 지금 본문이 새 기준이 된다. 받을 때마다 본문이 달라지는 페이지는 글이 아니라 제목 · 주소로만 판정한다.
  - 링크는 공개 HTTPS 주소만 받는다(소스마다 40개까지).
- **홈의 「최신성 점검」**: 버튼을 누르면 팝업에서 원본(samsung.com/business 제품 · e-카탈로그)을 여러 개 고르고 시작한다. 고른 원본은 **동시에** 점검한다 — 두 채널은 DB 를 읽기만 하고 받는 폴더가 달라 서로 기다리지 않는다(`Service.check_pool`). 대조 도중에 DB 가 바뀌지 않도록 소스 업데이트 · 삭제와는 서로 겹치지 않게 막는다. 창을 닫아도 계속 진행되고, 다시 열면 진행 화면으로 돌아온다.
  - 제품 보고: DB 상품 카드 수 ↔ 원본 수, 같음 · 바뀜 · 신규 · 판매 종료 후보(원본 목록에서 빠짐) 건수와 **전체 목록**(이름 · 모델 · 분류 · 링크, 앱 제품이 쓰는지), 바뀐 제품마다 무엇이 어떻게 달라졌는지(이름 A → B, 모델 추가 · 빠짐, 품절 상태가 바뀐 모델, 사양표가 바뀐 옵션 수, 특장점), 상품 번호만 바뀐 카드, 메뉴의 새 분류. 줄이지 않은 내역은 `GET /admin/api/sources/{id}/report`.
  - e-카탈로그 보고: 권마다 원본 파일이 DB 에 받은 것과 같은지 다른지(쪽 파일 수정 시각 ↔ 받은 시각), 다른 권의 이유와 바뀐 쪽, 새 권 · 빠진 권.
- 다른 항목을 실제 DB 에 반영하는 것은 「소스 점검 · 업데이트」의 채널별 업데이트다.

```bash
app/.venv/bin/python -B -m pytest admin/tests/test_origins.py -q
```

## 소스 점검 · 업데이트

다른 화면이 관리자 격리 DB 를 다루는 것과 달리, 이 화면은 **앱이 실제로 쓰는 DSS DB** 를 대상으로 한다.

- **매일 점검**: 매일 09:00(KST, 화면에서 시각 · 켜기/끄기)에 `proddb/build/dss/watch.py` 를 실행해 채널별 변경 여부를 기록한다 — samsung.com/business 제품(목록 · 옵션 · 사양 · 특장점, 약 10분) · 솔루션 · 분류 페이지 · e-카탈로그(파일로: 권 목록 · 쪽 수 · 쪽 이미지 파일 수정 시각) · B2B 삼성 AI 구독. 그 시각에 서버가 꺼져 있었으면 켜진 뒤 그날 한 번 실행한다(관리자 저장소를 처음 켜는 날은 이미 그 시각이 지났으면 건너뛰고 다음 날부터 — '지금 점검'은 언제든 된다). 점검은 DB 를 바꾸지 않는다. 수집이 실패하거나 일부만 된 채널은 '변경 없음'으로 표시하지 않는다. 점검 때 받은 원문은 `output/dss/watch/<시각>/` 에 최근 3회분만 남긴다.
- **코드 에이전트 연결**: Claude Code 또는 Codex CLI 를 OAuth 로 연결한다. 화면이 CLI 의 공식 로그인을 대신 진행한다 — 인증 페이지를 열어 로그인하고, Claude Code 는 페이지가 보여 준 코드를 붙여 넣고 Codex 는 화면의 기기 코드를 페이지에 입력한다. 연결 정보는 서버 계정의 개인 CLI 로그인과 분리해 `admin/runtime/agent/<claude|codex>/` 를 CLI 홈(`CLAUDE_CONFIG_DIR` · `CODEX_HOME`)으로 쓰고, 토큰은 CLI 가 보관한다(관리자 DB · 로그 · 브라우저에 남기지 않는다). 서버 환경의 API 키는 에이전트에 넘기지 않는다.
- **채널별 업데이트**: 채널 카드의 '업데이트'가 그 채널의 고정 프롬프트(`admin/dss.py` `update_prompt`, 실행 전 화면에 그대로 표시)로 에이전트를 실행한다. 에이전트는 `.agents/skills/winmate-update-dss-db` 를 그 채널 범위로 수행하고, 같은 날 점검이 받은 원문을 다시 쓴다. 판매 종료 항목은 표시까지만 한다. 로그와 결과는 실행 기록에서 본다.
- **삭제 후보 확인 · 삭제**: 판매 종료로 표시된 항목이 근거 · 대체 제품 · 연관 자료와 함께 나온다. 고른 항목을 확인 창에서 한 번 더 확인해야 `proddb/build/dss/deletions.py apply` 가 실행된다 — 제품 DB 에서 지우고, 샘플 시나리오 · 조감도 3D 오브젝트 · 레이아웃 · 에이전트 KB 까지 반영하고, 검증에 실패하면 모두 되돌린다. 이름 · 모델이 샘플 시나리오 · 레이아웃 글에 남은 항목은 '연관 글 정리'(에이전트)를 먼저 실행해야 삭제할 수 있다.

## 레이아웃 구성 관리

`/admin/layouts`. Storyboard의 '레이아웃 구성' 버블이 추천하는 **구성**(목차 템플릿 — 표준 제안서 · 공간 가치형 · 투자 효과형 …)을 관리한다. 구성의 구조(목차 흐름 · 목차마다의 장 · 업종별 시나리오)는 코드(`app/web/src/domain/templates/toc_templates.js`)가 정본이고, 이 화면은 그 위에 덮는 **운영 값**만 바꾼다. 화면은 앱과 같은 모듈을 직접 읽어 그리므로(관리자 빌드의 `chunks/`) 보이는 순서 · 꺼짐 · 기본 구성은 앱이 계산하는 값 그대로다.

- **바꿀 수 있는 값**: 추천에 사용(켜기 · 끄기) · 순서 · 기본 구성(추천 첫 칸) · 이름 · 설명 · 맞는 상황(추천 모델에게 주는 문구) · 연결 샘플 시나리오. 코드 구성의 목차를 더하거나 빼는 구조 편집은 하지 않는다 — 새 흐름은 아래 「구성 추가하기」로 직접 만든다.
  - 끈 구성은 추천 후보 · 전체 구성 보기 · 목차 템플릿 목록에서 빠진다. 이미 그 구성으로 만든 제안서는 그대로다.
  - 기본 구성은 끌 수 없다. 제품 제안서는 제품이 1개인 제안에서만 첫 칸에 놓이므로 기본 구성으로 정할 수 없다.
  - 다른 구성에 '구독 솔루션 제안'만 더한 변형(표준 제안서 + 구독 솔루션 …)은 요구사항에 따라 자동으로 쓰이므로 글 · 연결 샘플만 바꾼다.
- **구성 추가하기**(추천 구성 헤더 오른쪽 끝): 구성(목차 흐름)을 직접 만든다. 팝업에서 파트를 누르면 흐름에 바로 들어가고(다시 누르면 빠진다) 끌어서 순서를 바꾼다(키보드 ← → · Delete 도 된다). 흐름은 큰 파트 버블에 이름을 아래에 두고 번호는 없으며, 빼기(×)는 흐름의 버블에 마우스를 대면 오른쪽 위에 뜬다. 목록은 '만든 파트'(맨 끝에 '새 파트' 타일)가 '전체 파트' 위에 온다. Spec 도 다른 파트처럼 골라 넣고(넣으면 맨 끝), 파트는 4~7개(구독 솔루션이 있으면 8개 — 목차 장이 8칸이고 요구사항에 따라 구독 솔루션이 더해질 자리를 남긴다) · 같은 파트 두 번 없음 — 앱 · 서버가 같은 규칙으로 막는다.

`WINMATE_ADMIN_DATA`로 관리자 데이터 경로를 바꿀 수 있다. Python 선택 의존성은 계속 `admin/runtime/python`에 둔다. AI는 기존 서버의 `WINMATE_LLM_PROVIDER`와 `.env` 로딩 규칙을 공유한다. 기본은 OpenRouter(`OPENROUTER_API_KEY`, `OPENROUTER_MODEL`=qwen/qwen3.6-35b-a3b)이며, 사내 모델은 `INTERNAL_LLM_API_KEY`, `INTERNAL_LLM_MODEL`, `INTERNAL_LLM_BASE_URL`을 사용하고, Gemini를 선택하면 `GEMINI_API_KEY`, `GEMINI_MODEL`을 사용한다. 인증키는 브라우저·DB·로그에 저장하지 않는다. 공개 HTTPS 조회는 DNS 공인 주소 검사·검사한 IP 고정·리디렉션 재검사·용량/전체 시간 제한을 적용한다.

## Provider

`/admin/providers`는 서버가 아는 모든 모델 연결을 보여 준다. LLM은 `.env`의 API 프로필(openrouter · gemini · internal · openai), Decision 모델은 `TYPESAFE_*` 슬롯과 이 저장소의 로컬 Clef 서버(`clef-flash/`, 주소는 `CLEF_HOST` · `CLEF_PORT`)다. 화면은 역할(LLM · Decision 모델)별로 모든 연결을 작은 카드로 보여 준다 — 켠 것(대표 → 대체 순서) 먼저, 꺼진 것, 연결 정보가 없는 것 순서.

- **켜기 · 끄기 · 대표**: 카드의 토글로 켜고 끄고, 켠 카드의 「대표로」로 역할마다 대표 하나를 고른다. 재시작 없이 바로 적용된다. 앱은 대표에게 묻고, 대표가 응답하지 못하면(응답 없음 · 시간 초과 · 인증 거절 · 모델 없음 · 5xx · 429) 켠 순서대로 다음 Provider가 같은 요청에 답한다(대체 1, 2 …). 잘못된 요청 · 형식이 틀린 출력 · 출력 한도 초과 · 취소 · 공용 큐 대기 초과는 어디서나 같으므로 다시 보내지 않는다. 스트리밍은 첫 글자가 나오기 전 실패만 넘긴다. 대체 API는 같은 등급(기본 · quick · vision)의 자기 모델로 답한다.
  - LLM은 하나는 켜져 있어야 한다(마지막 하나의 토글은 꺼져 있다). 대표를 끄면 다음 것이 대표가 된다.
  - Decision 모델(TypeSafe · 로컬 Clef)은 둘 다, 하나만, 또는 모두 끌 수 있다. 모두 끄면 판단형 작업도 LLM이 처리한다.
  - 설정 키: `WINMATE_LLM_PROVIDER`(대표) + `WINMATE_LLM_FALLBACK`(대체, 쉼표 목록), `WINMATE_DECISION_ORDER`(`main` = `TYPESAFE_*`, `clef` = `WINMATE_CLEF_BASE_URL` · `WINMATE_CLEF_MODEL`, 앞이 대표) — `app/api/poc/settings.py`. `.env`로 시작 값을 정하고, 이 화면의 선택은 관리 DB(`provider_active`, 역할별 순서 목록)에 저장해 `.env`보다 먼저 적용한다(재시작해도 유지). `.env`가 고르는 것과 같아지면 저장값을 지운다. 이력: `provider.activate` · `provider.deactivate` · `provider.primary`.
- **정기 점검**: 켠 Provider 전부(외부 API 포함)를 08:00~22:00(KST) 매시 00분 · 30분에 점검한다 — 22:00이 마지막, 그 뒤와 08:00 전에는 하지 않고, 놓친 회차는 다음 회차 전까지만 따라잡는다(23시에 서버를 켜면 점검 없음). 카드에는 결과와 「최근 점검 시각」(오늘이면 14:30, 아니면 날짜와 함께), 화면 아래에 시간표와 다음 점검 시각을 적는다. 외부 API는 토큰이 들지 않는 호출만 쓴다 — OpenRouter 크레딧(`/credits`, 남은 크레딧이 0 이하면 응답 없음) · 모델 엔드포인트, Gemini 모델 정보, TypeSafe 모델 목록(목록은 `jev-latest` · `jev-preview`뿐이라 같은 계열의 버전 고정 ID는 정상). 모델 목록 API가 없는 서버에 1토큰 호출로 확인하는 것은 사내 · 자체 서빙에만 한다. 「지금 점검」은 연결 정보가 있는 Provider 어디서나 된다. `WINMATE_PROVIDER_CHECK_INTERVAL`로 간격(초)을 바꾸고 `off`로 끈다(관리 시험은 기본 꺼짐 — `admin/tests/conftest.py`).
- **주소 수정 · 재연결**: 연결 방식은 같고 주소 · 모델 ID만 바뀌는 사내 서빙용이다(`internal` · `openai` 프로필, 로컬 Clef, 자체 서빙 중인 Decision 슬롯). 「연결 테스트」는 저장하지 않고 입력한 주소를 점검하고, 「저장하고 재연결」은 값을 `admin/runtime`의 관리 DB에 저장해 `.env`보다 먼저 적용한 뒤 다시 점검한다. 활성 Provider라면 재시작 없이 앱 전체가 새 주소를 쓴다. 「원래 설정으로 되돌리기」는 저장한 값을 지운다. `.env` 파일은 고치지 않고, 인증 키는 이 화면에서 보거나 바꾸거나 저장하지 않는다. 주소는 https, 또는 사설망(10.x · 172.16~31.x · 192.168.x · 내부 호스트 이름)의 http만 받는다.
- **실험**: Winmate에서 실제로 생기는 요청을 줄인 샘플(LLM 9개 · Decision 5개, `admin/provider_samples.py`)을 골라 고친 뒤, 등록된 Provider 여러 개에 같은 입력을 동시에 보낸다. 같은 Provider를 다른 모델 ID로 여러 번 넣을 수 있다. 대상마다 요청 하나씩이라 먼저 끝난 결과부터 표시하고 응답 시간 · 토큰 · 초당 토큰 · 출력(JSON 유효성)을 보여 준다. 재시도와 응답 캐시 없이 실제 호출 한 번의 시간이며, 외부 API는 사용량이 발생하고 공용 LLM 큐의 분당 한도를 함께 쓴다.

## 사용자 관리 · 운영 추적

`/admin/users`에서 사용자를 추가하고 `/admin/tracing`에서 운영 대시보드를 연다. 기존 기본 관리자의 비밀번호와 유효한 로그인은 유지하며, 추가 계정은 별도 운영 DB에 보관한다.

- **일괄 생성**: `sales01, sales02, sales03`처럼 쉼표 또는 줄바꿈으로 1~50개 아이디를 입력한다. 자동 생성 또는 직접 입력한 **초기 비밀번호 하나**를 전체 배치에 동일하게 배정한다. 생성 결과에서 한 번 확인·복사할 수 있으며 평문 비밀번호는 DB·행동 로그·trace에 남기지 않는다. 기존 로그인 정책과 동일하게 12자 이상을 사용한다.
- **사용자 목록**(`web/src/users.jsx`, 집계 `activity.py`): 행 전체를 누르면 상세가 열린다. 위의 구분(전체 · 최근 7일 활동 · 30일 미접속 · 로그인 기록 없음 · 사용 중지 · 관리자)으로 거르고 최근 활동 · 최근 로그인 · LLM 토큰(30일) · 작업 수 · 이름 · 등록 순으로 정렬한다. 행에는 최근 활동, 제안서 · 조감도 · 시뮬레이션 수(예시 · 샘플 제외), 30일 토큰, 미접속 · 최근 7일 오류 표식이 있다.
- **사용자 상세**: 탭 순서 활동 내역 → LLM 사용 → 활동 로그 → 실패 로그 → 사용자 정보. 활동 내역 = 기간(오늘 · 7/30/90일 · 전체 · 직접) 총 횟수 카드(제안서 · LLM 토큰 · 제안 시뮬레이션 · 조감도(공간 + 건물) · 제안서 검토 · 로그인/오류) + 일별(90일 넘으면 주별) 그래프(새 기록 · LLM 토큰 · 로그인) + 기록 목록(종류 · 검색 · 상태 · 만든 날 · 최근 작업 · 그 기록에 쓴 LLM 토큰). 카드를 누르면 목록이 그 종류로 걸러진다. 원천은 앱 계정 저장소(`account_data.sqlite`) · 공간 조감도(`spatial.sqlite`) · 운영 DB spans이며 읽기만 한다. 오류는 실제로 깨진 것(5xx · 화면 오류 · 작업 실패 · 재시도 뒤 실패한 AI 호출)만 세고 4xx 거절은 따로 센다.
- **웹앱에서 보기**(기록의 '열기' · 상세 머리 버튼): `GET /admin/api/users/{u}/open?kind=&id=`가 짧은 열람 토큰을 만들어 새 탭에서 웹앱을 그 사용자로 연다(`app/api/inspect.py` · `app/web/src/api/inspect.js`). 토큰은 발급한 관리자 세션에 묶이고(로그아웃 · 만료 · 2시간이면 끝) 그 탭에만 있다. 서버는 그 요청만 대상 사용자로 답하고 쓰기를 모두 거절하며(조회용 POST만 허용), 탭은 대상 계정 기록을 이 브라우저의 저장소에 남기지 않고(메모리 · 탭 전용 IndexedDB) 사용 기록 · 공유 연결 · 배경 보강을 돌리지 않는다. 발급은 `admin.user` · `inspect`로 감사 로그에 남는다. 검사: `tests/test_user_activity.py` · `tests/user-activity-ui.mjs`.
- **계정 관리**: 표시 이름·메모·관리자/사용자 권한·사용 중지·비밀번호 재설정. 중지와 재설정은 기존 세션을 무효화한다. 마지막 관리자를 중지하거나 권한 해제할 수 없다. 기본 관리자와 일반 계정을 함께 재설정하는 경우에는 기본 관리자를 별도로 선택하도록 안내한다.
- **기록 격리**: 새 사용자의 localStorage와 IndexedDB를 계정별로 구분한다. 기존 기본 관리자는 원래 키를 유지하여 기존 문서·사진·My 템플릿을 보존한다. 다른 계정으로 바뀐 탭의 요청은 409로 차단하고 다시 불러온다. 비관리자는 다른 사람의 AI 작업·결과·취소 API를 이용할 수 없다.
- **전체 히스토리 보관**: 제안서·검토·시뮬레이션·브라우저 작업·서버 작업·고객 프로필·찜·My 템플릿의 저장 내용과 이전 버전을 사용자별로 보관한다. 기존 브라우저 기록은 해당 계정으로 앱/관리자를 열 때 수집한다. 오래된 브라우저의 일부 목록으로 다른 기기의 문서를 일괄 제거하지 않으며, 명시적으로 제거한 ID만 이전 기록으로 표시한다. 서버 작업 감사 이력은 클라이언트가 덮어쓸 수 없다.
- **화면 활동**: 화면 진입·이탈 시각과 체류 시간, 버튼·링크·탭·팝업·변경 동작을 수집한다. 비밀번호 입력값과 일반 폼 입력 내용·키 입력은 행동 로그로 남기지 않는다. 계정별 브라우저 outbox로 오프라인·새로고침 후 전송을 재시도하며 이벤트 ID로 중복 집계를 방지한다.
- **실패 추적**: HTTP 오류, 브라우저 오류/미처리 Promise, 백그라운드 작업 실패, 모델 실패를 사용자·화면·기능·코드·trace ID로 조회한다. 같은 trace에서 요청·작업·실제 LLM 호출의 부모 관계와 시간, 오류 메시지·stack을 팝업으로 확인한다. 로그인 실패에서 미등록 아이디는 원문을 보관하지 않고 지문으로 구분한다.
- **토큰 추적**: 실제 서버 LLM 응답의 입력·출력·추론·캐시 입력·전체 토큰을 요청별로 기록한다. 전체 토큰은 API가 보고한 값이며 부분 필드를 임의로 더하지 않는다. JSON 재시도는 각 실제 호출로, SSE 사용량은 마지막 누적 값 한 번으로 집계한다. 응답 캐시 재사용은 새 토큰 사용으로 집계하지 않는다. 실패·취소 등 사용량이 보고되지 않은 호출은 `미보고`로 표시한다.
- **대시보드**: 오늘·7/30/90일·직접 기간, 사용자·기능·모델 필터, 시간/일별 사용량 그래프, 기능별 분포, 방문 횟수와 최초/최근 시각, 활동·실패·LLM 요청 목록, 로그 JSON 내보내기를 제공한다. 시간대는 한국시간이며 기록이 없는 구간은 0으로 표시한다. 과거의 미수집 화면 활동이나 토큰을 생성하지 않는다.

운영 DB는 `admin/runtime/operations.sqlite`다. 계정 해시를 일반 에셋 JSON/테이블 탐색에 섞지 않는다. 시스템의 **DB 백업 → 사용자 · 추적 DB**로 별도 SQLite 사본을 만들 수 있다. 기본 관리자의 기존 인증 파일은 기존 `app/data/runtime/auth` 경계를 유지한다. 공통 앱의 인증·provider·작업·브라우저 저장 경계에는 선택적 연결 훅이 있으며, 실제 사용자 관리·운영 저장·대시보드는 결합 서버 `admin.server:app`에서 활성화된다. Git에서 제외한 운영 DB와 업로드·백업은 배포 환경의 영속 저장소에 별도로 보관한다. 관리자 없이 `app.api.main:app`을 직접 실행하면 기존 단일 계정과 비활성 추적 상태로 동작한다.

운영 테스트:

```sh
app/.venv/bin/python -B -m pytest admin/tests/test_admin.py admin/tests/test_operations.py app/tests/test_auth.py app/tests/test_provider_strict.py -q
WINMATE_ADMIN_TEST_URL=http://127.0.0.1:8796 WINMATE_ADMIN_LIVE=1 node admin/tests/operations-ui.mjs
```

브라우저 테스트는 별도의 `WINMATE_ADMIN_DATA`, `WINMATE_AUTH_DIR`, 사용자 저장 경로를 사용하는 격리 서버에서 실행한다. `WINMATE_ADMIN_WEB_DIST`와 `WINMATE_WEB_DIST`로 시험 빌드를 지정할 수 있다. 실제 JSON/SSE 모델 사용량과 계정 격리·오프라인 전송 결과는 `runtime/evidence/operations/`에 있다.

별도 구버전 비교 검사인 `app/tests/test_stage1_api.py`에는 현재 공개 bootstrap 정책과 검토된 제품 상세 overlay를 과거 동결본과 비교하는 기대값 차이가 있다. 해당 다섯 비교 항목은 이번 사용자·추적 검증 결과에 포함하지 않았고 앱의 현재 데이터 정책을 되돌리지 않았다.

### 에셋 관리 기존 검증

```sh
node admin/build.mjs
app/.venv/bin/python -B -m pytest admin/tests/test_admin.py -q
node admin/tests/collector.mjs
```

브라우저·실모델 검사는 production과 다른 인증·사용자 자료·관리 데이터 경로의 격리 서버에서 실행한다. `tests/ui.mjs`와 `tests/live.py`의 테스트 계정은 이 검사용 서버에만 생성하는 합성 계정이다. 실제 사용자 비밀번호를 읽거나 재설정하지 않는다. `tests/live.py`는 서버에 설정한 실제 LLM을 호출하며 사용량이 발생한다.

```sh
WINMATE_ADMIN_TEST_URL=http://127.0.0.1:8794 node admin/tests/ui.mjs
WINMATE_ADMIN_TEST_URL=http://127.0.0.1:8794 app/.venv/bin/python -B admin/tests/live.py
```

검증 결과와 화면은 `runtime/evidence/`에 보관한다. `live-results.json`은 카탈로그 목록 최신성 판단, 합성 문서 분석, 공개 페이지의 실제 갱신·관리 DB 반영, 버전 복구, DB 진단 결과이다. 삼성 전체 재수집과 모든 카탈로그 전권의 실모델 분석을 완료한 결과는 아니다.

### 에셋 이미지 · 전체 리소스

에셋 상세의 첫 화면에 대표 이미지와 관련 사진을 표시한다. **전체 리소스**에서는 이미지·장표·문서·영상·3D 파일·원본 데이터·출처 링크를 종류와 그룹, 파일명으로 찾는다. 선택한 리소스는 팝업 안에서 확대하며 원본 크기 전환, 개별 다운로드, 크기와 연결 근거, 출처 페이지 열기를 제공한다. 목록으로 돌아오면 필터와 페이지를 유지한다.

- 제품의 `img` PID, 썸네일·갤러리 pack 주소, 정확한 제품 ID로 연결된 이미지 라이브러리, 검토된 제품 상세의 첨부·카탈로그 연결을 읽는다. 비슷한 모델명을 근거로 다른 제품의 이미지를 연결하지 않는다.
- 솔루션·도입사례는 미디어 인덱스의 대표 사진·갤러리·원본 주소를 해석한다. 카탈로그는 등록된 전체 쪽과 연결된 추출 이미지·PDF 주소를 보여준다. 외부 파일을 서버가 임의로 수집하거나 접속 성공으로 표시하지 않는다.
- JSON 이미지 묶음은 실제 슬롯 번호를 보존하고, 한 장씩 디코딩·다운로드한다. 빈 슬롯·삭제된 파일은 확인 필요로 표시한다. 실제 앱의 `/img/lib`, 배경, 동결 이미지 경로 우선순위를 따른다.
- 레이아웃·시나리오의 장표 HTML, `data-fill` 사진과 CSS 배경, 시나리오 배경 풀을 연결한다. 장표 미리보기는 스크립트·탐색을 막은 sandbox에서 표시한다. 공간 에셋은 실제 썸네일·형상 근거 이미지·연결 제품·참조 장표를 표시한다.
- 업로드한 이미지·문서는 원본을 제공한다. PDF의 모든 쪽·삽입 이미지·첨부파일과 PPTX/DOCX/XLSX의 media·embeddings 항목도 각각 조회한다. TIFF 등은 보기용 형식으로 변환하고 원본 다운로드는 보존한다. 앱이 직접 미리볼 수 없는 파일은 원본 다운로드로 확인한다.

리소스 URL은 선택한 에셋의 연결 목록에서만 만들어진다. 임의 경로 요청, 사용자·인증·추적 DB, 비밀 파일과 허용 폴더 밖 symlink는 제공하지 않는다. HTML·코드 파일은 첨부 다운로드 또는 텍스트로 제공하고, SVG에는 실행을 차단하는 CSP를 적용한다. 모든 API와 원본은 기존 관리자 인증을 요구한다. 원본 DB나 동결 pack을 변경하지 않으며 구현은 `admin/`, 실행 데이터는 Git 제외된 `admin/runtime/`에 보관한다.

```sh
app/.venv/bin/python -B -m pytest admin/tests/test_resources.py -q
app/.venv/bin/python -B admin/tests/resource_fixtures.py admin/runtime/resources-e2e
WINMATE_ADMIN_TEST_URL=http://127.0.0.1:8796 node admin/tests/resources-ui.mjs
```

브라우저 검사는 위 경로를 `WINMATE_ADMIN_DATA`로 지정한 별도 서버와 합성 관리자 계정을 사용한다. 결과와 데스크톱·모바일 화면은 `runtime/evidence/resources/`에 보관한다.
